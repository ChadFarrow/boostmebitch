# Streaming sats — ledger, valueTimeSplits, live value, readouts

Read before touching `lib/v4v/streaming.ts`, `stream-ledger.ts`, `live-value.ts`, `live-block.ts`, or `components/streaming-settings.tsx`.

Core rules live in [`../CLAUDE.md`](../CLAUDE.md); this file holds the reasoning.

## Streaming sats (`action: 'auto'`)

The third Podcasting 2.0 payment mode, alongside the boost button and boost-all. `lib/v4v/stream-ledger.ts` (pure math) + `lib/v4v/streaming.ts` (the engine). **Off by default** — nothing is spent until the user flips the switch.

It is a ledger and a clock on top of the existing engine, **not a new payment path**: settlement calls the same `sendBoost()`, with `action: 'auto'` on the boostagram (a field `lib/types.ts` and `lib/v4v/boostbox.ts` already carried). Rails, splits, TLV and the lnaddress→keysend upgrade are untouched, so all three rails work — batching at 10 minutes is what keeps Spark (BOLT11-only, an LNURL invoice per leg) affordable.

**`action` is `'auto'`, not `'stream'` — the two describe different cadences.** `'stream'` is the per-minute drip, one payment per minute per recipient; what we actually send is a ten-minute lump for time already listened, which is what `'auto'` names. Tagging it `'stream'` made each batch read as one minute of listening in the receiver's stats. `'boost'` stays reserved for the button, so a host's deliberate one-tap payments remain separable from ambient ones. **Confirmed against a real Helipad:** `'auto'` lands in the **Stream tab, flagged with an AutoBoost marker** — so the batches stay out of the host's boost feed while still reading as distinct from a per-minute drip, which is exactly the split this tagging exists to produce.

**The two wire surfaces disagree on purpose, and `lib/v4v/boostbox.ts` must keep downgrading `'auto'` → `'stream'`.** Keysend legs carry `'auto'` verbatim in the TLV. BoostBox — which is how the *LNURL* legs carry metadata — validates `action` against a strict malli enum, `[:enum "boost" "stream"]` (`src/boostbox/boostbox.clj`), so posting `'auto'` is rejected; the rejection is silent and non-fatal, meaning the leg loses its whole `desc` descriptor and degrades to the bare user message. The action string also lands verbatim in the BOLT11 description BoostBox builds (`rss::payment::<action> <url>`). **Widening that mapping requires widening the enum on the BoostBox side first.**

**Every rule here follows from one property: this spends money unattended, on a timer, with no confirmation step.** A mistake has no screen in front of it to be noticed on.

- **Elapsed time is `min(wall-clock delta, playback-position delta)`, capped at 5 min.** Neither signal works alone: wall clock alone bills a sleeping laptop and a stalled buffer; position alone bills a forward seek. Taking the smaller charges only for time that both *passed* and *played*. This is also what makes backgrounded mobile listening correct — iOS suspends timers while audio keeps playing, so one tick can legitimately cover minutes, and **counting ticks instead of measuring them under-pays such a session by up to 60×**.
- **The surplus from a double position step is carried (`StreamLedger.posCarryMs`), bounded at 2 s.** Position arrives as a floored whole second pushed from `timeupdate`; the engine ticks on its own 1 Hz timer. They drift, so a tick sometimes spans two position steps and the next spans none — and because `min()` only ever clips *upward*, the clipped surplus never comes back. It's a permanent one-directional under-payment (0.1–2.5% by `timeupdate` jitter). **The carry is added BEFORE the wall clip, never after**, so a tick still can't bill more time than passed — that ordering is what keeps every rule above intact. Discarded outright on a seek (either direction, and on the way *out* as well as in — zeroing only the incoming carry lets a 10-minute scrub bank a full one), on pause, on a non-finite position, and past the tick cap. The carry only reaches forward, so the *first* empty tick of a session is still lost; that's a one-off, pinned so it can't become per-tick again.
- **Accrual is unrounded msat, and `accruedSats` floors with an epsilon.** Rounding per tick biases every tick the same direction (~1.8 sats/hour). And once the sum is a fraction, a bare `Math.floor` costs a whole sat at every boundary — an hour at 1 sat/min settled 59, forever. Both were caught by `check:stream` before shipping; that's what it's for.
- **The ledger is debited BEFORE the payment is awaited** (`maybeSettle`). Crediting after leaves the same sats for the next tick to spend again — a real double-spend. The cost is that a failed run needs `refund()` and one that dies with the tab is lost. **Losing sats is recoverable; sending them twice is not.**
- **Settles are serialized** through a promise `chain` (same pattern as `toggleFollow`), so a track change landing mid-payment queues rather than races.
- **A batch below `max(10, recipientCount)` sats carries instead of sending — even when forced.** `splitSats` guarantees 1 sat per weighted recipient by pulling from the largest allocation, so a 12-sat batch across 20 recipients starves legs; and dust costs a full routing fee to move nothing.
- **Two consecutive failed settles stop streaming for that item**, surfaced through `<StreamMeter>` and `<StreamPulse>`. A dead wallet must not accrue an unpayable debt in silence. **Both a rate change and a wallet connecting clear the give-up state** (`clearGiveUp`, wired to `subscribeStreamRate` + `subscribeNwc`/`subscribeSpark`/`subscribeWebln`, the wallet arm gated on `pickRail()` so a *disconnect* doesn't re-arm). Rate-only was wrong: the commonest first failure is `no wallet connected`, so the natural fix — go connect one — left the item dead with no visible way back.
- **A rail that provably CANNOT pay this value block gives up after ONE failure, with its own message.** Spark is BOLT11-only, so a value block of nothing but `node` recipients can never be paid from it; retrying is guaranteed to fail identically, and the generic "change the rate to retry" copy just loops the user. `StreamingStatus.stoppedReason` (`'failures' | 'rail-cannot-pay'`) is what lets the meter offer only a remedy that can actually work.
- **Settles inherit biggest-share-first from `sendBoost`** (boost-flow invariant 10, [`../CLAUDE.md`](../CLAUDE.md)), so an unattended settle that dies partway now drops the dust legs rather than the artist. Nothing here needed changing — the ordering lives in the engine, which is the point. `results.find(r => r.error)` still picks the first error *by index* rather than chronologically; it feeds a status string, and a second place that knows about ordering would cost more than it buys.
- **`lastError` and `consecutiveFailures` are scoped to the item.** `lastError` carries a `lastErrorKey` checked against the item now playing, exactly like `stopped` — without it one failure painted its ⚠ on every later episode for the rest of the page session. `consecutiveFailures` resets in `releaseContext`, or one failure on item A plus one on item B gives up on B after a single try.
- **A failed run's sats go back**, to the live ledger when the item is still playing, otherwise straight into `bmb:stream_pending` under that item's own key — a settle can still be in flight when the context is torn down, and crediting only the live ledger dropped those. A refund never lands in a *different* item's accrual; inventing a cross-item debt that surfaces during an unrelated show later is worse than dropping.
- **Failures are logged to `bmb:streamed` once per item, not per attempt**, so "why is nothing being sent?" is answerable without a dead wallet filling a capped-100 log with the same line.
- **`sender_id` honors the same anonymity signal as the boost modal** (`shareNostr` + `shareNostrAs === 'site'`). A user told their pubkey doesn't ride along with their payments must not have it leak out of the background path.
- **No Nostr note, no confetti, no `playBoostSound`.** Streaming is ambient.
- **`bmb:streamed:<npub>`, never `bmb:boosts:*`.** That log is capped at 200 *and* rendered into the global feed as the user's own sends; six settlements an hour would evict real boosts within a day and bury the feed.
- **`bmb:stream_pending`** holds the unsent accrual so closing the tab mid-window doesn't silently discard it. Adopted only when the key matches the item now playing (a remainder for a different item can't be settled — that metadata is gone), and dropped after 24 h. `pagehide` **persists but does not settle**: a payment started there can't be observed, and one sent without its deduction recorded is the double-spend above.
- **Two units: sats per MINUTE, or a fixed amount per TRACK.** `rate × time` makes a track's earnings depend on its length — at 25 sats/min a two-minute song earns 50 and a six-minute one 150 for the same attention. Per-track mode pays both the same. It is a payment *policy*, not a payment *path*: `creditFixed` (pure, in `stream-ledger.ts`, pinned) puts the fixed sum into the ordinary per-bucket ledger through the **same `distribute` and the same allocation** a tick uses, so a `remotePercentage` below 100 splits it between track and host on exactly the rate path's rule, and settlement, the boundary edge and the boostagram are untouched.
  - **"Track" here means *payment target*, not *song*, and every kind earns.** On a Split Kit show the host's own segments (`type: "chapter"` — promos, a PayPal link, a phone number, shared photos) are targets of their own, and they are *supposed* to earn: the listener chose an amount for the show, and a promo is the show. The settings copy has to say so, because "sends N per track" understates the hourly cost, and understating spend is the one direction this area must never fail in.
  - **`STREAM_TRACK_MIN_PLAY_MS` (30 s) is what stops the runaway, and it is a floor on ATTENTION, not a cap.** A real broadcast flicked through two shared photos **16 seconds apart** and fired two full payments. A target must be current for 30 continuous seconds before it earns; past that it earns the same whether it runs three minutes or thirty. The credit therefore fires **mid-run, not on the change**, which is why `ctx.run = { bucket, sinceMs, credited }` exists: with a time-window check instead of a once-per-run flag, a five-minute song would clear the window and be credited twice.
  - **A filter on Split Kit's block `type` was built and removed.** Refusing `chapter`/`podcast` would have cut a show's own segments out of a mode whose amount the listener chose *for the show*. The kind is still carried onto `LiveTarget.blockType` and surfaced in `bmbLive()` for diagnostics — it just doesn't gate payment. Don't reintroduce it without that argument being revisited.
  - **The INCOMING track is credited, not the outgoing one.** Otherwise the last track of every session — the one with no change after it — silently earns nothing. It also means the payment goes out while that block is still current, so `liveEvents` names the block that actually earned it.
  - **`accrue` still runs every tick, with `ratePerMin: 0`.** It is what stamps `lastTickMs`/`lastPositionSec` and clears the carry. Skip it and switching the unit back to per-minute mid-show bills one enormous catch-up tick for every minute spent in track mode. Pinned.
  - **A trackless show in track mode pays NOTHING, and both the settings line and `<StreamMeter>` say so** (`StreamingStatus.trackModeIdle`). An ordinary podcast has no valueTimeSplit windows and no live blocks, so there is nothing for the fixed amount to attach to. Same obligation as the global switch's copy: the rate path proves itself with a rising number, this one can sit at zero forever and silence reads as "working".
  - **`STREAM_TRACK_CREDIT_DEBOUNCE_MS` (60 s) is an anti-flap guard, NOT a listen threshold.** The live target oscillates without the music changing — a dropped socket hands ownership to the RSS poller and the reconnect hands it back — and a flap slower than the minimum-play window would otherwise pay one song twice. It must **outlast** `STREAM_TRACK_MIN_PLAY_MS`, and `check:stream` asserts that relationship rather than just the two numbers: a debounce shorter than the minimum lets a flap restart a run *and* clear the guard.
  - **The double-pay guards live on the LEDGER, not the context — this shipped wrong once.** They started on `StreamContext`, which is rebuilt on every reload, Fast Refresh and item change, while the balance is restored from `bmb:stream_pending`. So a refresh mid-song wiped "already paid" and charged the same track again thirty seconds later; it presented as an accrual that emptied on settle and climbed straight back. `StreamLedger.creditedRun` marks the bucket paid for the run in progress (cleared by `clearCreditedRun` the moment a different target is current, so a genuine replay earns again) and `StreamLedger.creditedAt` timestamps each bucket across runs. **`creditedRun` is exact rather than time-based on purpose**: a reload two minutes into a five-minute song is still the same run, and any window short enough to permit a replay is short enough to let that through. The credit also persists **immediately** instead of waiting for the 10 s mirror — a reload inside that gap is the very case this fixes. `storage.streamPending` normalizes both fields like `posCarryMs` rather than rejecting an older record: losing them errs toward paying twice, so they're read defensively but never treated as a reason to drop a ledger holding real sats.
  - **The whole policy lives in `applyTrackCredit`**, beside `adoptLiveTarget` and `allocationAt`, and is a no-op outside track mode so `tick()` calls it unconditionally. It returns the ledger. Don't inline it back into `tick()` — it was 38 lines of stacked conditions wedged between two unrelated steps of a function that is otherwise a sequence of one-liners.
  - **The unit is a picker on the amount field, not a second toggle.** An amount and its unit read as one setting; a mode switch beside the existing on/off switch reads as two settings that might disagree. `bmb:stream_rate` and `bmb:stream_amount` are separate keys so flipping the unit never destroys the other number — the same discipline that keeps the on/off switch from wiping the rate. `ratePerMin` remains the single ON signal in both units (see `resolveStreamPlan`); a second per-mode on/off is exactly the ambiguity the tri-state rules exist to prevent.
- **Rate resolution: per-show override → global → off.** At show scope, "no opinion" and "explicitly off" are different states — off means "never stream this show" and must outrank a global rate raised later. `storage.streaming.getShow` stays tri-state (`number | null`), but it is now **derived from a separate on/off flag** rather than from a magic zero in the rate field, so the rule is structural. See [`storage.md`](storage.md).
- **The switch and the rate field carry mobile tap sizing that is load-bearing — `min-h-[44px]` on the switch, and a 16px font floor on the input below `sm:`.** The switch graphic is 20px tall, and a 20px target is under half Apple's 44pt minimum: a mouse hits it every time, a thumb does not, so the control read as **completely dead on iPhone while working perfectly on desktop** — reported from the wallet modal and the show page at once, which is the tell that the shared control is at fault rather than either screen. The switch grows its hit area with padding and deliberately **not** a negative margin, since the reclaimed strip would sit over the "Follow my default instead" button below it and steal that button's taps. The input's floor is separate and just as required: iOS Safari zooms the viewport whenever an input under 16px takes focus, and the app sets no `maximumScale` (on purpose — that kills pinch-zoom for everyone), so at `text-xs` every tap on the rate lurched the page and scrolled the switch out of view mid-edit. Both revert to the compact desktop sizing at `sm:`.
- **The control is a switch plus a number, and the number survives the switch.** `<StreamRate>` (`components/streaming-settings.tsx`) serves both scopes: `[●— ON] [10] sats/min`. Turning it on with nothing remembered seeds `DEFAULT_STREAM_RATE_PER_MIN` (10 — pinned by `check:stream`, since it's the one number that spends money without the user ever having seen it). The rate field stays **live while the switch is off** — that's what makes "turning it off didn't lose my number" visible. At show scope a `[Use default]` pill clears **every** show key — on/off, rate, unit and amount — and goes back to following the global settings; an invisible leftover unit is worse than a leftover number, since 100 means something very different per minute than per track. The description line spells out the third state literally ("Never streams this show, even if your default is on"), because that rule is otherwise invisible.
  - **That description is a pure function, `streamRateDescription`**, not an IIFE inside the component. Every branch is a promise about spending and it encodes the subtle storage rules — the tri-state, and a per-show override outranking the global switch — so it's readable without reading JSX and can be exercised directly if the copy keeps growing.
- **The global switch must never claim "nothing is sent".** A per-show `'1'` outranks it, so a user can be streaming a show while the wallet modal's global control reads OFF — caught in testing with the mini-bar showing `≋ 11` beside copy promising nothing was leaving. `storage.streaming.showsExplicitlyOn()` counts the explicit per-show opt-ins and the off-state description degrades to "Off by default — but N show(s) you turned on individually still stream." The tri-state is deliberate and stays; what can't stay is a settings screen that answers "am I spending money?" with a confident no. Any future copy on that switch has the same obligation.
- **Both halves of the tri-state have to be *visible*, not just correct.** The same confusion landed twice in one testing session, from opposite directions: a global switch reading OFF while a show streamed, and a show reading OFF that was actually pinned "never" and immune to the global switch. The model is right — "never stream this" must outrank a default, or raising your rate later silently re-enables shows you turned off on purpose — but nothing distinguished the two offs on screen. A pinned-off show now renders its description in `text-nostr` with an inline **"Follow my default instead"** button (`pinnedOff` in `<StreamRate>`), because `[Use default]` was the only way out and nothing said so. Don't neutralise that styling back to `text-muted`.
- The engine is a module singleton with its own 1 Hz timer, started from `<Player>`'s mount effect. **Deliberately not a store subscription** — that would re-render the player subtree every tick, which is what its per-field selectors exist to prevent. UI reads `subscribeStreaming` instead.
- **The observable notifies only on a real change** (`notifyIfChanged`, signature over the fields the UI renders, countdown bucketed to whole minutes). `<FullscreenPlayer>` is *always mounted* (translated off-screen when collapsed), so an unconditional per-tick notify re-rendered `<StreamMeter>` 60×/min for users who never opened it. The resolved rate is likewise cached and invalidated from `onRateChange`, so the tick isn't reading localStorage twice a second. (Known, pre-existing: nothing in the app listens for cross-tab `storage` events, so another tab's rate change isn't seen live.)
- **`stopStreamingEngine` persists but does NOT settle** — same argument as `pagehide`, and not hypothetical: `<Player>`'s cleanup effect runs on every Fast Refresh, so a settling teardown means *editing a comment in dev fires a real Lightning payment*. The real force-settle edges (pause, item change) live in `tick()`. Module state that survives a restart (`chain`, `pendingSettles`, `disabledKey`, `sessionSentSats`) is deliberate: `chain` is what keeps settles serialized across a remount and `pendingSettles` is what keeps the meter honest about money in flight.
- **Skipped for live streams** (the NIP-57 zap path owns those) and for items with no value recipients.

### valueTimeSplits — paying the artist whose track is playing

A V4V music show redirects payment to a different artist every few minutes via `<podcast:valueTimeSplit>`, while settlement is batched every ten. **A batch routinely spans three tracks**, so the ledger accrues into **per-target buckets** (`StreamLedger.buckets`) rather than one balance — a single balance would have to be paid to whoever happened to be playing when the timer fired, which is wrong for every other artist in the window and wrong the same way every time.

- **`allocationAt(position)`** picks the split covering the current position and returns `[{track, remotePercentage}, {host, remainder}]`. `accrue` is handed the allocation; it does the arithmetic and knows nothing about Podcasting 2.0.
- **Conservation is enforced in `distribute`:** every accrued msat lands in exactly one bucket, and an allocation that doesn't add to 1 sends the shortfall to the host rather than dropping it — dropping would make the meter lie about what the listener is being charged. It's also the spec-correct default: a valueTimeSplit *redirects* part of the show's value, so anything not redirected is still the show's.
- **The host share pools into ONE bucket across every track**, unlike `BoostAllModal`'s per-track host leg. A boost needs per-track correlation because it's a discrete event; a streamed host share is the same recipient all episode, and pooling is the difference between one Lightning payment per batch and a dozen.
- **The settle interval belongs to the BATCH; the floor belongs to the BUCKET.** `settleBatch` evaluates the interval **once**, before its loop, then settles every funded bucket that clears its own floor — a bucket under it carries, across the episode and across replays (bucket keys are `t:<feedGuid>:<itemGuid>`), instead of being rounded away every batch. **Do not go back to looping `settlePlan` in the engine.** That's how it shipped, and it's wrong in a way nothing else catches: `settlePlan` stamps `lastSettleMs` on the ledger it returns, so bucket 2 was checked against a stamp bucket 1 had written microseconds earlier, and failed — as did every bucket after it. A host bucket plus fifteen tracks drained **one bucket per ten minutes**, so in practice nothing settled during the episode and it all bunched into the force-settle at the end. Invisible on an ordinary podcast, which only ever has one bucket. Pinned by the `settleBatch` section of `check:stream`.
- **Track boostagrams mirror `BoostAllModal` exactly**: primary fields = the HOST episode (the playlist the listener chose), `remote_feed_guid`/`remote_item_guid` = the track. Don't "simplify" it by putting the track in the primary fields — the artist would see their own track mangled into the podcast field and the host couldn't correlate the payment.
- **An unresolved split falls back to the host block, never to nothing.** PI doesn't index every album feed (the same ~50% coverage gap that forced the RSS fallback in `resolveValueTimeSplits`), and those sats have already been accrued from the listener. Splits load fire-and-forget via `/api/value-splits`, cached on **`<feedId>:<episodeId>`, not the bare episode id** — RSS-derived episodes get `-fnvHash(guid)` ids and `fnvHash` is 31-bit, so two feeds can collide, and a collision here doesn't render wrong, it *pays another show's artists*. A *fetch failure* is deliberately not cached, so a blip can't pin a whole episode to the host block.
- **A valueTimeSplit boundary is a settle edge, alongside pause / item change / episode end.** `allocationTrackBucket` (pure, in `stream-ledger.ts`, pinned) names the track an allocation credits; the engine forces a settle when it changes. Not cosmetic: batching straight through a boundary means a track straddling the ten-minute mark is paid **twice** — a partial run at the mark and the remainder later — so on a 111-minute playlist of ~4-minute tracks the window costs roughly twice the payments it saves. Settling at the boundary is one payment per track. Safe because `settleBatch` still applies the per-bucket floor and returns the ledger **untouched** when nothing clears it, so a boundary arriving with dust is a genuine no-op that doesn't restamp the interval the host bucket is still waiting on. Evaluated **after** `accrue`, so the straddling tick lands on the incoming track first and the outgoing bucket is complete when it pays. `ctx.lastTrack` starts `undefined` so opening a context can't read as a boundary; a host-only allocation is `null`, so a gap between tracks correctly reads as "the track ended".
- **Boundary rule, pinned in `check:stream`:** a tick is credited to the split covering the position playback has *reached*, so the one tick straddling a track change goes wholly to the incoming track. ≤1 s per change, unbiased (each track loses a tick at its end and gains one at its start). Sub-dividing the straddling tick would be exact and isn't worth the complexity — but it's a choice, so the numbers are pinned to make any change deliberate.

### Live value switching — following the artist during a live show

A live V4V music show plays a different artist every few minutes and the payment target has to follow. **`<podcast:valueTimeSplit>` cannot do this**: it is anchored to `startTime`/`duration` offsets into a finished enclosure, and a live stream has no absolute time base to sync those to (namespace Discussion #567 says so outright). There is no live-VTS tag.

**What the shows actually use is a PUSH channel: `<podcast:liveValue uri="…" protocol="socket.io"/>` inside the `<podcast:liveItem>`.** The show runs **The Split Kit** (`thesplitkit.com`, source at `github.com/thebells1111/thesplitkit`), which holds an ordered list of *blocks* — one per track, each with its own value destinations — and pushes the currently broadcasting block to every listener over socket.io. The host clicks a track; every app's target moves within a second. Split Kit's own UI calls this tag out verbatim: *"Copy the tag below and paste into the `<podcast:liveItem>` of your podcast feed"*, and Sovereign Feeds calls the same URL a "Live Value Link". CurioCaster (`github.com/thebells1111/curiocaster`, public, same author) is the reference consumer.

The RSS-rewriting signals below are the **fallback** for shows that don't run Split Kit. Both paths are implemented; the push channel wins whenever it is delivering, because it is what the host is actively driving where re-reading XML is inference.

**It is not a new payment path — it is a bucket.** `lib/v4v/live-value.ts` resolves "who is playing now" and publishes it; `streaming.ts` pushes that into `ctx.splits` under an ordinary `trackBucket` key and sets `ctx.liveBucket`. So the per-bucket ledger, `allocationTrackBucket`'s **track-boundary settle edge**, `targetFor`'s host fallback and `buildBoostagram`'s track shape all apply unchanged, and **the ledger's arithmetic needed no edit at all** — the only change there was moving `trackBucket` in (see below) so the watcher and the engine share one definition. Reopening the context on a value change instead would `releaseContext(true)` → force-settle the whole ledger → restamp `lastSettleMs`, and on a show switching every three minutes the host bucket's ten-minute interval would never elapse — the `settleBatch` starvation bug in a new costume.

**The push channel (`lib/v4v/live-block.ts`).** `connectLiveValue(uri, onBlock)` opens the socket and maps each `remoteValue` event to a `LiveBlock`. Wire contract, read off Split Kit's own client:

| | |
| --- | --- |
| connect | `io(uri)` — the uri carries its own `?event_id=<eventGuid>`, and socket.io forwards the query on the handshake; that's how the server knows which show |
| event `remoteValue` | the block now broadcasting: `{ title, image, feedGuid, itemGuid, blockGuid, eventGuid, eventAPI, settings.split, value.destinations[] }` |
| event `playerPause` | ignored |
| empty payload | back to the show's default block |

- **`socket.io-client` is dynamically imported**, so ~40 kB stays out of the initial bundle for everyone who never plays a Split Kit show — the same treatment `hls.js` and the Spark SDK get.
- **A destination whose address contains `@` is an lnaddress whatever its stored `type` says.** Split Kit infers the same way in its own sender; trusting the stored type sends a keysend to an email-shaped string.
- **Split Kit's `split` is a percentage its sender divides by 100; ours is a weight over the recipient total.** For destinations summing to 100 those are the same number, and `splitSats` uses the total as denominator either way — so it carries across untouched. Don't "convert" it.
- **Every failure path reports `null`, never an empty target.** A dropped socket is not evidence the set ended, so it hands ownership back to the RSS fallback and the failure counter rather than clearing the artist.
- **`eventGuid`/`blockGuid`/`eventAPI` ride onto the boostagram** so Split Kit's own tooling can tie a payment to the block that earned it. The standard `remote_feed_guid`/`remote_item_guid` still carry the track — these are additive, and `JSON.stringify` drops the undefined keys, so a non-Split-Kit boostagram is byte-identical to before. **They are recorded PER BUCKET at adopt time** (`StreamContext.liveEvents`, written in `adoptLiveTarget`), never read from the watcher's live snapshot at settle time: a track boundary *is* a settle edge, and the boundary is detected **after** `adoptLiveTarget` has moved `liveBucket` to the incoming track — so a snapshot read attaches the incoming block's ids to the outgoing track's payment, or, with a `liveBucket === bucket` guard, attaches none at all to the one settle these ids exist for. The boost modal's `liveBoostFields` reads the snapshot legitimately, because a boost pays *now*.
- **The uri goes through `httpUrl` at parse time.** It arrives from a third-party feed and becomes a socket opened from the browser; same fail-closed allowlist direction as `safeUrlAttr`.

**Three RSS fallback signals, resolved in `lib/pi.ts:resolveLiveSplit`, precedence `remoteItem > valueTimeSplit > value`:**

- **`<podcast:remoteItem>` inside the live item** — the explicit "now playing" pointer. Resolved by handing a synthetic `ValueTimeSplit` to the existing **`resolveOneSplit`**, so it inherits the whole PI-then-RSS chain including the ~50%-coverage `resolveRemoteItemFromRss` rescue. No new resolver.
- **A `<podcast:valueTimeSplit>` inside the live item** — interpreted **only when there is exactly one**, with `startTime`/`duration` ignored. Two or more is a pre-authored timeline with no time base to choose between them, and guessing pays the wrong artist.
- **The live item's own `<podcast:value>`** — the weakest signal, and the only one that **needs two polls**: a static block inside a live item is indistinguishable from a show that simply has one and never touches it. So it is baseline on first observation and a signal only once it has been seen to *change* (`valueIsLive` in `live-value.ts`). Its bucket key is derived from a sorted fingerprint of the payees, so it turns over exactly when they do.

**`LiveTarget.bucketKey` — the invented identity, kept off the wire.** A Split Kit block usually names no feed and a rewritten `<podcast:value>` never does, so both need a fabricated key for the ledger. That key lives on its own field and is passed to **`trackBucket(split, fallbackId)`** (moved to `stream-ledger.ts`, so the watcher and the engine can't drift into two definitions — the watcher is imported *by* the engine and can't reach back into it). It is deliberately **not** parked in `split.remoteItem.feedGuid`, which is where it started: both boostagram builders copy that field straight into `remote_feed_guid`, so a recipient's aggregator was handed `sk:ed6adf33-…` in a field specified as an RSS `<podcast:guid>`. **A guid we invented never leaves the device.** `remoteItem` is therefore absent unless the block names a real feed, and `liveBoostFields` omits the keys rather than emitting `undefined` — it is spread **over** the episode branch, so an `undefined` there would erase the episode's real `remote_item_guid` instead of falling through to it.

**A change is `guid|signal|bucketKey|blockType|title|payees`, not payees alone** (`targetSig`). An artist playing two tracks back to back pushes two blocks with **identical destinations**; keyed on payees only the second reads as "no change", `setTarget` returns early and the previous split stays current — so the meter and the boost modal name the last track, `trackBucket` doesn't move so no settle edge fires, and the eventual payment credits the wrong item guid. Pinned in `check:stream`'s `trackBucket` section.

**Rules, each from something that would otherwise go wrong:**

- **A failed poll keeps paying the last known artist for `MAX_FAILURES` (3 ≈ 1 min), then falls back to the host block.** One blip is not evidence a track ended; believing a target forever pays an artist whose set finished 40 minutes ago.
- **`ctx.splits` is append-only for live.** A bucket carrying under the per-bucket floor must still resolve to *its own* artist when it finally clears; deleting the outgoing entry routes that artist's dust to the host via `targetFor`'s fallback.
- **`LiveTarget.hostValue` exists because the watcher overwrites `episode.value`.** The swap is what makes boosts follow with no plumbing (every `episode.value ?? podcast.value` reader picks it up), but the engine derives the **HOST** bucket's target from that same expression — so without the pre-swap block kept aside, the show's own share would be paid to whichever artist was on when the context opened.
- **The swap goes through `store.syncCurrentValue`, never `play()`.** `play()` force-sets `isPlaying: true` and resets `positionSec` and `videoMode`, so using it here would un-pause a paused listener and drop them out of video on every track change. `syncCurrentValue` replaces `value` and **nothing else** — touching `episode.id` or `enclosureUrl` re-runs `<Player>`'s source effect and kills playback and the hls.js attachment.
- **A `pending` live item never accrues** (`streaming.ts` eligibility). It is scheduled, not broadcasting; metering it bills wall-clock against silence.
- **`stopLiveValueWatcher` closes the socket but KEEPS `watching`.** The two halves pull opposite ways. The socket must close — `<Player>`'s cleanup runs on every Fast Refresh, and leaving it open orphans a connection nothing would reopen, since `watching.guid` still matches. But `watching` must survive, because `baseValue` is the show's own block captured **before the first swap**; rebuilding it from `episode.value` after a restart reads back whichever artist was playing and pays the host's share to them for the rest of the broadcast. `attachSocket` reconnects on the next poll, which is why it runs every poll rather than only on an item change, and `socketOwns` is cleared with the socket so the RSS fallback isn't left muted.
- **A show whose value exists ONLY on the socket never streams.** Eligibility reads `liveTarget.hostValue ?? podcast.value`, so a live item with no `<podcast:value>` on a feed with no channel-level block is skipped even while the socket pushes payable destinations. Deliberate: making it eligible leaves the HOST bucket with nothing payable, `targetFor` falls back to an empty `c.value`, and two failed settles give up on the item anyway. The show has to declare a value block for streaming to engage — Homegrown Hits does.
- **Nostr kind:30311 streams are still excluded from streaming sats.** Their payments are real NIP-57 zaps (boost-flow invariant 0, [`../CLAUDE.md`](../CLAUDE.md)) so the receipt lands in the stream's chat; a streamed settle would go out as an ordinary boostagram, uncorrelated and invisible to the host. Making that a zap means a new payment path inside the file whose whole discipline is "not a new payment path". Deferred deliberately.
- **Known limitation, pinned in `check:stream`: a live source whose `currentTime` never advances bills nothing.** `accrue` charges `min(wall Δ, position Δ)` and there is no live wall-clock mode — deliberately, because wall-alone would bill a sleeping laptop. A live clock in step with the wall bills correctly, a jump to the live edge bills one tick, a re-source to 0 bills nothing for that tick. A stuck `≋ 0` in `<StreamMeter>` is the tell; check `useApp.getState().positionSec` in devtools.

**Pressing play is a poll trigger, and it has to be.** The timer, `focus` and `visibilitychange` are none of them fired by starting playback, so hitting play on a live show left the Split Kit socket unopened for up to a full 20 s interval — during which the RSS fallback answered "the show's own block" and the host was paid while an artist was on. `onCurrentItemChange` is a **vanilla `useApp.subscribe`**, not a hook: it runs outside React and renders nothing, so it doesn't touch `<Player>`'s render path. It fires on every store write including the 1 Hz position tick, so its body must stay a guid comparison and nothing more.

**The poller** (`lib/v4v/live-value.ts`) is a module singleton with its own 20 s timer, 15 s floor, `document.hidden` gate and `visibilitychange`/`focus` triggers — the `nostr-live-streams.tsx` pattern — started from the same `<Player>` mount effect as the engine and **deliberately not a hook**, for the same reason: a store subscription there would re-render the player subtree on every poll. `<LiveNowPlaying>` subscribes to it directly and names the target in the boost modal, because a live boost that silently pays someone other than the artist on screen is the failure this feature exists to prevent.

**The block's own art follows the target, on four surfaces.** Split Kit pushes the cover of the record actually playing and we were already parsing it into `split.image` — for a while nothing rendered it, so the screen showed the show's logo while payment went to an artist whose name appeared only in small type. Art is recognised faster than a title is read, which makes it the cheapest check that the redirect points where the listener thinks. Four surfaces show it. **`useLiveBlockImage(episodeGuid)`** (`live-now-playing.tsx`) feeds two of them — the fullscreen art pane and the mini-bar thumbnail; `<StreamMeter>` renders `status.blockImage` off the engine's status object (16 px), and `<LiveNowPlaying>` reads `split.image` from its own watcher subscription (32 px). That last one matters most, since it sits in the boost modal where money is about to move.

- It **subscribes to the watcher, not the store.** `<FullscreenPlayer>` and `<Player>` are both always mounted, and `setTarget` dedupes on block identity, so Split Kit's ~5 s heartbeat produces one notify per block rather than twelve a minute.
- Returns `null` for anything that isn't a live block with art, so it slots in as the first entry of each existing `??` chain and ordinary playback is untouched.
- **`blockImage` is in the engine's notify signature, not just the render.** Two blocks can share a title while carrying different covers, so the art would otherwise go stale while the text looked right.
- Known gap: the OS lock-screen / media-session artwork still shows the show, not the block.

**`/api/live-value`** mirrors `/api/value-splits`' shape (`rateLimit` → resolve → short `Cache-Control`), at 60/min because it is polled. It passes `maxAgeMs: 10_000` to **`fetchFeedXml(url, opts)`** — a per-caller override that does **not** shorten the shared 60 s window for the normal feed path, and whose successful fetch still populates the shared cache. Don't shorten `RSS_FRESH_MS` or `/api/feed`'s `s-maxage=300` to achieve the same thing; that re-fetches every publisher's RSS on every page load.

**Debugging a live show: `bmbLive()` in devtools** (registered by `startLiveValueWatcher`, same convention as `window.bmbCleanFavorites()`). Every way this feature fails is silent and identical from the outside — the target just never moves — so it reports which one it is: `notWatchingBecause` (nothing playing / `liveStatus` isn't `live` / no guid / no feedId), `liveValueTag` (absent means the feed has no tag, **or** its uri failed the `httpUrl` allowlist), `socket.opened`/`socket.delivering`, `pollFailures`, and the resolved `target` with its recipients. `bmbLive().poll()` forces a poll instead of waiting out the interval. In dev the watcher also `console.debug`s every socket connect, every raw `remoteValue` payload and every target change.

**`npm run probe:live -- <feedUrl>`** (`scripts/probe-live-item.mjs`) is the discovery step for a show whose convention you don't know: it polls a feed and diffs the raw bytes of each signal, reporting which one a given publisher actually moves and the median gap between changes (which answers "does this feed switch faster than the poller?"). It deliberately does **not** interpret value semantics — a parser copy there could drift from `lib/pi.ts` and report something the app doesn't do. **A feed carrying `<podcast:liveValue>` is expected to sit still**; the target is arriving over the socket, and the probe says so rather than reporting "nothing changed".

**Two pre-existing money-path leaks were fixed alongside this**, both in `lib/pi.ts` and both made dangerous by feeds that rewrite a live item:

- **`channelSlice(xml)` now strips `<podcast:liveItem>` blocks.** `/<item\b/` does not match `<podcast:liveItem>`, so a live item published in the channel header — where the spec puts it — landed inside the channel slice, and `parseValueBlock(channelXml)` could adopt **the live item's** value block as the show's in the `?url=` preview path. Once a feed rewrites that block per track, the show-level `⚡ BOOST` pays whoever is on stage.
- **`parseValueBlock` now strips nested `<podcast:valueTimeSplit>` before scanning recipients.** A split is a *child* of `<podcast:value>` and may carry its own inline `<podcast:valueRecipient>` tags, which were being merged into the block's own — so a show would pay a guest's segment splits for the whole episode.

### Three readouts, one observable

All in `components/streaming-settings.tsx`; each subscribes to `subscribeStreaming` itself, so nothing about streaming touches `<Player>`'s render path.

- **`<StreamMeter>`** — the full readout in the fullscreen player's right pane: rate or per-track amount, the block's art, **the track currently being credited**, accrued sats, countdown, failure. Naming the track is the only visible proof the valueTimeSplit redirect is being followed; otherwise streaming looks identical whether the artist is paid or not.
  - **On a live block it must NOT show the interval countdown** (`StreamingStatus.settlesOnBlockChange`). The block change force-settles, which on a music show is minutes sooner than the ten-minute mark, so "next in 10m" answers "when does my money move?" with a number that is almost never the answer. It names the edge instead. Same obligation the global switch carries.
  - **`StreamingStatus.ratePerMin` falls back to the SETTINGS when no context is live, and `0` there means "off for this show" — the meter must say so rather than printing it.** The meter renders on `active || lastError`, and `lastError` outlives the context that produced it by design, so the failure case is *exactly* the case with no context to read a rate from. Taking the rate off `ctx` alone therefore printed **`≋ streaming 0 sats/min`** over the error — a live-rate claim for a show that has none — and printed the identical line for a show still set to 10 that had merely given up, collapsing the one distinction this readout exists to make: *paused, and fixing your wallet resumes it* versus *off, nothing further will be tried*. The remedy copy inherits it: "Change the rate or connect a wallet to retry" asks a user who has already turned streaming off to re-arm unattended spending over a failure they did nothing to cause. **Reported from the field exactly that way** — "I see this payment error but I have streaming sats turned off for this show."
  - **Turning streaming off is a settle edge, so the last thing it does is send a payment** (`tick()` → rate 0 → `releaseContext(true)`), for time already listened. Correct — those sats are owed — but it means a failed settle routinely surfaces *after* the switch is off, and on a music show one force-settled batch can hold several buckets, so `MAX_CONSECUTIVE_FAILURES` (2) is reachable in that single batch and the item ends up flagged "gave up" with streaming already off. Any copy on this surface has to survive that ordering.
  - **"Nothing was sent" is a claim about money and must be DERIVED, never assumed from the presence of an error** (`sentClause`, shared by `<StreamMeter>` and `<StreamPulse>` so one wording can't drift from the other). Two independent things make it false, and neither is visible on screen. First, the bullet above: a force settle flushes several buckets in one chained batch, so bucket 1 can pay and bucket 2 fail — `lastError` then describes only the last one, beside sats that are already gone. `StreamingStatus.lastErrorSentSats` carries what the failing batch had already paid (`batchSentSats`, reset in `chain` order rather than at enqueue time, or a batch queued behind a running one zeroes the count mid-flight). Second, a NIP-47 reply timeout is not a refusal — the engine still counts it as a failure on purpose, the safe direction for an unattended payer, but `StreamingStatus.lastErrorIndeterminate` stops the readout promoting that to fact. This is the same rule the boost modal follows when it renders `?` instead of `✗`: **losing sats is recoverable, telling someone they still have sats they've already spent is not.** Both fields are scoped to the current item exactly like `lastError` and cleared with it in `clearGiveUp`, or a stale partial-send figure captions the next failure.
  - **`accruedSats` sums EVERY bucket, not the current track's.** A sub-floor carry left over from earlier rate-mode listening therefore reads as part of the current track's figure — which is why a 200-sat credit can show as 204. Correct arithmetic, confusing presentation; it has been raised once and is a UX decision, not a bug.
- **`<StreamPulse>`** — a `≋ N` chip on the mini-bar's show line (not the controls cluster — that side is tight on mobile). `shrink-0`, so the already-truncating title just truncates ~40 px earlier and nothing else moves. It exists because the mini-bar is where most listening happens: without it, a user who never opens the fullscreen player has **no signal at all** that money is leaving. The `⚠` failure state is never hidden at any width.
- **`<StreamedLog>`** — the `bmb:streamed:<npub>` history, collapsible, in the wallet modal's `connected` view under `<StreamRate>` (mirrors the account menu's "Muted accounts (N)"). NWC and WebLN wallets have their own transaction lists and Spark's lives in the SDK, but **none of them carry podcast context** — this is the only record that says which show and which track. It re-reads only when `sessionSentSats` changes, not on every notify. `timeAgo` takes unix **seconds** while `StreamedEntry.ts` is **ms**; the mismatch doesn't throw, it silently renders 1970.

### The `≋ STREAM` control — four entry points, one hook

`useStreamPanel(podcast, enabled)` returns `{ button, panel }`; the show header, the episode detail page and the fullscreen player each render both, and the wallet modal renders `<StreamRate>` bare at **global** scope. All of them edit the **same show-scoped keys** and stay in sync through `subscribeStreamRate` — there is no per-episode streaming setting, and adding one would mean a second scope in the resolution rule.

- **Button and panel come back separately** because only the wiring is shared: each surface puts the button in a different flex row and the panel at a different point in the document (below the header, after the value split, above the meter). One element containing both would force a layout on all three that fits none.
- **The hook must be called above every early return** — `<EpisodeList>` returns early for no-feed/loading/not-found, `<FullscreenPlayer>` for `!current`. It takes a nullable podcast and returns nulls, so hoisting it costs nothing. Placing it beside the JSX instead is a `react-hooks/rules-of-hooks` error; lint catches it.
- **It exists because it was triplicated first.** Three copies of the state, the label and the aria wiring, for a control whose job is to start spending money unattended — three places to drift.
- Gated on the same `hasValueRecipients` check as BOOST: a show with no value block can't be streamed, so the button doesn't render.
