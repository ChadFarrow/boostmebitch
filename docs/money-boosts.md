# Boosts — boost-all, celebration, keysend upgrade, our LN address

Read before touching `lib/v4v/boost.ts`, `components/boost-modal/`, `boost-all-modal.tsx`, `lib/v4v/keysend-lookup.ts`, `lib/boost-sound.ts`, or `app/.well-known/keysend/`. The numbered boost-flow invariants stay in the core.

Core rules live in [`../CLAUDE.md`](../CLAUDE.md); this file holds the reasoning.

## Show-level boost

`BoostModal` accepts `episode` as optional. When omitted (`isShowBoost = !episode`): headlines the podcast title, skips the timestamp line, reads value from `podcast.value`, and the boostagram includes `podcast`/`feedID`/`url`/`remote_feed_guid` while skipping `episode`/`itemID`/`episode_guid`/`remote_item_guid` with `ts: 0`. The note body skips the `📻 <episode>` line and the `podcast:item:guid:` `i`-tag.

The `⚡ BOOST` button on the `EpisodeList` header opens this mode (gated on `showHasValue`). The per-episode path in `Player` is unchanged.

**Per-track BOOST on each row.** Every `EpisodeList` row carries a far-right `⚡ BOOST` (`boostTrack` state → `<BoostModal episode={boostTrack}>`) when `hasValueRecipients(e.value)`. `ev.stopPropagation()` keeps it off the row's play/open handler. Not music-only — any feed whose tracks carry a value block gets it.


## Which value block a boost is paid against (`payableValue`)

`episode.value ?? podcast.value` was the expression at every boost surface — the fullscreen player, the episode page, both modals, and `lib/v4v/streaming.ts`. It is correct for an ordinary show and it is a **wrong-payee bug the moment the container is not the item's parent feed**.

A Podcasting 2.0 PLAYLIST is that case. Its rows are `<podcast:remoteItem>` references to items in hundreds of other feeds, so the container's `<podcast:value>` is the CURATOR's. Falling through to it pays the person who made the list for a song they had no part in, and nothing reports it: the modal renders a valid split, every leg settles ✓, and the boost log records a payment that went where it says it went. The streaming payer runs the same expression on a timer with no confirmation step in front of it. Same rule as `<FavEpisodeHeart>`'s `containerIsParent` guard, arriving at the money path instead of at a favorite — see the container bullet in [`../CLAUDE.md`](../CLAUDE.md).

`payableValue(episode, podcast)` (`lib/util.ts`) is the one expression now, and it is in `lib/util.ts` rather than `lib/v4v/` for the reason every other money helper is: that file loads under `node --experimental-strip-types`, so `check:musicl` pins the shipping function rather than a copy, and `<SplitsPreview>` can read an allocation without importing a wallet.

**TWO independent signals refuse and neither alone is enough.** The list MEDIUM is the direct one — a list feed is never the parent of what it lists — and it answers even for a playlist Podcast Index has never indexed. The GUIDS catch a container whose medium did not say so, and are the same discriminator the boost modal already uses to write `remote_feed_guid`.

**Over-refusing costs as much as over-falling-through, so the refusal is narrow in three deliberate places.** A SHOW-level boost (no episode) always pays the feed's own block, playlist or not — the listener chose the container. An episode carrying its own block is returned untouched, which is also what keeps a *hybrid* list feed working: `/api/feed` folds the channel block into `e.value` server-side before this is ever asked. And the guid test needs BOTH guids present, because a feed PI has not indexed carries neither — refusing there would hide BOOST on exactly the independent releases this app exists to pay. A disabled BOOST button reads as a feature that does not exist, not as a bug.

**What arrives as `episode.value` is decided server-side too, and Podcast Index's copy of it can be STALE.** `/api/feed` ships the feed's own block over PI's whenever it read the feed (`feedItemValue`) — see *The feed's value block outranks Podcast Index's copy* in [`feeds.md`](feeds.md) for the measured case and the three branches.

Where a playlist row's real block comes from is the other half, and it is server-side: see *Whose value block pays a playlist row* in [`feeds.md`](feeds.md).

## A `fee` is inside the split, not on top of it — and why 45 renders as 44.6%

Reported as a bug: a boost modal read `ChadF 44.6%`, `ChadF test node 44.6%`, `boostr 9.9%`, `fee Podcastindex.org 1%`. The decimals look like a rounding fault in our arithmetic. They are a fact about the feed.

**`split` is a WEIGHT and a fee recipient's weight is in the denominator with everyone else's.** A publisher who writes 45 / 45 / 10 and adds a `fee="true"` recipient at 1 has authored a total of **101**, not 100 — they read the fee as sitting outside the split. So 45/101 = 44.554% and the artist is paid 100/101 of the share the publisher meant to give them. On a 100-sat boost the legs come out 45 / 44 / 10 / 1: two rows with identical weights are paid a sat apart, because `splitSats`' largest-remainder pass has three leftover sats to hand out and hands them to whoever was floored furthest (the fee at 0.990, then boostr at 0.901, then one of the two tied 44.554s).

**This is the spec.** From the `podcast:value` specification v1.4 (Dave Jones with Gigi, Evan Feenstra & Paul Itoi, September 2021), `docs/examples/value/value.md` in `Podcastindex-org/podcast-namespace`:

> The `fee` attribute tells apps whether this split should be treated as a "fee", or a normal split. If this attribute is true, then this split should be calculated as a fee, meaning its percentage (as calculated from the shares) should be taken off the top of the entire transaction amount.

**Cite v1.4, because the tag reference no longer defines the attribute.** `docs/tags/value-recipient.md` — the page rendered at podcasting2.org, and the one anybody looks it up on — now carries only *"`fee` (optional) If this attribute is not specified, it is assumed to be false."* The defining clause was lost when the per-tag prose was split out of `docs/1.0.md`. So someone who checks the live docs finds `fee` undefined, concludes the denominator is our bug, and "fixes" `splitSats` — which is a money change, against boost invariant 4.

**What the spec does NOT say is whether the fee weight belongs in the denominator.** Its payment formula has no fee carve-out and no worked example uses a fee recipient. "Off the top" fixes the direction of the money; the arithmetic is left open, and what this app does is one defensible reading of it. Two hints point opposite ways: *"as calculated from the shares"* puts the fee inside the share total, while the spec's own production example pairs non-fee shares summing to exactly 100 with a `split="1" fee="true"` narrated as "effectively 1%". 1/101 is 0.99%, which also rounds to "effectively 1%", so the example does not discriminate.

**Grossing the boost up was considered and rejected.** Paying the artists a full 100 and adding the fee as a 101st sat on top means the wallet spends more than the number on the button. It would also have to be threaded through the streaming ledger, which debits *before* it pays — a fee spent outside the ledger is neither refundable nor logged — and through `<BoostAllModal>`'s `N x sats` headline, which knows nothing about any block's recipients. The amount typed is the amount that leaves the wallet.

**What shipped is a sentence, not arithmetic.** `feeNote` (`lib/util.ts`) returns *"Podcastindex.org's fee comes out of your boost, not on top of it."*, or null when the block has no fee recipient — so it is silent on every ordinary feed. It is rendered by both splits surfaces: `<SplitsPreview>` (`components/boost-modal/splits-preview.tsx`, under the list and **outside** the `aria-live` `<ul>`, or it is re-announced every time a leg settles) and `<ValueSplitRows>`. Those two components are deliberately not one — see the note in `value-split-rows.tsx` — so the string is the only thing they share, and it lives in `lib/util.ts` for the same reason `targetWord` does.

**It is derived per SPLITS LIST, never per modal.** A boost inside a `<podcast:valueTimeSplit>` window renders two `<SplitsPreview>` cards with two different recipient sets, and `payableSplit` may have trimmed the host card's list — see the comment at `components/boost-modal/index.tsx:93-97`, which is the same reason the percentages are per-card.

## Boost-all tracks (valueTimeSplits)

Music podcasts tag each track in their RSS with a `<podcast:valueTimeSplit>` — a startTime/duration window plus a `<podcast:remoteItem feedGuid itemGuid>` pointing at the track's own album feed. **PI surfaces these as `e.timesplits[]`** — a flat top-level array on the episode, NOT nested under `e.value.valueTimeSplits` despite the field name. Each entry carries `feedGuid`/`itemGuid`/`medium` directly; `parseRawValueTimeSplits` maps that to the consumer-facing nested `ValueTimeSplit.remoteItem`.

The `⚡ BOOST N TRACKS` button on each episode row (`components/lists.tsx`) opens `<BoostAllModal>` (`components/boost-all-modal.tsx`). Sequential per-track sends, not parallel.

**Resolution pipeline** (`/api/value-splits` → `lib/pi.ts:resolveValueTimeSplits`):

1. **Probe-first-then-batch.** Try the first resolvable split synchronously; if it throws, return the whole batch unresolved rather than hammering a degraded PI. The rest fan out in parallel with per-call try/catch.
2. **PI's `/episodes/byguid` requires `podcastguid`** — lowercase. `feedGuid`/`feedid` are silently rejected with "This call requires either a valid feedid, feedurl or podcastguid argument".
3. **Fallback to RSS chain** (`lib/musicl-resolver.ts:resolveRemoteItemFromRss`) when PI returns "Episode not found". Server-side, two cases: an album feed → find the `<item>` with matching `<guid>`, extract `<podcast:value>` (or channel-level); a publisher feed (`<podcast:medium>publisher`) → walk `<podcast:remoteItem feedUrl>` entries, fetch each album feed in parallel, return the first match. 5-min in-memory cache keyed on feed URL, 5 s `AbortSignal.timeout` per fetch. **Without this fallback ~50% of music-podcast tracks fail to resolve**, because PI doesn't index every album feed.

**Modal-side filtering.** Splits whose remote items didn't resolve to a value block are dropped; the header reads `Tracks (N of M — K unresolved)` when there's a gap. Remaining gaps are host-RSS authoring problems (stale feedGuid, no feedUrl hint, feed not in PI) and are unrecoverable from the client.

**Per-track payment loop (`BoostAllModal.go()`):**

1. **Two legs per track, both through `payableSplit`.** Each track sends `floor(sats × remotePercentage / 100)` to its own recipients (the artists) — a DERIVED share, so the typed amount's 100-sat minimum says nothing about whether it reaches every payee. The remainder fires as a SEPARATE host-share leg to `episode.value` (or `podcast.value`) immediately after, **per-track, not aggregated**. Both legs carry the same `remote_feed_guid`/`remote_item_guid` so the host's Helipad can correlate which track triggered each share. Default `remotePercentage` = 100 (no host leg).
2. **Boostagram shape.** Primary fields (`podcast`, `feedID`, `episode`, `episode_guid`) = HOST episode; `remote_feed_guid`/`remote_item_guid` = the TRACK. Mirrors `BoostModal` so recipient artists see the listener's host context, not mangled track-as-podcast metadata.
3. **Each successful leg logs its own `StoredBoost`** to `bmb:boosts:<npub>`.
4. **StrictMode guard.** `cancelled.current` is **reset to `false` on mount AND set to `true` on unmount**. Without the mount-side reset, dev StrictMode's mount → unmount → mount leaves it stuck at `true` and the loop bails on the first iteration with no Lightning traffic at all.
5. **Confetti on success** when at least one track pays.
6. **Single Nostr summary note.** When `shareNostr` is on and ≥1 track paid, ONE kind:1 via `publishBoostNote` with `contentOverride` listing every successful track title (no truncation). NOT one note per track.
7. **The note is the only artifact that carries the ALBUM total, and it names the per-track figure so the two can be reconciled.** Every wire record carries one track's share — `value_msat_total = trackSats * 1000` — and nothing in a boostagram says it is 1 of N. So the note's `n × sats` and a single boostagram's `sats` differ by the track count, with no way to connect them from either end. Reported as a boost that "only sent 10%" of a ten-track album: nothing was lost, the wallet spent the whole `n × sats`, and the two observers were reading different artifacts. The note line ends `for <total> sats (… each)` for that reason.

   **The `(each)` half names the ARTIST's share, never the typed amount.** A feed taking a host share pays each artist `floor(sats × remotePercentage / 100)`, and THAT is the number their boostagram carries — so `(1000 each)` beside a 900-sat wire record leaves the reader in front of the same 10% gap this line exists to close. It reads `(900 to the artist + 100 to the show, each)` when the show takes a share, and `(900 each)` when it does not, so the two halves account for the whole. It is **omitted** when the paid tracks divide differently from one another — `remotePercentage` is per window, so that is ordinary, and one number cannot describe them. Suppressed at one track too, where it reads as a fault. `value_msat_total` on the note stays the album total — invariant 7, intent not actual.
8. **Every row states how its track's amount DIVIDES, and that is the fix the "it only sent 10%" report actually needed.** Reported against Two For Tunestr, whose feed takes 10% when a track plays (`remotePercentage="90"`): a 1000-sat track boost pays the artist 900 and the show 100, so every tool watching the SHOW's node correctly showed a tenth of what the listener intended. No sats were missing — the other 900 reached the artist, which is the whole point of a valueTimeSplit. What was missing was any way for the listener to learn the division was coming. `<BoostModal>` shows it as two `<SplitsPreview>` cards; this modal showed it nowhere, so the first news of it was a boost bot reading out an unexpected number. Each row now reads `900 → track · 100 → <show>`, gated on the host leg's `payable` rather than on `remotePercentage` — `splitTrackAndHost` returns 0 when the show has no block to pay, and a row promising a share that will not be sent is the same silent omission pointed the other way. The track half names the MEDIUM's word (`targetWord`), not "artist": the line above it may say "4 recipients", so naming one artist put three different recipient counts on one row. The show is NAMED, because the listener reads this to decide whether the division is what they want. **The wire is not the place to fix this**: a host who authored a 10% split should receive 10%, and a boostagram has no field for "this is 1 of 2 legs". Sender-side disclosure only.
9. **`trackLegs` is ONE object carrying BOTH legs, read by the rows AND the loop.** A component-scope memo over `splits × sats × hostValue`, each entry a `redirectLegs` result; `go()` reads `trackLegs[i]` rather than recomputing the allocation it is about to pay. The host half is carried there too — it was recomputed inside the loop with its own `payableSplit` call while the row rendered `host.sats` from the memo, so the payees reached and the figures shown came from two independent computations that nothing kept in step. A row claiming "4 recipients" while the leg pays three is the same silent omission `payableSplit` exists to stop, so a track whose share cannot reach every listed payee says so on its own row — a count and a reason, as `<BoostModal>` does, not a list of names across N tracks. There is no `<SplitsPreview>` here on purpose: N cards is a different screen. `hostValue` had to move out of `go()` for this, since the rows need it at RENDER time.
10. **The amount is PER TRACK and the screen says so before the tracks resolve.** The shared `<AmountInput>` takes one optional `label`, and this modal passes `Amount per track (sats)`. The `n × sats = total` footer line is gated behind `loadState === 'ready' && splits.length > 0 && !done`, so it discloses nothing while the tracks load — which is most of the time somebody is deciding on a number. `<BoostModalBalance>` takes **`total`**, never `sats`: this is the one surface that multiplies the spend by the track count, so a chip reading the typed amount would clear a boost the wallet refuses part-way through, after some artists are already paid.

    **`<AmountInput disabled>` while a send is in flight, in BOTH modals.** The per-leg figures are derived from `sats` at RENDER time while `go()` pays from the closure it captured at the tap, so an edit mid-run repaints every row with numbers that differ from the sats going out — and the ✓ glyphs land beside those repainted rows as each leg settles. `<ModalShell dismissable={!running}>` already takes the same position about the overlay.

Rail picker: see [`wallets.md`](wallets.md) — `components/rail-picker.tsx` is shared with `BoostModal`. Computed inline (no `useMemo`) so the existing `subscribeNwc`/`subscribeSpark` re-render path surfaces newly-connected wallets without remount.

### The single BOOST button inside a split window

`BoostAllModal` pays every track in an episode; this is the other half — the plain BOOST button, pressed while one of those tracks is playing.

It didn't exist for the whole life of the valueTimeSplit feature, and the gap was invisible from the inside: the boost succeeded, the modal showed ✓, the sats arrived — at the *show*. The report that surfaced it was a host who had built an episode specifically to demo value-for-value music (Chad and Reeds Podcast ep. 002, 97% redirected to Matt Finlay's "Copenhagen Time" for the last 281 seconds) and found the boost button ignoring the split he'd authored. Two things were wrong at once: the artist got none of it, and the boostagram carried no `remote_feed_guid`/`remote_item_guid`, so nothing downstream could tell that boost apart from any other.

The asymmetry that hid it: a **live** show redirects correctly, because `live-value.ts` rewrites `episode.value` with the artist's block and the modal reads `episode.value`. A pre-recorded split rewrites nothing, so there was no path from `episode.valueTimeSplits` to the modal at all.

**Shape** (`components/boost-modal/use-active-split.ts` + `index.tsx`):

1. **Window test is synchronous, target resolution is not.** `startTime`/`duration` are already on `episode.valueTimeSplits`, so `splitAtPosition` knows *instantly* that a redirect applies; the artist's recipients need `/api/value-splits` (the same endpoint and the same one-hour CDN cache `BoostAllModal` uses). The button is disabled in between — that gap is the only moment where a tap could pay the show while the screen was about to promise the artist.
2. **`splitAtPosition` re-runs over the RESOLVED list** rather than matching the unresolved window against it by guid. One rule, one place; the alternative is a second definition of "which split is this" that can drift from the first.
3. **Both legs, not a merged block.** `splitTrackAndHost` returns `{trackSats, hostSats}`; `sendBoost` runs once per block, sequentially. Merging would mean rescaling two sets of weights against one denominator and would break `splitSats`' one-sat-per-recipient floor.
4. **The show's share is paid however small it is; `payableSplit` decides who can receive it.** 100 sats at 97% is 97 and 3 — that is what the feed asked for, and the first version got this wrong by folding a too-small remainder back into the track, so a 100-sat boost paid the show nothing.

   The thing that actually needed fixing is one layer down. `splitSats` honestly returns 0 for a payee it can't reach (3 sats cannot be 4 payments), and `payOne` short-circuits `sats <= 0` to `ok: true` **without contacting anyone** — so the leg rendered a ✓ and wrote a `StoredBoost` entry for a payment that never happened. Each behaviour is defensible alone; together they invent money. `payableSplit` drops the unreachable payees from the leg and re-splits over the rest: 3 sats becomes one each to the three largest, not 1/1/1/0. One re-split always settles, since every kept payee holds ≥1 sat and therefore `kept.length <= total`.

   **The same object feeds the preview and the send** — re-deriving the trimmed set at send time would let the rows the user approved differ from the legs that go out. The dropped payees are **named on screen**, not silently absent from a list someone is reading to check where their money went. `BoostAllModal`'s per-track host leg has the identical exposure and uses the same helper.

   Applied to **both** legs, not only this one. The rule here used to exempt a boost's primary leg as "the whole amount, gated by `MIN_BOOST_SATS`" — true only for an *unredirected* boost. Inside a window the primary leg is `floor(sats × remotePercentage / 100)`, and `remotePercentage` is authored by the host's feed, so the exemption held the ✓-for-nothing open on the BIGGER half of every redirect: a 2% window makes a gated 100-sat boost a 2-sat leg over a four-payee artist block, and `splitSats` leaves two of them at 0. The exemption read as safe because the leg it named is the small one in the common case — at 97% the show's 3 sats are obviously fragile and the artist's 97 obviously are not. It is the *rare* percentages that invert that, and a feed picks them.

   The minimum gates the amount a user TYPES; `payableSplit` gates every amount derived from it. Both modals call it on both legs through **`redirectLegs`** (`lib/util.ts`), which is `splitTrackAndHost` composed with `payableLeg`. It lives there rather than in either component for the reason `splitTrackAndHost` does — two copies is how the same feed comes to be paid two different ways depending on which button was pressed, and it happened: one modal gated its track send on `trackSats > 0` and the other did not. `lib/util.ts` also loads under `--experimental-strip-types`, so `check:vts` pins the shipping composition instead of a copy.

   **`payableLeg.payable` is the send gate, and it is NOT `sats > 0`.** `payableSplit`'s `payable.length === 0` arm hands back **every** recipient with an all-zero split — its honest answer for "nobody here can be paid" — and a caller reading that array as "the payees" sends a group of zero-sat legs, each of which `payOne` reports as `ok: true` without contacting anyone. A `<podcast:valueTimeSplit>` with `remotePercentage="0"` is exactly that leg: `<BoostModal>` shipped sending it, so every artist in the block got a ✓ and a `StoredBoost` entry while the show quietly took the whole 100. `<BoostAllModal>` guarded the same case with `if (trackSats > 0)` and the single modal did not, which is the drift the shared helper closes. `payableLeg` EMPTIES `recipients` when the leg is unpayable, so a caller that forgets the gate sends nothing rather than a group of false ✓.

   **Two drop reasons, because only one of them is the user's to fix.** A payee this leg is too small to reach is included by a bigger boost. A payee the feed lists at `split="0"` is reached by NO amount — `splitSats` clamps the weight to 0 and `payableSplit` drops them from every leg, redirected or not — so "boost more to include everyone" is a sentence that cannot come true, and the modal printed it at one. `droppedTooSmall` and `droppedZeroWeight` are separate fields for that reason, and `<DroppedPayees>` (`components/boost-modal/dropped-payees.tsx`) is the ONE component that renders either: three hand-written copies of that sentence had drifted into three wordings for the same fact, across two files.

   **An unredirected boost is not exempt and it is not a no-op.** It drops nobody on a block whose payees all carry weight — `payableSplit` returns the array it was handed there — but a block listing a `split="0"` recipient is trimmed at any amount, which is what makes the two drop reasons visible outside a redirect at all.

   **`<SplitsPreview>` takes the untrimmed list as `listed`.** The percentages it renders are the feed's AUTHORED shares, so their denominator is the authored weight total. Computing it from the trimmed rows made a 5/1/5/1 block trimmed to its two 5s read **50% each where the feed said 41.7%** — directly above the line saying two more payees exist, so the card asserted two payees were entitled to half each while naming four.
5. **Two `<SplitsPreview>` cards, titled.** Track first (it's the larger share and the thing on screen), show second. `<LightningStatus>` counts both.
6. **Confetti and the ping fire ONCE, after both blocks have settled.** They started inside the first `sendBoost`, which meant a redirected boost celebrated when the *track* legs finished — confetti up and the chime played while the show's legs were still going out and the button still read "sending…". Reported as "the audio trigger fired after the track payments, then the other show splits started being paid". A success chime over money that is still moving makes the same wrong claim a ✗ on an unanswered wallet does, pointed the other way. `primeBoostSound` still runs synchronously in the click handler — that part must not move, or iOS blocks the unprimed `play()`.
7. **One `StoredBoost`, one note.** The user pressed boost once. `storedBoostLegs` runs per group and the results are concatenated track-first — a single merged sort would compare a host payee's raw weight against an artist's across different denominators. The note uses the base boostagram's `value_msat_total` (the full amount), so a 100-sat boost reads "Boosted 100 sats" rather than naming one leg — invariant 7. **The note names the TRACK** when its leg settled — a `🎵` line and the track's NIP-73 `i` tags, from the same frozen `redirect` that fed the send (`PublishArgs.track`, [`nostr.md`](nostr.md#nostr-publish-shape)). It is handed `collected`, the track's legs only, never `allLegs`: a note that names an artist on the strength of the host leg names someone who was not paid.
7.5. **(Retired 2026-09-25.)** The live-stream zap gate read the FEED's block, never the trimmed leg, so that trimming could not change which rail a boost took. A live-stream boost no longer zaps, so there is no second rail to choose.

8. **`value_msat_total` on the WIRE is per LEG GROUP, and the groups sum to the boost — only the NOTE and the `StoredBoost` carry the whole amount.** The two readers want opposite things from the same field, and the base boostagram can only be right for one of them. `lib/types.ts` defines it as "same on every leg", which is true *within* a `sendBoost` call and says nothing about the two calls a redirect makes. The show's leg always overrode its own total to `hostSats`; the track leg passed the base object through, so a redirected 100-sat boost at 90% emitted groups advertising **100 + 10 = 110 sats for 100 sats sent**, and anything reading TLV `7629169` saw a total larger than what arrived. `<BoostAllModal>` has always written both groups per-group (`trackSats` + `showLegSats` = `sats`) — it is the reference for what correct looks like here, and the single modal is the one that drifted. The override is conditional on `redirect`, so an ordinary boost's wire bytes are untouched.

Everything above is pinned by `npm run check:vts` except the React wiring; see the CLAUDE.md table for what the boundaries cost when they're wrong.


### Success celebration (confetti + sound)

`fireConfetti()` + `playBoostSound({ appIsPlaying })` (both in `lib/format.tsx`) fire together at every boost-success point: `BoostModal`'s zap path and boostagram path, plus `BoostAllModal.go()`. `playBoostSound()` plays a lazily-created singleton `Audio('/boost.mp3')` — SSR-guarded, resets `currentTime`, swallows play/decode errors so a missing or blocked asset is a silent no-op. No user-facing toggle (add one by mirroring the `shareNostr` boolean in `lib/storage.ts` and gating both). Three rules, each from a real regression:

**1. Prime synchronously in the click handler, before any `await`.** The sound plays seconds *after* the async payment, past the button's transient user-activation, so iOS Safari blocks the unprimed `play()` (worked on desktop, silent on mobile). `primeBoostSound({ appIsPlaying })` unlocks the singleton inside the real gesture. **If you add a new boost entry point, call it in its click handler before the first await.** One-shot per page (`boostAudioPrimed`); both helpers go through `ensureBoostAudio()`.

**2. The prime must pause synchronously, in the same turn as `play()` — don't await.** Pausing in the `.then()` puts a **second live media element** on the page for a frame or more: iOS arbitrates concurrent elements, so a second one starting can duck or interrupt our own podcast; `muted` isn't reliably honored for `<audio>` on iOS; and a fast payment races it, the late `pause()` + `currentTime = 0` chopping the very ping it exists to enable. WebKit grants the unlock when `play()` is *called* inside the activation, not when its promise resolves, so a synchronous pause keeps the element at a standstill and still unlocked. The sync pause rejects the play promise with `AbortError` — expected and swallowed. Worst case elsewhere is a lost ping, which beats interrupting what the user is listening to. **Don't "clean this up" by awaiting `play()`.**

**3. Route through `boostSoundPlan()` (`lib/boost-sound.ts`) — the ping used to permanently kill the user's music app.** An unmuted `play()` on an otherwise-silent page gets `navigator.audioSession.type = 'auto'`, which the UA resolves to **`playback`**, and per the Audio Session spec a playback session "should not mix with other playback audio." So a two-second ping took an **exclusive** session, iOS interrupted Apple Music/Spotify, and resumption is the *other* app's decision — in practice it never came back. The spec describes `transient` as this feature verbatim. Three plans:

- **`appIsPlaying` → `'as-is'`.** We already hold the session. **We must NOT retype it here** — it's **document-scoped, not per-element**, so setting `transient` mid-podcast demotes our own playback (transient sessions are what stop audio on screen lock).
- **Idle + API → `'transient'`.** Ducks instead of seizing, restoring the previous type on `ended` with a 5 s backstop so a stalled decode can't leave it retyped.
- **Idle, no API → `'as-is'` on desktop, `'skip'` on mobile.** The API is **Safari/iOS 16.4+ only**, so skipping unconditionally would silence the ping for most desktop users to fix a problem desktop OSes don't have. Mobile without the API has no good move, so we drop the ping rather than kill the user's music.

Priming routes through the same plan (`'skip'` primes nothing, `'transient'` primes under a borrowed session); both helpers borrow/restore via one `borrowTransientSession(plan)`, and the type must be set **before** `play()`, since the session is created when the element starts playing.

**`appIsPlaying` must be read live at call time** (`useApp.getState().isPlaying`), never captured during render — the ping fires seconds after the tap, and a stale `false` would retype the session out from under a podcast that started in the meantime.

### The share picker and `anonymous` — one definition, because it has broken twice

The picker state both modals run on — whether to post a Nostr note, whose identity signs it, and the `anonymous` flag derived from those two — lives in `useSharePicker` (`components/boost-modal/use-share-picker.ts`). **A new boost surface uses that hook rather than re-deriving the flag.**

It used to be a verbatim copy in each modal: the same two `useState`s seeded from the same two storage keys, the same two write-through handlers, the same expression. That is not a cosmetic duplication, because `anonymous` is a promise made to the user *on screen* that has to hold across four separate wire sites — the boostagram's `sender_id`, its `sender_name`, its `reply_address`, and the note body `formatContent` builds. The app has shipped that promise broken twice, and each time the cause was one surface learning a rule the other didn't:

- **`sender_id`** — the user's pubkey, which recipient aggregators resolve to a profile picture and name. It rode along on an "anonymous" boost while the note itself was correctly site-signed, so the PFP leaked despite the promise.
- **`sender_name`** — leaked the same way afterwards, and then leaked *a second time* through `BoostAllModal`'s hand-built summary `contentOverride`, **after** the single-boost path had already been fixed.
- **`reply_address`** — the newest one, and the reason the count above is worth keeping current. It is a node id resolved from the sender's own lightning address, so it names its owner as surely as a pubkey does. It is dropped on the same line as `sender_id` in the boostagram literal, not inside the hook that resolves it, so a reader sees every identity decision at once.

One definition is the structural fix for that class of bug: there is no longer a second place for the rule to be learned late.

**`senderName` deliberately stays at the call site.** It needs each modal's own "From" input state, so `resolveSenderName(name, anonymous)` is computed per modal. The *flag* is the invariant worth centralizing; the string is formatting. Substituting `DEFAULT_SENDER_NAME` rather than omitting the field matters for its own reason — `JSON.stringify` drops an `undefined` key entirely, leaving presentation to each recipient's aggregator, so the same boost renders blank in one and "Unknown" in the next.

**The `!!identity` gate is load-bearing and survives the extraction unchanged.** Signed out, the picker degrades to a bare checkbox with no anonymous option, every note is site-signed, and the typed "From" name is that note's *only* attribution. But `bmb:share_nostr_as` is a single **global** key, not per-identity — so without the gate a user who chose Anonymous while signed in would sign out and silently have their name replaced by the default, with no control anywhere on screen to turn it back on. `sender_id` is unaffected either way: it is `identity?.pubkey`, already absent when signed out.

### What a leg actually logs

Three console lines, one per rail-shape, because "I don't see any payment metadata being sent" was previously unanswerable from a console — **the LNURL path logged nothing at all**, working or broken, and a `type="node"` recipient logged nothing either.

| Line | Where | Says |
|---|---|---|
| `[keysend] <pubkey>… → keysend N sat (node recipient…)` | `payOne` | a node leg went out with the full TLV boostagram |
| `[boostbox] <addr> — metadata NOT stored…` | `boostbox.ts` | the descriptor was lost, and why |
| `[lnurl] <addr> → comment (desc "…", message N chars, N/255 used)` | `fetchLnInvoice` | exactly what the one metadata channel carried |

**The descriptor is printed in full and the message is only counted.** The descriptor is a public URL already rendered by `<BoostCard>` and is the thing that proves metadata went out; the message is the user's own prose, and a console line is something people paste into a chat.

**`[boostbox]` exists because every failure there returned a bare `null`.** A rate limit, a dead upstream and a malformed response were indistinguishable from a leg that never asked — the payment succeeded, `<BoostCard>` rendered correctly from the sender's own history, and nothing said the recipient had received nothing machine-readable.

**Why the node line matters more than it looks.** A feed can list the same node twice — once as `type="node"` and once behind a lightning address that resolves to it. `lnurl-test-feed` does exactly that: `"My Node" 032870511bfa…` and `chadf@getalby.com`, which upgrades to that same pubkey. Only the address half printed a line, so a missing Helipad row could not be traced to a leg that never went out.

**A keysend leg carries the boostagram inline in TLV `7629169`; an LNURL leg carries none.** On the LNURL rail the metadata is reachable only through the `rss::payment` descriptor in the LUD-21 comment, which is what BoostBox exists to provide. So the two rails present differently to whatever the recipient runs, and a boost that looks absent on the receiving side is a question about **which rail its legs took** before it is a question about anything here. **Do not assert what a particular receiving tool does with either** — that was tried in this file and was wrong twice: a missing Helipad row was diagnosed here as an LNURL leg having no TLV to show, and turned out to be a Helipad-side fault that a reinstall fixed. We can only speak for what leaves this app.

### Reading an LNURL endpoint (`lnurlFetch` + `/api/lnurl`)

**Every LNURL-pay read goes through `lnurlFetch` (`lib/v4v/lnurl-fetch.ts`), never a bare `fetch`.** Four call sites did: the `.well-known/lnurlp` document and the `callback` in `lnaddr.ts` (the boost leg), and the same two in `zap.ts` (the NIP-57 leg). All four were unreachable for the same provider, and each would have had to learn the fix separately.

**It tries the provider DIRECTLY first, and that order is deliberate.** LNURL is browser-facing by design and nearly every provider sends `Access-Control-Allow-Origin: *`, so going straight to them keeps this app's server out of the money path, keeps the user's typed boost message off it, and costs no extra hop inside a payment the user is waiting on. An unconditional proxy would give all three away to fix a minority.

**The minority is real and costs the whole leg.** Reported live: `livewire.io` answers `/.well-known/lnurlp/reflex` with a **302** to a host carrying no CORS header, so the browser blocks the read. That does not degrade to another rail — **LNURL *is* the rail every wallet supports**, so `reflex@livewire.io` could not be paid by NWC, WebLN or Spark, and the only thing on screen was a console CORS warning.

Four rules, each a way to turn a fallback into a new failure:

- **The fallback fires on a THROW, never on a non-2xx.** A 404 or a 400 is the provider *answering*, which is exactly what the proxy is not needed for; re-asking would double the latency of every genuine rejection to learn the same thing. A throw is the browser refusing to let us look — CORS, DNS, connection refused, offline. Those are one indistinguishable `TypeError`, and retrying all of them costs a fast second failure and rescues the one that matters.
- **Retrying is safe HERE and nowhere downstream.** Reading a `.well-known` is idempotent, and asking a callback for an invoice does not move money — it mints a BOLT11 that expires unpaid. Money moves once, later, when the rail pays what this returned. Do not generalise it past that; the keysend retry two sections down is gated far more tightly for exactly this reason.
- **`/api/lnurl` is a POST with the URL in the BODY.** A callback URL carries the user's boost message in `comment` and, on a zap, their signed kind:9734 in `nostr`. As a query parameter all of that lands in this origin's request line, in Vercel's access log, and in a `Referer` — the same reasoning that put the Amber signer result in a fragment. It also means no caching, which is correct: the callback mints a payable invoice.
- **The route returns the upstream STATUS and BODY verbatim and judges neither.** An LNURL service reports failure as a 200 carrying `{status:"ERROR", reason}` at least as often as by a non-2xx, and `zap.ts` shows that `reason` to the user. Flattening either into a 502 replaces the provider's explanation with our guess. A failure of *our own* route (a 429, a refused URL, an SSRF block) is thrown instead of shaped like a response, or the rate limiter's body would be printed to the user as the LN service's reason.

`safeFetch` + `readCappedText` + `https:`-only, because the callback URL is whatever the `.well-known` document said — third-party data. A `safeFetch` refusal names the host it rejected, so it is left to `withErrorHandling`'s generic fallback rather than reflected, or the route becomes an SSRF oracle.

### lnaddress → keysend upgrade

**`type="lnaddress"` recipients upgrade to keysend when the address publishes one.** `lookupKeysendTarget` (`lib/v4v/keysend-lookup.ts`) probes `.well-known/keysend/<name>` **through `app/api/keysend/route.ts`, never directly** — `.well-known/lnurlp` is browser-facing so *nearly* every provider sends CORS headers, but the keysend well-known is a server-to-server convention with none, so a direct browser fetch is blocked and the client's catch turns *every* address into "LNURL-only" silently. (Same reason `/api/chapters` exists; this shipped broken once for exactly this.) **"Nearly" is doing real work in that sentence** — this file used to say "always", and a provider that does not is what the LNURL proxy below exists for.

A valid response makes the leg a real keysend via `payKeysend`, so the boostagram rides inline in TLV `7629169` — `sender_id`, the `remote_feed_guid`/`remote_item_guid` correlation, and the endpoint's sub-account routing all intact — instead of degrading to a LUD-21 `comment` only BoostBox-aware tooling reads.

**Parsing is loose on the envelope, strict on the pubkey.** `pubkey` / `destination` / `nodeId` are all accepted and `tag: "keysend"` is *not* required (self-hosted endpoints are looser than Alby's), but the pubkey must match `/^0[23][0-9a-f]{64}$/`. `customKey`/`customValue` are only ever taken **together from the same object** (spec `customData: [...]` or top-level) and the key must be numeric — pairing a key from one source with a value from another misroutes to the wrong sub-account on a shared node.

**These guards keep it strictly non-regressive** — LNURL works on every rail, keysend doesn't, so an upgrade must never make a leg *less* likely to pay:

- **The probe never throws.** Missing endpoint, timeout, non-2xx, junk JSON, bad pubkey → `null` → LNURL as before. The route answers **404 `no keysend endpoint`** for a non-2xx *and* for a 200 whose body won't parse as JSON — SPA-hosted domains serve their app shell with a 200 for unknown paths (primal.net does), and letting `res.json()` throw dressed an absent endpoint up as a 500.
- **`railCanKeysend(rail)` is a tri-state — `'yes' | 'no' | 'unknown'`, not a boolean.** `'no'` (Spark always, BOLT11-only; NWC with a **non-empty** method list lacking `pay_keysend`; WebLN without `window.webln.keysend`, readable without an `enable()` prompt) skips the probe entirely, so the feature costs those users nothing. `'unknown'` (NWC that never reported a method list, or reported an empty one; **WebLN whenever the method exists**) **attempts the keysend anyway**, safe because of the refusal arm below. It shipped folding `'unknown'` into `'no'`, which is why it **never once fired in production** — plenty of NWC wallets omit `methods` from `get_info`, or grant `get_balance` but not `get_info`.

  **On WebLN the method's ABSENCE is an answer and its PRESENCE is not.** The Alby extension defines `keysend` on the provider object regardless of what the connected account can do, so `'yes'` claimed a capability nothing had checked — and the code comment asserting "there's no unknown here" was wrong about the one extension most users have. Reported live: a boost to `podcastindex@getalby.com` failed on the Alby extension and succeeded on Spark, which never keysends at all (BOLT11-only, so it takes the LNURL path). The correction is free — `'unknown'` and `'yes'` both attempt — and it makes the tri-state mean the same thing on both rails.
- **An empty method list means "don't know," never "can do nothing."** `[]` is truthy, so `nwcGetMethods()` returning it read as settled — and since `setNwcMethods` persisted it and `saveNwcUri`'s `if (!nwcGetMethods())` prefetch guard then skipped re-probing, one empty `get_info` **latched the upgrade off permanently for that URI**. `nwcGetMethods()` now returns `null` for an empty list and `setNwcMethods` refuses to persist one. Two accepted knock-ons: a wallet that keeps reporting empty is re-asked `get_info` **once per boost** (never per leg), and `<NwcWallet>`'s "does not support sending payments" warning (gated on `methods !== null`) correctly stops firing for it.
- **The capability is settled at connect, not at boost.** `nwcValidate` records the method list on the paste path; `saveNwcUri` prefetches it fire-and-forget on the paths that don't validate (backup auto-restore, manual restore, login-time restore), persisted to `bmb:nwc_methods`. Resolved **once per `sendBoost`**, not per leg, and only when the value block contains an lnaddress recipient — `nwcFetchCapabilities` doesn't cache when `get_info` fails, so a per-leg call would re-fire a relay round trip per recipient against an unreachable wallet.
- **The WebLN rail has the same refusal arm, from the two paths `webln.ts` controls.** `WeblnNotAttemptedError` is raised when the provider is absent or refuses `enable()`, and when it exposes no `keysend` — both **before** `wl.keysend` is reached, so no payment can have been attempted. `payOne` retries those over LNURL and records nothing against the recipient. **Anything `wl.keysend()` itself rejects with stays a plain `Error`**: WebLN has no error codes, the extension may already have paid, and a message heuristic is not proof that it didn't. It is fatal to the leg unless `routingFailureProvesUnpaid` matches its reason — the one exception, and the reason that predicate had to be message-based. Without this the plain `Error` from a locked extension or a keysend-less account was filed against the *address* by `failureBlamesDestination`'s default-true arm — blaming the recipient's node for the payer's wallet. The union lives in `payOne` rather than inside `failureBlamesDestination` because `nwc-errors.ts` must stay loadable under plain Node and so cannot import a browser-only module; `check:nwcerror` cannot reach the WebLN half for the same reason.

- **No LNURL retry after a keysend attempt — except on the two arms that prove nothing was sent.** A keysend that errors *after* the payment left the wallet (the Zeus no-preimage case) would double-pay; a failed leg is the cheaper wrong answer. **Arm one** is the class of NIP-47 codes returned *instead of* executing the payment — **`NOT_IMPLEMENTED`**, **`UNAUTHORIZED`**, **`RESTRICTED`** — because nothing moved, so LNURL can't double-pay, and that class is what makes the `'unknown'` arm safe. The three belong together for one reason: each answers a question about **permission or capability**, which a wallet can only answer *before* it tries to pay. The last two are ordinary, not exotic — a NIP-47 connection carries a per-**method** scope list, so a connection granted `pay_invoice` and not `pay_keysend` is a normal Alby per-app setup, and the LNURL retry then pays with the method it does hold. They ride on a **typed** `NwcNotAttemptedError` (`NwcMethodUnsupportedError` is its `NOT_IMPLEMENTED` subclass, so every older `instanceof` site keeps its narrower meaning); flattening either into a plain `Error` makes "can't keysend" indistinguishable from "the route failed and may already have paid," and retrying *that* is a double-pay. Don't collapse **this** arm into a message check: arm two reads a message, and it is a separate function with separate vectors precisely so that this one stays a type test.

  **`INSUFFICIENT_BALANCE`, `QUOTA_EXCEEDED` and `RATE_LIMITED` are deliberately outside the class even though they equally prove nothing moved.** They refuse the *money*, not the *method*, so the LNURL leg would be refused identically — including them would buy nothing and would widen a class whose entire value is that it means one thing.

  **And `PAYMENT_FAILED` is outside it too, however final that code reads.** It is the wallet reporting on a payment it *did* attempt, and the code by itself cannot prove an HTLC never settled. This is the code a genuinely unreachable destination produces, so it is the one that will keep being argued for. `check:nwcerror` pins it as pass-through, and widening `NwcNotAttemptedError` to reach it would hand a retry to every `PAYMENT_FAILED` there is.

  **Arm two is `routingFailureProvesUnpaid` (`nwc-errors.ts`), and it is deliberately NOT that class.** It reads the failure *reason* rather than the code, and fires only for a route search that **finished and found nothing** — `FAILURE_REASON_NO_ROUTE`, or the bare `NO_ROUTE` token. What licenses this where no other wallet-side report qualifies is the payment protocol, not a judgement about wallet honesty: a Lightning payment is **atomic**, so a settled HTLC returns a preimage and *is* a success. A wallet that has finished searching and found no route has therefore already resolved every HTLC as failed. Nothing moved, and LNURL cannot double-pay.

  Without it the leg that failed was never paid by anything: the demotion below only redirects the **next** leg, so whichever recipient the traversal reaches first simply loses their sats on every boost. Reported live — `podcastindex@getalby.com` failed with `400: FAILURE_REASON_NO_ROUTE` on leg 1 and was paid over LNURL on leg 2 of the same boost, because a second recipient happened to share the address.

  Four constraints on it, and each is pinned by `check:nwcerror`:

  - **It reads a MESSAGE, and that is forced, not lazy.** The reported case is the Alby browser extension, which rejects `wl.keysend()` with a plain `Error` — WebLN has no error codes at all. On the NWC rail the same text arrives as the message of a `PAYMENT_FAILED`, so one predicate covers both rails.
  - **The exclusions run FIRST, before any text is read.** `NwcIndeterminateError`, **both** timeout leaves (matched at the shared parent, on purpose) and a suspect socket return false whatever their message says. Each means *we do not know what happened*, and a wallet is free to put anything in the text of one — read the token first and a leg that may already have paid is paid again. This is invariant 11 reaching into a message.
  - **The token list is an allowlist and must stay one**, matched on a **non-alphanumeric boundary** rather than `\b` (which counts `_` as a word character and `-` as a boundary — backwards for these codes) and never with a bare `includes`. `notarealNO_ROUTEthing` must not match.
  - **Deliberately narrow.** `FAILURE_REASON_TIMEOUT`, `INCORRECT_PAYMENT_DETAILS` and the spaced English phrase "no route to destination" are all excluded. `INSUFFICIENT_BALANCE`, `QUOTA_EXCEEDED` and `RATE_LIMITED` stay out for the same reason they are out of arm one: they prove no payment moved, but the LNURL retry would be refused identically.

  **If the LNURL retry then fails, the surfaced error names both attempts** (`keysend: …; LNURL retry: …`), and the wrapper **preserves indeterminacy** — a retry that times out is re-thrown as an `NwcIndeterminateError`, or the flag the outer catch reads is stripped and a payment that may have landed renders ✗.

- **A keysend target that does not pay is remembered, and later legs to that address go to LNURL.** `noteKeysendFailure` / `keysendRecentlyFailed` (`keysend-lookup.ts`, 6 h, memory-only). The case is a recipient whose `.well-known/keysend` is published and correct while the node behind it cannot be paid — unreachable, `accept-keysend` off, or no route from this wallet. **Nothing in the document says so and the probe keeps succeeding**, so without a memory the same leg fails on every boost forever, and a value block's **fee recipients ride on every show and every track**: a boost-all over 20 tracks failed the identical leg 20 times. Podcast Index is the reported instance.

  Three properties, and each is what keeps it out of the double-pay class:

  - **It never rescues the leg that failed.** That leg was attempted and, on this evidence, may have paid. This only changes where the *next* one goes, which is why it can afford to be liberal where the retry cannot. Rescuing the failed leg is arm two's job, behind a far stricter predicate — do not read this as a repo-wide ban on retrying, and do not widen this function toward one.
  - **And it fires only when there WAS no rescue — `shouldDemoteAddress` (`nwc-errors.ts`), "demote only what could not be rescued".** Once arm two pays the leg over LNURL, the demotion repairs nothing and only costs: an LNURL leg carries **no TLV boostagram at all**, so `sender_id`, the podcast and episode titles, and the `remote_feed_guid`/`remote_item_guid` correlation are absent from the wire, and a 255-character LUD-21 comment is the whole metadata channel — for six hours, on every leg to that address. It is also usually the wrong verdict: `FAILURE_REASON_NO_ROUTE` says the **payer** found no path, which is as often the payer's own liquidity as an unreachable recipient, and on the WebLN rail there are no error codes so `failureBlamesDestination` reaches its default-TRUE arm and files an Alby routing problem against a recipient whose keysend works. Reported live: three `@getalby.com` addresses demoted at once, every one of them paying fine, every one silently stripped of its boostagram. **An UNEXPLAINED failure still demotes** — that case has no rescue, so the original reasoning is untouched. `check:nwcerror` pins both arms, and asserts they are mutually exclusive on the rescue path.
  - **Attribution is a separate question from retryability, decided by `failureBlamesDestination` (`nwc-errors.ts`).** It asks *whose fault*, never *did the sats move*. Payer-side failures — an empty wallet, a spent budget, a rate limit, a permission refusal, either timeout class, a dead socket — record nothing, or one dry wallet demotes every address in the block at once. **The two timeout classes are collapsed here on purpose**, which is the exact opposite of the rule `mapNwcError` follows: that rule exists because they answer "did this pay?" differently, and for "was the recipient at fault?" they answer the same — no. Unknown errors default to **blaming the destination**, chosen not left over: being wrong that way costs one address its inline boostagram for a few hours and it still pays, being wrong the other way is the bug. `INTERNAL` and `OTHER` are therefore *not* excused as payer-side — wallets bucket a failed route search into them freely, and excusing them would disable the demotion for exactly the wallets whose error reporting is worst.
  - **The short-circuit sits ahead of the CACHE, not just the fetch** — the same placement rule, and for the same reason, as `LNURL_ONLY_DOMAINS`. By the time a leg fails we are already holding a cached hit for that address, which is the ordinary state and not an edge case: leg 1 probes, caches, pays, fails; every later leg reads that hit. Check the demotion after the cache and each of them keysends again — passing every cold-cache assertion while fixing nothing. `check:keysend`'s warm-cache vector is the one that catches it; a cold-cache one cannot.

  It is **memory-only and lapses on its own**, so a wrong demotion never needs a user to find a setting, and the case it exists for reproduces on the first leg of the next boost anyway. `payOne`'s fallback log gains a **fourth** reason string for it, on the same rule as the third: a log naming the wrong cause is worse than no log.

**One provider list runs the upgrade backwards: `LNURL_ONLY_DOMAINS` in `keysend-lookup.ts`, currently just `fountain.fm`.** The reason is **not** that Fountain lacks keysend. It has keysend, it publishes the well-known, it is the provider the namespace discussion was written around (`customKey` `906608` routes to a Fountain sub-account), and the payment arrives — **it just never shows the recipient what rode in the TLV.** So the upgrade fired on every `@fountain.fm` leg, did precisely what it was designed to do, and the boostagram was discarded at the far end anyway. The upgrade's entire justification — "carry the metadata inline instead of degrading it to a LUD-21 comment" — is void against a recipient that doesn't read the inline copy, and for Fountain the comment is the only channel actually surfaced.

**Nothing observable from our side distinguishes a provider that renders the TLV from one that drops it.** The keysend succeeds identically either way: sats land, `payKeysend` returns a preimage, the modal shows ✓. That is why this went unnoticed for as long as it did, and why membership in this list is *knowledge about the provider*, not something a probe can answer — don't "fix" it by checking whether the domain serves the well-known, because it does.

This is **still non-regressive** under the rule above, just read the other way: LNURL works on every rail and keysend doesn't, so moving a leg *back* to LNURL can only make it more likely to pay. Spark users gain outright — that rail is BOLT11-only, so `payKeysend` threw for these recipients before.

Three details worth not re-deriving:

- **The short-circuit sits ahead of the cache, not just the fetch.** These domains genuinely answer the probe, so a cached hit would be a real keysend target that every reader then has to remember to ignore. Refusing to look is the only version with one place to get it wrong.
- **Matching is exact-or-parent (`fountain.fm` or `*.fountain.fm`), never a bare suffix.** `domain.endsWith('fountain.fm')` also matches `notfountain.fm`, which hands anyone who registers such a hostname the ability to strip the inline boostagram off other people's payments. The domain is lowercased and a trailing root dot stripped first, because the value block is attacker-authored text and `USER@Fountain.FM.` is the same host to DNS. `npm run check:keysend` pins both halves; its must-NOT-match list is deliberately longer than its must-match list.
- **`payOne`'s fallback log has a third reason string** (`LNURL-only provider`), and now a fourth (`a keysend to this address failed earlier`). An @fountain.fm leg matches neither of the first two arms, and a demoted address matches none of the three — these branches exist precisely because every gate falls back silently, and a log naming the wrong cause is worse than no log.
- **The divert keys on the ADDRESS, so a Fountain *node pubkey* still pays by keysend — and that is correct, not a gap to close.** `<podcast:valueRecipient type="node" address="<pubkey>" customKey="906608">` is the standard PC2.0 shape for a Fountain-hosted payee. It has no `@`, so `isLnAddressRecipient` is false and `payOne` goes straight to `payKeysend` without consulting the list. The boostagram is swallowed at the far end exactly as it was before the divert existed. **No code change can recover it**: there is no LNURL endpoint for a bare pubkey, so there is nowhere else to pay. `customKey 906608` identifies the payee as Fountain-hosted but doesn't give us an address. Pay the pubkey; the metadata loss is the provider's, and the user who controls it is whoever authored the value block.

**Two things about Fountain that were measured, so nobody re-derives them.** Both from a live `chadf@fountain.fm` during the audit of this feature:

- **`commentAllowed` is 500**, so the descriptor rides whole with ~425 characters left for the message. The `72` that appears in `check-lnurl-comment.mjs` is the descriptor's own *length*, not a threshold anywhere in code — if BoostBox ever lengthens its URL, the whole-or-nothing boundary moves silently and nothing fails loudly.
- **The invoice amount is exact.** A 10 000 msat request returns a 10 000 msat invoice, decoded by the shipping `bolt11AmountMsat`. That matters because the divert is what first put Fountain legs behind boost invariant 9's strict-equality guard — a provider that rounded or added a fee would make **every** Fountain leg throw before paying, which looks identical to a transport failure.

**The divert did not cause the "every leg ✗, nothing sent" outage** that followed it (issue #176). Worth stating because the timing invites the conclusion: a BoostBox failure is non-fatal by design (`storeBoostMetadata` returns null and the comment falls back to the bare message), and the amount guard passes against a real Fountain invoice, so neither half of the LNURL path can fail a payment. The cause was NWC socket exhaustion — pre-existing, amplified by the balance chip, fixed in #175. Testing the divert is when it was noticed, not what caused it.

**`desc` is the SERVER'S composition and already contains the message — and BoostBox is not at fault for that.** It returns `rss::payment::<action> <url> <message>`, a pre-formatted **BOLT11** description truncated against Lightning's 639-char limit with `...` marking the cut. Deliberate and documented: [`noblepayne/boostbox`](https://github.com/noblepayne/boostbox) `src/boostbox/boostbox.clj:371-391` builds it that way, pins it in its own unit test (`"rss::payment::buy https://example.com hello world"`), and its README Step 3 says to use the field *"as the description when paying"*. `ChadFarrow/boostbox`, the fork deployed at `tardbox.com`, is 33 commits ahead, **0 behind**, and byte-identical in that function. The append predates the fork by three months. **There is nothing to fix upstream, and an earlier version of this file implied otherwise.**

The bug was ours: this app appended a message the server had already included, and recipients read the prose twice. The wire read `…X90JV helipad test — helipad test`; the plain space before the first copy against the ` — ` before the second is what identified which side added which, and the stored record held the message once.

**We take `desc` apart rather than forwarding it for one reason: the service budgets against BOLT11's 639 and cannot see the recipient's `commentAllowed`**, which is routinely 255 and sometimes 32. Forwarded whole, a padded `desc` crosses 255 at roughly a 182-character message, hits the drop-it-entirely rule below and sends no machine-readable metadata at all. `descriptorOnly` recovers the two spec tokens by **shape**, never by `endsWith(message)` — that reads simpler and fails the moment the service truncates its own copy, leaving a clipped duplicate beside a whole one — and unrecognised input rides through unchanged, because a future descriptor format belongs to a newer writer and trimming it wrongly is a dead URL.

**Because that list exists, the LUD-21 comment is now a metadata channel with a known reader, and `buildLnurlComment` (`lib/util.ts`) protects it.** `payLnurl` hands `fetchLnInvoice` the BoostBox `desc` and the typed message as **separate arguments** — it must not pre-join them, and `fetchLnInvoice` is the only place that knows the recipient's `commentAllowed`. The two truncate differently: the `rss::payment::<action> <url>` descriptor is a spec Fountain wrote and parses, so it is worth something only *whole*, while the message is prose that reads fine clipped. The obvious `${desc} — ${message}`.slice(0, budget) puts the fragile half first and cuts from the right, so a tight budget shortens the URL into a dead link **and** still spends the entire allowance on it — the recipient gets no metadata and no message, the payment succeeds, and nothing reports a thing. So: keep the descriptor only if it fits whole, spend the remainder on the message, and if it can't fit, **drop it entirely** rather than send a broken URL. Services allowing 255 or 500 hide this completely; one allowing 32 does not. `npm run check:lnurl` pins it, including a `naive()` vector that reproduces the clipped descriptor.

**A service's `commentAllowed` is an advertisement, not a contract, and a refusal over it must never be the reason a payment does not happen.** Two incidents, one rule. Measured 2026-09-11: `ungovernablemisfits@getalby.com` advertised `commentAllowed: 255` and refused 105 characters with `{"error":true,"message":"length 105 exceeds limit 90"}` — `buildLnurlComment` had budgeted against the 255 it was told, correctly, and the leg threw with the sats still in the wallet. Measured 2026-09-16 on a live Nostr stream zap to `pearlwolf53@breez.tips`: the descriptor *alone* was 91 characters against a service enforcing 90, with no typed message, so `Length 91 exceeds limit 90` came back and the whole zap died. `lnurlCommentRetry` (`lib/util.ts`) answers both, in **three** ways:

- **A shorter comment.** The enforced limit is read out of the refusal by **arithmetic, not phrasing** — the smallest number in the message that is below what we sent and at least 20. Smallest because a message naming two numbers names what you sent and what it allows, and what it allows is the smaller; taking the largest picks the length just refused and earns a second refusal. The floor keeps error codes and ordinals from shrinking the comment to nothing.
- **`{ comment: undefined }` — ask again with no comment at all.** This is the 2026-09-16 case: the descriptor is whole-or-nothing, it does not fit the enforced limit, and there is no prose to spend the budget on, so there is nothing shorter to build. Paying without metadata beats not paying. It is also what a retry that would not be *shorter* than the rejected comment gets, so the loop guard moved here rather than going away — a comment-less ask is a different request and cannot loop.
- **`null` — do not retry.** Every refusal that is not about length. A loose predicate here would cost a wasted round trip on **every leg** of a wallet that is simply down.

**The retry is safe for one narrow reason that does not generalise:** the service refused *before* it minted an invoice, so nothing moved, and asking again mints a BOLT11 that expires unpaid. That is licence to re-ask for an **invoice**, never to re-attempt a **payment**.

**The retry only runs if the refusal is SEEN, and `!res.ok` does not see one.** LUD-06 specifies the error body, not the status, so a service refuses with a 200 carrying `{status:"ERROR", reason}` at least as often as with a 4xx. `sendZap` consolidated that in #382 and `fetchLnInvoice` did not, so on the ordinary boost leg every 200-shaped refusal skipped the comment retry entirely and fell through to *"No invoice returned from LNURL callback"* — naming neither the refusal nor the reason the service gave. `lnurlCallbackRefused(status, body)` (`lib/util.ts`, pinned by `check:lnurl`) is now the one predicate both call sites use, for the gate **and** for the thrown error. A 2xx with no `pr` and something that reads as a reason counts: an invoice is the only successful answer this callback has.

**And the drop is never silent.** On an LNURL leg the comment is the entire metadata channel — there is no TLV boostagram on that rail — so a leg that pays with no comment reaches the recipient looking like an anonymous payment. Both call sites (`fetchLnInvoice`, `sendZap`) log a `console.warn` naming what went, the same sentence `boostbox.ts`'s `noDesc` writes for the same loss arriving from the other side. On the zap path the prose is not among the casualties: the typed message also rides in the kind:9734 `content`, which is the copy every Nostr client renders.

**The other way to lose the descriptor is the rate limit, and it is just as silent.** `/api/lightning/boostbox` is a **per-leg** route — one POST per LNURL leg — and it sat at 30/min/IP, the tier used by `site-sign`, `publisher` and `value-splits`, which fire once per *user action*. `<BoostAllModal>` calls `sendBoost` twice per track (track legs, then host legs), so a 12-track album with two LNURL recipients plus a host leg is ~36 POSTs in a single run: from leg 31 the limiter returns 429, `storeBoostMetadata` doesn't distinguish that from any other non-2xx and returns null, and the later tracks pay fine with no descriptor. Nothing is logged and `<BoostCard>` still shows the BoostBox link, so it looks right in the sender's own history. Now **120**, matching `/api/keysend` — the other per-leg route. It's a ceiling rather than a target: legs are serial, so a minute of boosting can't produce more than ~30–60 of them. Note the limiter is in-memory per lambda, so on Vercel the effective cutoff was always nondeterministic — one instance or two.

Separately, and for the same recipients: **`payOne` dispatches on `isLnAddressRecipient` (`lib/util.ts`), not on `type === 'lnaddress'`.** An address containing an `@` is a Lightning address whatever the wire claims, and both publishing sides mislabel these as `"node"` — The Split Kit stores that type for lnaddress destinations (which is why `live-block.ts:78` re-infers, and why the fixtures in `check-live-block.mjs` carry `type:'node', address:'artist@fountain.fm'`), and hand-written `<podcast:valueRecipient>` tags do it too. The three feed-side parsers — `lib/pi.ts` twice and `lib/musicl-resolver.ts` — take the declared type verbatim, so before this a feed declaring `type="node" address="user@fountain.fm"` fired a keysend at an email-shaped string, which no rail can route: the leg failed outright, every time. `live-block.ts` keeps its own inline copy of the rule rather than importing the helper, because its only import is `import type` and `check-live-block.mjs` relies on that to load it under plain Node — **the two must stay in step.**

The endpoint's routing pair **wins** over the feed's (a feed-side `customKey` on an lnaddress recipient is ignored by the LNURL path anyway, while the endpoint's pair selects the sub-account); the feed's is used only when the endpoint supplies none. An upgraded leg **skips BoostBox** — LNURL-only by design, and the TLV now carries the metadata. `BoostResult.recipient` reports the **original lnaddress recipient**, not the resolved pubkey, so per-leg rows and `bmb:boosts:*` stay readable. Lookups are cached module-scope (6 h hit / 15 min miss) so a boost-all over 20 tracks sharing an artist address probes once. **Zaps stay LNURL:** `lib/v4v/zap.ts` must not take the keysend upgrade — a keysend can't make the recipient's LN service publish a kind:9735 receipt. They do now carry the BoostBox descriptor, though: `sendZap` takes an optional `metadata` and builds its LUD-21 comment through the same `buildLnurlComment` as `payLnurl`, so a live-stream boost to a Fountain host gets the `rss::payment` descriptor instead of the bare typed message it used to. The POST lives in `zap.ts` rather than the modal because `boostbox.ts` is not on the surface components may reach, and because the desc-whole-or-not-at-all rule should exist once. **It goes in the `comment` param, never the kind:9734 `content`** — that content is the zap message Nostr clients render, and a descriptor there shows up as `rss::payment::boost <url>` inside the user's own prose.

### The zap rail: the receipt the note quotes

**A boost payment is NEVER a zap — it is a Podcasting 2.0 payment and carries PC 2.0 metadata** (removed 2026-09-25, pinned by `check:zapreceipt`'s source scan). The boostagram rides in TLV `7629169` on a keysend, the `rss::payment` descriptor in the LUD-21 comment on LNURL, exactly as before any of this section existed. From #402 until then, a signed-in boost shared under the user's own key paid every lightning-address leg whose provider advertised `allowsNostr` as a NIP-57 zap, AHEAD of the keysend upgrade. A zap is a BOLT11 and carries neither kind of metadata, so a recipient's Helipad showed "33 sats from Lightning Invoice" and the message, where the same address (`reed@getalby.com`, which publishes a keysend endpoint) had shown the app, sender, podcast and episode a week earlier from a boost sent signed out. The zap work existed for ONE thing — a receipt the note can quote so Fountain renders a ⚡ figure — and the site-signed summary receipt below does that for every posting boost without touching how a leg pays. `useZapRouting`, the `zap`/`zapRefs` options of `sendBoost`, `payOne`'s zap arm and `lib/nostr/nip05.ts` went with it, and so did the Nostr LIVE-STREAM zap: a live-stream boost used to be one NIP-57 zap to the host whenever the host's `lud16` supported it, and now pays through `sendBoost` like any other (`lnaddrZapSupport` and `collectZapReceipts` went with that). What is left of the zap rail is the summary receipt and zapping a NOTE from a note card, which is not a boost.

**The problem this solves is a rendering one, and it is not fixable in the note.** Our boost note states the amount twice — in the prose `formatContent` writes, and in an `amount` tag — and Fountain renders neither. It reads a **kind:9735 zap receipt that the note quote-references**, which is how Fountain's own boost notes work; this repo already reads that shape in the other direction (`buildNote` in `lib/nostr/discover.ts` resolves a quoted receipt through `zapReceiptAmountMsat`, and `parseQuoteRefs` exists because Fountain writes the reference as a `nostr:nevent1…` URI in the **body**, which a `q`-tag scan misses). So the fix is not a tag we can add: it is a kind:9735 the note can quote. This paragraph used to conclude that the LEG had to change rail, because only the recipient's own LNURL server can publish a receipt for a real zap. The summary receipt below replaced that conclusion, and changing the leg's rail cost the recipient the PC 2.0 metadata (see the top of this section).

**The note quotes ONE receipt: the site-signed SUMMARY for the sats actually paid.** This paragraph used to say the opposite — "we do not mint receipts" — on the strength of NIP-57 Appendix F, which has a validating client check a receipt's signer against the recipient's lnurl provider. Three production boosts and one answer from Fountain changed it. Quoting the per-leg receipts rendered "⚡ 33" under a note that said 100 (note `b88137ca…`, 2026-09-16): Fountain renders the FIRST quoted receipt's amount, not the sum, not the note's `amount` tag, and a client-side split can never hand it a provider receipt for the whole — four recipients are four invoices from four providers, two of them keysends with no receipt at all. Fountain's own boosts carry a receipt for the total because Fountain IS the recipient: its request names Fountain's key, its node issues one invoice for the whole, and Fountain splits server-side. Asked, Fountain's developer said they sign the receipt for the total being sent and that this app should do the same with its own key (2026-09-17). So it does.

**What the summary receipt is.** A kind:9735 signed by the site's key (`/api/nostr/zap-receipt-sign`), in Fountain's exact shape minus the invoice that does not exist: `p` the site, `P` the sender, `description` a kind:9734 for the settled sats, `amount`, and the NIP-73 pairs mirrored from the request as Fountain's server mirrors them. No `bolt11` and no `preimage` — there is no invoice for the whole, and minting one nobody can pay would be a fabricated payment record, which is a different thing from an attestation. NIP-57 itself says a receipt "is not a proof of payment … you are trusting the author"; this one's author is the site, attesting that a boost this app sent settled — the same trust level as the site-signed boost notes it already publishes. A client that validates per Appendix F will refuse it; Fountain renders it. **The amount is the sats that SETTLED, ok legs only, never the typed amount** — the note's `amount` tag stays intent (invariant 7), and when a leg failed the receipt is the one telling the truth. Fountain's reader takes an amount from a receipt with no `bolt11`: the first boost through this path — note `81802c0c…` quoting receipt `470f0fa0…`, 2026-09-17, a 100-sat boost split four ways — rendered "⚡ 100" in Fountain's feed. Measured, not assumed; the earlier per-leg quotes on the same episode rendered "⚡ 33".

**For every boost that posts to Nostr; "Don't post" is the only thing that skips it.** The request half must be signed by its sender, so who signs it is decided by the same rule that picks the note's signer: the user's key when the user's key publishes the note; the SITE when the note is site-published (signed out, or Anonymous) — a user-signed request would put the user's pubkey in `P` and inside `description`, which is exactly what Anonymous refuses. In the site case the client sends a `spec` — amount, relays, refs — and the oracle builds the kind:9734 itself, signs it, and runs it through the same `validateSummaryRequest` a sender-signed one passes. Nothing a caller sends reaches a tag.

**What bounds the oracle.** It is unauthenticated, like site-sign, and it never signs caller-supplied receipt tags: it derives the 9735 from a validated 9734, so a stranger can make the site attest a payment from their OWN key (or an anonymous one from the site's) — the same claims a boost note already lets them make — and nothing else. Not a payment from someone else's key: `verifyEvent` proves the sender signed it. Not a quote of any note: `e` is refused. Not a line of prose: `content` must be empty. Amount whole sats, at most 1,000,000; `p` the site, once; relays `wss://`, at most eight; NIP-73 refs in the podcast namespace only, an `i` needing its `k`, a hint needing `http(s)`. Pinned by `check:zapreceipt` with Fountain's own real request as the must-accept vector and Fountain's key standing in as the site. **`site-sign` grew a `q` rule for the same feature**: a site-published note may carry ONE `q` tag, and only one whose author field is the site's own pubkey — so it can quote its summary receipt and cannot become the `e` tag that oracle refuses.

**No boost waits for a provider receipt any more.** Per-leg zaps used to reach the artist's own zap feed, `P`-tagged to the sender and naming the track, and the live-stream zap's own receipt used to be what that note quoted. Neither was worth the Podcasting 2.0 metadata the payment lost; the summary receipt now stands for every boost, live streams included.

**A live-stream boost's kind:1311 chat line is gated on `maySignAsSelf` = `shareNostr && shareAs === 'self'`.** It is signed by the user's key and carries their prose. It was once gated on being signed in and nothing else, so an Anonymous or "Don't post" live-stream boost published a signed, timestamped attribution on `LIVE_STREAM_RELAYS`. What the gate costs is the chat line for a user who asked to publish less, which is what they asked for.

**Writing that gate as `!anonymous` is a privacy inversion.** "Anonymous" (`shareAs === 'site'`) obviously must not publish under the user's key. **"Don't post" must not either** — it writes `shareNostr = false` and leaves `shareAs` alone, so `!anonymous` is TRUE for a user who has just asked to publish less. This is the same trap `streamingMayPublish()` (`docs/value-playback.md`) exists to name. The same gate once decided whether a boost leg could be a zap, whose request is signed by the user's key and whose receipt republishes that pubkey as the payer; that path is gone.

**The kind:9734 carries the show and item as NIP-73 `k`/`i` pairs, and no `client` tag.** `zapRequestTags` (`lib/nostr/zap-request.ts`, import-free, pinned by `check:zapreceipt` against both real requests byte for byte) writes, after `relays`/`amount`/`lnurl`/`p`: `["k","podcast:item:guid"]`, `["i","podcast:item:guid:<item>", <url hint>]`, `["k","podcast:guid"]`, `["i","podcast:guid:<feed>", <url hint>]` — item first, `k` before its `i`, the hint the show or episode share URL on this site. The recipient's server mirrors them onto the receipt, and that is the ONLY place a receipt says what it paid for: our own `parseZapReceipt` reads `podcastGuid` and `episodeGuids` off the embedded request, so a request without them yields a receipt that parses as no show and no episode, in our explorer and in every aggregator keyed the same way. The `client` rule (CLAUDE.md, Names) is about an app-identity claim on the money path; the first version of this read it as "no tags at all" and stripped every receipt's podcast linkage. Today the summary receipt's request carries them, naming the show (and the item, when there is one). A live stream's `episode.guid` is a Nostr stream id, not an item guid, so it names only the show.

**A zap never takes the keysend upgrade, and a value-block leg never takes the zap.** The first is the rule stated above for `lib/v4v/zap.ts`: a keysend cannot make the recipient's LN service publish a receipt. The second is the top of this section: `payOne` does not reach the zap module at all.

**Two retry arms again, and merging them is a double-pay.** `sendZap` is split into `prepareZap` — everything up to and including the invoice, none of which spends anything — and the wallet call. Every failure `prepareZap` can raise is wrapped as **`ZapNotAttemptedError`**, totally rather than at each `throw`. It was the only class `payOne`'s zap arm could fall back to `payLnurl` on. No boost zaps any more; the rule still holds for the one caller left, the note card's zap, which reports any failure without a fallback — the class is what would license a fallback if one is ever added. A wallet rejection after the invoice was handed over is an ordinary leg failure and is never re-paid. Classifying throw sites one at a time is how the opposite mistake gets made: a single unwrapped `throw` reads as a payment failure and the leg is silently dropped instead of paid. Same discipline as `NwcNotAttemptedError`.

**The wallet-call wrapper must preserve `NwcIndeterminateError`.** `nwcPayInvoice` maps a reply timeout to that class — the request was published and the wallet may have paid — and `payOne`'s outer catch reads it to render `?` rather than ✗. `sendZap` re-wrapped every wallet failure in a plain `Error` for the message prefix, which stripped the class: a zap leg on a wallet that never answered showed ✗, and a ✗ is what talks the user into boosting again and paying twice (invariant 11). It re-wraps as the same class now, exactly as the keysend→LNURL wrapper in `boost.ts` does.

**`sendZap` files no BoostBox record and carries no `rss::payment` descriptor.** A zap is never a boost payment, so there is nothing for a descriptor to describe; the LUD-21 comment is the typed message alone. The boost-only options — `metadata` (the BoostBox POST), `meta` (a prefetched payRequest document), `refs` (NIP-73 pairs) and `aTag` (a live stream's address) — were removed with the last boost caller, together with `ZapNotAttemptedError.stored`, `BoostResult.zapPending` and `BoostResult.zapReceipt`. The summary receipt builds its own kind:9734 through `zapRequestTags` with the refs, which is where `check:zapreceipt` now pins them.

**`sendBoost` takes no `zap` table at all, which is also what keeps streaming out.** `lib/v4v/streaming.ts` settles through the same function, unattended and on a timer; it must never acquire a signer prompt or a relay subscription because a UI surface wanted a quotable receipt.

**No boost waits for a provider's receipt, and nothing reads one.** `collectZapReceipts` (`lib/v4v/boost.ts`) waited once per boost for the zap legs' kind:9735s and was deleted with them in #444. #447 then removed what only that wait used: `awaitZapReceipts` (`lib/nostr/zap-receipt-wait.ts`), the matcher `zapReceiptAccepts` with `requestIdInDescription` and `receiptRelayHints` (`lib/nostr/zap-receipt-match.ts`), their `check:zapreceipt` vectors, and `sendZap`'s `pending`. `QuotedZapReceipt` moved to `lib/nostr/zap-summary-receipt.ts`, the module that makes one. The four-second-wait history: per-leg waits would have spent the ceiling serially, and a waiting note was dropped when the user pressed × on a boost that had already paid.

**What Fountain's wire actually looks like, captured rather than remembered.** Two Fountain boost notes and the receipts they quote, read off public relays on 2026-09-16 and embedded verbatim in `check-zap-receipt.mjs`: notes `4d97826b…22a9` and `57b63ba5…d942`, receipts `aeacff06…477b` and `881b07bc…4567`. The note carries the quote in the BODY only, as `nostr:nevent1…` with `kind: 9735` and the zapper as author and no relay hints; it carries no `q` tag, no `amount` tag, no `client` tag; its NIP-73 `i` tags carry a fountain.fm URL hint as the third element; a mention is `["p", pubkey, "", "mention"]`. Fountain reads a `q` tag when one is present (confirmed by Fountain, 2026-09-16), so writing both halves is right. The receipt is signed by `b866ce76…` on both, its `p` IS that key, `P` names the sender, `content` is empty, `created_at` is three seconds after the request, `bolt11` carries the amount (`lnbc1u1…` = 100 sats), and the request inside `description` has empty `content` — the human message lives only in the kind:1. Nothing in this paragraph is an assertion about what Fountain does with a leg; it is what its bytes are.

**The quote is BOTH forms of ONE receipt — a `q` tag and a body `nostr:nevent…` — because each buys a different half.** Measured across three notes on 2026-09-16: with `q` tags only (`918e7cd0…`) Fountain LISTS the note on its episode, with the episode card, and draws no ⚡ figure; with the body reference too (`b88137ca…`) it draws it. Fountain's own writer emits only the body form, with `kind: 9735` in the nevent. A general client renders each body reference as an embedded zap card, which is why #405 removed it and why the per-leg receipts stay unquoted: the body line is the price of the figure, and there is exactly one of it now. `parseQuoteRefs` reads both forms, so the explorer's wrapper-vs-receipt dedupe holds. What that production note also proved: both routes work end to end — one leg's `p` was the NIP-05 pubkey, the other's the provider's own key — Alby signs and publishes the receipt, and the embedded request carries the NIP-73 pair; Alby does not mirror the pair onto the receipt itself, which is fine because every reader, ours included, takes it off the request.

**The `q` tag's relay hint names a relay that HOLDS the receipt, not the first one the request asked for.** Measured on a production boost with per-leg zaps: the request named seven relays with the user's NIP-65 write relay first, Alby's receipt landed on four of them and not the first, and the hint said `wss://podtards.com` — the note was there, neither receipt was. For the summary receipt the rule is simpler, because this app publishes it: `mintSummaryReceipt` hints with the relays that ACCEPTED it (`acceptedRelays`, three at most) and quotes nothing when none did.

**If a PROVIDER's receipt is ever read again, the matching rules are in git history, not here.** `zapReceiptAccepts` (removed in #447) held them: a busy payee has many receipts, all `p`-tagged to the same person and signed by the same zapper key, so "the kind:9735 that p-tags the payee" matches a stranger's payment a second earlier. The `description` tag (the kind:9734 we signed) and the `bolt11` tag (the invoice we paid) each correlate a receipt to one zap — either is enough, neither may contradict, and a receipt with neither is refused. Its vectors were two real Fountain receipts from two senders under one zapper key; `check-zap-receipt.mjs` still embeds both, for `zapRequestTags` and the oracle.

**Boost All quotes the summary receipt for the ALBUM's settled sats, and that closes the mismatch that made it quote nothing.** Its note states "boosted 20 tracks for 2000 sats"; a per-leg receipt is one leg of one track, so quoting those would have Fountain render ~44 beside 2000. The summary attests the album's settled total — accumulated from the ok legs of every track and every host share, never `sats × tracks` — so the figure Fountain renders is the one the note states. The legs pay by keysend or LNURL like every other value-block leg, the note still carries `results: []`, and there is no per-leg receipt wait — which keeps closed the window where `running` was already false, the overlay dismissable, and a four-second wait followed by a `cancelled.current` return dropped the note for a boost that had already paid when the user pressed ×.

**Before the summary receipt, the amount Fountain rendered was the LEG, not the boost.** On a 44.6/44.6/9.9 split, the largest per-leg receipt said 89 of 200 sats, because a receipt's amount is the invoice that payee's own server issued. The summary receipt (#408) attests the settled TOTAL instead, so the figure is the boost's. Our `amount` tag still keeps `value_msat_total` (invariant 7), and `buildNote` only adopts a quoted receipt's amount when the wrapper carries none, so our own explorer is unchanged.

### The reply address (Helipad's Reply button)

Helipad offers a **Reply** button on a received boost only when the boostagram named somewhere to reply to. Three fields carry it, and this app fills them from the boost modal:

```
reply_address      the sender's node pubkey, or their lightning address
reply_custom_key   ┐ the sub-account routing pair on a shared custodial node
reply_custom_value ┘
```

**`reply_address` takes EITHER a node pubkey or a lightning address, and the receiver tells them apart by the `@`.** That is the Podcast Index maintainer's wording ([podcast-namespace #525](https://github.com/Podcastindex-org/podcast-namespace/discussions/525)) and it is what Helipad's `LnAddress::resolve` implements: no `@` keysends to that pubkey using the pair we supplied; an `@` makes Helipad resolve the address itself, `.well-known/keysend` first and `.well-known/lnurlp` after. **The field is in neither blip-10 nor the satoshis.stream registry** — blip-10 has `sender_key` and nothing else — so #525 and the receiving code are the whole of the specification.

**We prefer the pubkey and fall back to the address, and the order is the point.** The pubkey is the only form an older receiver understands: one predating that resolver hex-decodes whatever it finds in the field, and an `@` string fails outright. The address reaches strictly more people, because an LNURL-only provider publishes no keysend document for us to resolve while the receiver can still pay it over LNURL. So the lookup is an optimisation, not a requirement, and a failed lookup still sends something useful.

**`reply_custom_key` is a NUMBER on the wire, and this is not a style choice.** Helipad reads it with `as_u64()`, which returns nothing for a JSON string. A quoted key therefore leaves the value half present with the key half absent, and Helipad answers that with `400 "No reply_custom_key found in boost"` — the reply does not degrade, it fails. It shipped here quoted once. A zero is read as absent for the same reason.

**The pair goes on the wire together or not at all, and a pair we cannot express falls back to the ADDRESS, never to a bare pubkey.** Helipad enforces the both-or-neither rule itself, with a 400 for either half alone. The subtler half is ours: when an endpoint published routing and we drop it, a keysend reaches the shared node with no sub-account selected, so the sats arrive somewhere nobody asked for. Handing over the address instead lets the receiver resolve the same pair.

As everywhere else in this file, all of that is read off the receiving code rather than assumed — and **it stays a statement about what leaves this app.** Helipad is one reader among several, and the next one may implement less of #525 than it does.

**The address comes from the user's kind:0 `lud16` and there is no `bmb:*` key for it.** It is already published where every other client reads it, so a second copy on this device would be one more thing to go stale. The one place it can be TYPED is `<ProfileEditor>`, which writes the profile rather than a local setting — see the `lud16` note in [`docs/nostr.md`](nostr.md), which had asked to be revisited before that field was added. `lud06` is not a fallback: it is a bech32 LNURL with no `name@domain` to hand over or to build a well-known path from. `useReplyAddress` (`components/boost-modal/use-reply-address.ts`) resolves it.

**It must never gate the send button, and that is the difference from `useActiveSplit`.** That hook's `'loading'` state is a money gate — a boost sent before it resolves pays the wrong person. This one is not: an unresolved lookup costs a boost that carries no reply address, which is what every boost carried before the feature existed. So there is no loading state, nothing is awaited inside `go()`, and a slow provider delays no payment.

**`lookupReplyTarget` is a separate function from `lookupKeysendTarget`, and calling the latter here would be a silent bug.** The paying lookup applies two divert rules first, and both answer *should we pay this address as a recipient* — a different question from *what is this address's node id*:

- `isLnurlOnlyAddress` refuses `@fountain.fm` because Fountain never shows the **recipient** the TLV that arrived. Nothing is being paid when we name a reply node, so a Fountain user would lose their Reply button for a reason that is not about them.
- `keysendRecentlyFailed` is a six-hour demotion learned from a keysend **we** sent while paying that address. It says nothing about whether its owner can be replied to, and it would drop the field with nothing on screen to explain the gap.

Both losses are invisible from this side: the boost sends, every leg shows a ✓, and the only symptom is a missing button on somebody else's Helipad — the same shape as the fountain.fm bug the divert list itself was written for. The two functions share one `cache` on purpose, because that map answers a question about the **document**; `failedTargets` answers a question about the **node**, and only the paying caller reads it.

**Deliberately boost-modal only.** `<BoostAllModal>`'s three boostagram sites and `lib/v4v/streaming.ts`'s `senderFields()` do not carry the reply fields. Streaming is unattended and per-minute, so a Reply button on each of six settlements an hour is noise rather than a feature; boost-all is a queue of legs the sender is not sitting in front of either. Adding them later is a decision, not a bug fix — and it inherits the anonymity rule above.

### The unanswered wallet

**A NIP-47 reply timeout is the one payment outcome that is neither success nor failure, and the UI used to have no way to say so.**

The Alby SDK caps a `pay_invoice` / `pay_keysend` reply at **60 s** (reads — `get_info`, `get_balance`, `get_budget`, `list_transactions` — are capped at 10 s; the cap is not reachable from the public API, since `executeNip47Request` is private). AlbyHub answers only once the payment settles, and settlement can take minutes: pathfinding on a keysend leg, a slow destination on an LNURL one. So the cap fires while the payment is still in flight.

What that looked like in production: every leg of a boost showed **✗**, while Alby pushed a "Sent 10 sats" notification for each one and the recipient's Fountain wallet showed the sats arriving two minutes later. The payments were fine. The report was wrong.

**A false ✗ is worse than a failed payment**, which is why this is an invariant and not a polish item. It reads as "this didn't send", the obvious response is to boost again, and a re-boost repeats **every** leg — including the ones that already paid. The repo's standing trade — losing sats is recoverable, sending them twice is not — points the same way here as it does at the streaming ledger and the keysend retry rule.

So `mapNwcError` maps `Nip47ReplyTimeoutError` to a typed `NwcIndeterminateError`, `payOne` sets `BoostResult.indeterminate` alongside `ok: false` (false is correct — we hold no preimage and must not claim delivery), and every surface that renders a leg renders three states instead of two: `<SplitsPreview>`, `<LightningStatus>` (which counts them and leads with them, since "go look at your wallet" is the actionable part), `<BoostCard>` for the permanent log, and `BoostAllModal`'s per-track rows plus its summary line.

Three things not to get wrong:

- **Match `Nip47ReplyTimeoutError`, not its parent `Nip47TimeoutError`.** `Nip47PublishTimeoutError` shares that parent and means the request never reached the relay — no payment can have happened, so a plain failure is the honest answer. Matching the parent would launder real failures into "maybe".
- **It must never become retryable.** Neither arm of `payOne`'s LNURL retry may reach it: arm one tests `instanceof NwcNotAttemptedError`, which this is not, and arm two (`routingFailureProvesUnpaid`) **excludes it first, ahead of reading any message**. A refusal is the wallet answering *instead of* paying, which is proof nothing moved; a timeout is proof of nothing. The two are exact inverses and the pair is only safe held together — which is why a routing reason found in the text of a timeout is still not a retry.
- **Streaming still treats it as a failure.** `paidAny` is false, so `noteFailure` fires and two consecutive stop the engine for that item. Correct for an unattended payer — and the ledger is debited before the await, so an in-flight payment that later settles was already accounted for.

**Not pinned by a check script.** `lib/v4v/nwc.ts` imports `../storage`, which touches `localStorage`, so it can't be loaded under `node --experimental-strip-types` the way the other `check:*` targets are. The mapping is three `instanceof` arms; if it grows conditions, extracting them into a pure helper in `lib/util.ts` would make it pinnable.

### The failed leg a user reads (`explainPaymentError`)

A ✗ leg's `error` is a library string, and one unreachable wallet relay fails every NWC leg with the SAME one — a real screen printed `Failed to connect to wss://relay.getalby.com` eight times and buried the single different cause (a recipient's LNURL service refusing) between them, while the zap wrapper told the user their wallet had "rejected" an invoice it never received. `<LightningStatus>` now groups the ✗ legs by `explainPaymentError(error)` (`lib/util.ts`): a cause in the user's terms, whose side it is on, and what to do. The raw text stays under "technical details", and `<BoostCard>` keeps it on hover — it is what a bug report needs.

**`nothingSent` is a money claim and it is an ALLOWLIST.** "Nothing was sent" is true only for a throw that precedes any payment request: the wallet relay never connected (the SDK throws in `_checkConnected`, before it publishes), no wallet was ready, the recipient's LNURL service produced no usable invoice, or the app refused an invoice for the wrong amount. `PAYMENT_FAILED`, a timeout and anything unrecognised say nothing about whether sats moved, because "you still have these sats" is the sentence that talks someone into paying twice. Add a new arm to the true side only with the throw site that proves it. A leg retried as `keysend: …; LNURL retry: …` is explained by the RETRY — the keysend was retried only because it provably sent nothing. Pinned, both directions, by `check:lnurl`.

### Serving our own lightning address

The mirror image of the above: `chadf@boostmebitch.com` is a recipient other apps pay, assembled from two pieces on this domain plus an LNbits instance behind `pay.boostmebitch.com` fronting Chad's LND node.

- **LNURL is a `vercel.json` rewrite**, `/.well-known/lnurlp/:user` → the pay subdomain. An edge rewrite, so the hottest path in a payment costs no lambda invocation. **`next dev` does not apply `vercel.json`**, so this is only observable on a deploy — don't conclude it's broken from a local 404.
- **Keysend is a route handler**, `app/.well-known/keysend/[name]/route.ts`, holding the node pubkey in a `NAMES` map. **Deliberately not a file in `public/`**: an extensionless static file is served as `application/octet-stream`, and this has to be JSON, CORS-open and cacheable. It validates on the way *out* against the same `/^0[23][0-9a-f]{64}$/` the reader enforces, so a typo fails closed as one 404 here rather than in someone else's payment path — and an unset pubkey serves 404, because publishing a malformed one is worse than publishing nothing (a payer that trusts it sends a keysend that can never arrive).
- **The two are not independent.** Discovery *starts* at lnurlp — nothing ever looks for the keysend document except a payer already holding the address — and every BOLT11-only wallet (Spark among them) can only pay that way. Drop the rewrite and the keysend doc goes dark with it.
- **`accept-keysend` must stay enabled on the node**, and the node has to stay reachable. A rejected spontaneous payment doesn't degrade gracefully: no sender retries LNURL after attempting a keysend (that rule exists to prevent double-pays), so the leg just fails. This app's own payer now demotes an address after one such failure and sends later legs to LNURL — but that is *our* client's recovery, on *its* next leg. Every other Podcasting 2.0 app is still paying the first shape, and ours still loses the leg that discovers the problem.
- **Known cosmetic mismatch:** LNbits returns `text/identifier` as `chadf@pay.boostmebitch.com`, so a wallet resolving the bare-domain form is handed metadata naming the subdomain. Payment is unaffected — the invoice's `description_hash` is computed over the same metadata string the wallet received — but strict LUD-16 readers may surface the discrepancy. Fixing it means changing the address domain in LNbits, not in this repo.
