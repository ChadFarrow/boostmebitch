# Storage — the `bmb:*` key table

Read before adding or changing any `bmb:*` key. The rules that govern this table (typed helpers only, `safeSet` semantics, cache-never-displaces-a-setting) stay in the core.

Core rules live in [`../CLAUDE.md`](../CLAUDE.md); this file holds the reasoning.

Keys (per-identity ones key on `<npub>` or `:guest`):

| Key | Purpose / quirk |
|---|---|
| `bmb:signer` | `'amber' \| 'bunker' \| 'local'` when a polyfill signer is active; absent for NIP-07 / signed out. `'local'` and `'bunker'` restore **asynchronously**. A failed async restore calls **`abandonRestoredSession()`** — clearing this sentinel alone isn't enough, since identity has already painted from the cached npub and the user would look signed in while `window.nostr` is undefined. It clears `bmb:npub` and resets identity/favorites/mutes, but deliberately does **not** wipe the local key (a transient IndexedDB error must not become permanent key loss). Its hidden half: `doLoadProfile` bails after its `Promise.all` when `storage.npub.get()` no longer matches, or the in-flight `setIdentity(enriched)` resurrects the session ~4 s later. **It must only abandon the session it was actually restoring** — the mount effect captures the npub it started with and re-checks before tearing anything down, since a user can complete a whole sign-in while a restore is still in flight. That failure **only reproduces on an origin with a past** (page load must find `bmb:npub` + `bmb:signer` AND the restore must fail), which is why localhost never caught it. |
| `bmb:bunker` | NIP-46 `{ uri, clientSk }`. Persisting `clientSk` keeps the bunker treating us as the same logical client across reloads (no re-auth). |
| `bmb:nwc_uri` | NWC URI. Global (one key, not per-npub). Restored from the opt-in Nostr backup on login when absent; **cleared on sign-out and npub-switch** so it can't leak across accounts on a shared device. |
| `bmb:rail_pref` | `'nwc' \| 'spark' \| 'webln'` — preferred boost rail, written by `recordLastRail` after a successful boost and by the wallet modal's "Switch wallet" picker; **synced to Nostr** (`d:boostmebitch:settings`). Honored by `pickRail()`, falling back to NWC > Spark > WebLN when absent or unavailable. Setter notifies `subscribeRailPref`. |
| `bmb:nwc_methods` | `{ uri, methods }` — the wallet's NIP-47 method list, captured at connect. Tagged with the URI it was fetched for, so switching wallets invalidates it. Read by `nwcGetMethods()`; decides whether an lnaddress leg may take the keysend path, so persisting it keeps that decision off the payment path. Cleared on disconnect. **Never written with an empty `methods`** — an empty list is no evidence, and persisting it latched the keysend upgrade permanently off for that URI. `nwcGetMethods()` treats a stored empty list as absent, so poisoned records self-heal. |
| `bmb:nwc_backup:*` | Per-npub `'1'` when the user opted in to backing up the NWC connection to Nostr. Set on publish and on auto-restore; cleared (and the event tombstoned) on toggle-off/disconnect. |
| `bmb:wallet_balance:*` | `{ rail, balance, ts }` per npub. Read on mount so the header chip paints instantly while the SDK reconnects; written after every successful fetch; cleared on explicit Spark/NWC disconnect. |
| `bmb:spark:opted_out:*` | **Per-npub** (`:guest` signed out). **Tri-state:** `'1'` opted out, `'0'` explicitly opted in, absent = no opinion. Set when that account disconnects Spark, or when `clearOtherWallets` disconnects a **connected** Spark because another rail was connected — suppresses the silent auto-restore in `loadProfile`. Must **never** be set when Spark wasn't connected: connecting NWC/WebLN on a Spark-less device (a normal signed-out first step) would poison the flag and block the restore on the next sign-in. Cleared by every Spark connect path (`spark-wallet.tsx` create/paste/manual restore **and** `provision-spark.ts`). **The bare pre-per-npub `bmb:spark:opted_out` (no suffix) is a DEAD key — never read it.** Inheriting it was tried and reverted after it cost a real user their wallet: a returning Google account with no scoped entry inherited a stale global `'1'`, and `deriveSparkFromLocalKey` silently refused to bring the wallet up. **The two failure directions aren't symmetric** — wrongly *restoring* a wallet is visible and self-correcting (the user disconnects, writing a proper per-npub `'1'`), while wrongly *withholding* one is invisible and permanent, and this flag guards neither funds nor privacy. The dead key is inert in existing localStorage; leave it. |
| `bmb:stream_rate` | The **remembered** streaming sats-per-minute — a positive number or absent, **never `0`, and never removed by the toggle**. Also the prefix for the per-show number, `bmb:stream_rate:<podcastGuid\|feedId>`. Read through `saneRate`, which rejects anything below 1 or above `STREAM_RATE_MAX_PER_MIN` (10,000): this value is multiplied by elapsed time and paid without a prompt, so a corrupt key must read as *off*, not as an unbounded spend. |
| `bmb:stream_mode` | `'track'` when the amount is per-track; absent or anything else = per-minute (the behaviour that predates the key, so a corrupt value keeps it). Also the prefix for the per-show unit, `bmb:stream_mode:<showKey>`, which overrides the global one on the same precedence as the rate. |
| `bmb:stream_amount` | The remembered **sats-per-track**, bounded by `saneAmount` (1…`STREAM_AMOUNT_MAX_SATS`) exactly as the rate is by `saneRate`. **Deliberately a separate key from `bmb:stream_rate`** — the two numbers mean different things and both must survive flipping the unit, so neither may be overwritten by the other. Per-show prefix as above. `setShowOn(key, null)` clears the mode and amount show keys alongside the rate ones: an invisible leftover unit is worse than a leftover number, since 100 means something very different per minute than per track. |
| `bmb:stream_on` | `'1'` on \| `'0'` off \| absent = no opinion, at both scopes (`bmb:stream_on:<showKey>` for the per-show one). **Globally, absent means OFF** — streaming is opt-in. **At show scope, absent means "follow the global rate" and `'0'` means "never stream this show", outranking a global rate raised later.** Split from the rate on purpose: the control is a switch plus a number, and encoding "off" as a `0` in the rate field destroyed the number the user typed (encoding it as a negative is worse — `saneRate` treats negatives as corruption, so overloading the sign fights the corrupt-reads-as-off rule). `setOn(true)` with nothing remembered seeds `DEFAULT_STREAM_RATE_PER_MIN`, so "on" can never resolve to 0 and make the switch lie; `setShowOn(key, null)` clears **both** show keys, since a lingering invisible per-show number would ambush the user next time they flipped that show on. Every setter notifies `subscribeStreamRate`. **No migration from any earlier shape, deliberately** — a rate with no on-flag reads as off, the safe direction. |
| `bmb:stream_pending` | The unsent `StreamLedger`, mirrored every ~10 s and on every edge, so closing the tab mid-window doesn't silently discard accrued sats. Adopted on the next play of the **same** item only, dropped after 24 h. Reads reject a structurally-incomplete record outright — this value becomes a payment. The exception is `posCarryMs`, which is **normalized to 0 rather than rejected**: it's sub-second billing dust, not a balance, so a record written before the field existed must not throw away the real sats sitting in `buckets`. |
| `bmb:streamed:*` | Per-npub streamed log, capped 100, **rendered by `<StreamedLog>`** in the wallet modal. **Deliberately not `bmb:boosts:*`** — see [`streaming.md`](streaming.md). Holds successful runs *and* the one failure per item that stopped streaming (`ok: false` + `error`), so the log can answer "why is nothing being sent?". `ts` is unix **ms**. |
| `bmb:amber_pending` | The NIP-55 request dispatched to Amber and awaiting a callback: a 128-bit random request id, the method, a timestamp, and the route to return to. **No payload and no key material** — see the pair rule below. Consumed by `/amber-callback` when the answer arrives, and by `invokeAmber` when a caller re-asks. |
| `bmb:amber_result` | The result Amber handed back, parked until the caller re-issues its request. **Only ever a `get_public_key` result**, i.e. a PUBLIC key: `storage.amberResult.set` returns `false` and writes nothing for any type outside `AMBER_PERSISTABLE_TYPES`, and `get` re-checks on the way out so a value left by an older build cannot become readable by widening the set later. Single-use via `take()`. |
| `bmb:theme` | `'light'` when chosen; absent = dark. The FOUC-blocker `<script>` reads this synchronously and sets `data-theme="light"` before first paint. |
| `bmb:relays` | JSON array, manual publish-relay override. |
| `bmb:sender_name:*` | Last "From" name in the boost modal, **per-npub**. It was a single global key, which leaked a real name across identities: someone who had boosted as themselves then signed in with a Google-onboarded account got their old name pre-filled — and the stored value **outranks the profile name** in the modal's fallback chain, so it would have shipped as the boostagram's `sender_name`, tying a generated npub back to the identity it was built not to be linked to. **Deliberately no migration from the old global key** — there's no way to know whose name it was, so adopting it into whichever npub reads first recreates the exact leak. |
| `bmb:share_nostr` | `'0'` = default to NOT publishing a Nostr note for new boosts. |
| `bmb:share_nostr_as` | `'site'` when a signed-in user prefers boost notes signed by the site identity; absent/`'self'` = own key. Consulted only when `bmb:share_nostr` is on and the user is signed in (signed-out shares always use the site key). |
| `bmb:stream_receipts` | `'1'` = publish a kind:3369 value-playback receipt for each streaming settle. **Absent = OFF**, the opposite default to `bmb:share_nostr` above, and the asymmetry is deliberate: that key governs one note per button press, this one governs a continuous public timestamped record of what was played. Folding the two together would borrow one consent for the other. A device SETTING, not a cache — deliberately absent from `EVICTABLE_PREFIXES`. See [`docs/value-playback.md`](value-playback.md). |
| `bmb:npub` | Sentinel for silent re-login on page load. |
| `bmb:favorites:*` | `Record<podcastGuid, FavoritePodcast>` cache — a keyed object, not an array (same shape as `useApp`'s `favorites`). |
| `bmb:favepisodes:*` | `Record<itemGuid, FavoriteEpisode>` — favorited episodes. Separate map from `bmb:favorites` because the two resolve through different PI endpoints; they share one Nostr event. |
| `bmb:favbaseline:*` | `{feeds: string[], items: string[]}` — the NIP-73 identifiers this device last agreed with the kind:10333 favorites list on. **Not a cache, and not evictable.** That event has many writers and no partial update, so without this baseline the merge can't tell "another app added this" from "I removed this" — prefer the relay and unfavoriting stops working, prefer local state and you delete the other app's entries. See [the spec](https://github.com/ChadFarrow/PC20-Nostr/blob/main/pc20-favorites.md). `feeds` records every group this device *emitted*, favorited or opened purely to place an item, because the question it answers is "did I write this group". Losing it isn't fatal (an empty baseline yields no removals, so the next publish is a pure union) but it costs one unfavorite its propagation. Deliberately **not** cleared on an identity switch: it's per-npub, so switching back must find that account's baseline intact. **Starts empty and is deliberately NOT seeded from the two keys below.** Those describe a different event at a different address, so carrying them over claims this device published those ids *to the 10333 list* when it never did — and any entry on 10333 this device didn't write then reads as "mine, and I removed it" and is deleted on the first publish. That shipped for one build and destroyed a real album favorite that existed only on the other app's side. Empty is safe (no removals, so the first publish is a pure union) and correct (a pre-cutover removal already propagated to the *old* list; there are no pending removals against a list never written to). |
| `bmb:sect_collapsed` | `string[]` — which `<FeedSection>` headings the user folded away, as caller-chosen keys namespaced by surface (`npub:sent`, `npub:recv`). A device **setting**, so it is not in `EVICTABLE_PREFIXES`. Stores **collapsed** keys, never expanded ones, for the same reason `bmb:fav_collapsed` does: a section added later must default to *visible* rather than hide behind a heading nobody touched. Unlike that key, the flag is read in an **effect**, not a lazy `useState` initializer — `<FeedSection>` server-renders on `/npub/[npub]`, so reading storage during render would make the first client render disagree with the server HTML and cost React 19 the whole subtree. The one-frame cost lands while the list still reads "searching nostr relays…", so nothing visible flashes. Each section holds its own copy of the flag against one flat shared array, so the toggle is a read-modify-write against storage; writing from local state would erase the sibling section's key. |
| `bmb:fav_collapsed` | `string[]` — which foldable favorites headings the user closed, as caller-chosen keys (`favpage:feeds` / `favpage:items` today). A device **setting**, so it is not in `EVICTABLE_PREFIXES`. Two things about it are load-bearing. It stores **collapsed** keys, never expanded ones: a heading this device has never rendered must default to *visible* — inverting the sense would hide future sections behind a heading nobody touched, and hiding a favorite is the one failure this control must not have. And the keys are **namespaced by surface**, because one flat array serves every caller. Not per-npub: it describes this device's view, not an identity. `useCollapsedGroups`' toggle is a read-modify-write against storage — writing `[...ownSet]` from one caller would erase another's keys. **Call the hook once per SURFACE, never per section.** Collapsing is **independent of `FAV_PAGE`** and does not replace it — folding hides a section the user isn't working in, while `useRevealed` bounds what an OPEN one costs, which folding cannot do. Keys written before the favorites page existed (`show:<medium>` / `ep:<medium>`, when medium was a stack of headings rather than a tab strip) are orphaned and inert — the read is a membership test, so no migration was needed. |
| `bmb:fav_view` | JSON `{tab, sort, split}` — the `/favorites` control row: which medium tab is selected, `recent` vs `az`, and whether the page is showing albums, items or both. A device **setting**, not per-npub and not in `EVICTABLE_PREFIXES`. **One key rather than three**, because the three are read together on every render of that page and written together by one handler; three keys would be three `safeSet` calls that can fail independently on a full store, leaving a control row in a state the user never chose. **Every field falls back on its own** — a value from a newer build must not take the other two down with it, so each is validated separately and a bad one resolves to its default rather than discarding the object. `tab` is deliberately **not** validated against the medium vocabulary here: that vocabulary is open and lives in `groupByMedium`, so the page falls through to `all` when the stored tab names a medium the user no longer has anything under. The filter TEXT is deliberately not persisted — returning to a library silently filtered to three rows is indistinguishable from having lost the rest. Replaced `bmb:fav_panel_open`, which described a home-page panel that no longer exists; stale values under the old key are inert. |
| `bmb:muted:*` | `MuteListState` JSON; `lib/storage.ts` auto-promotes the legacy shape. **`set` returns whether the value reached disk and `persistMuted` must not drop that answer** — a mute held only in `safeSet`'s memory mirror filters for the session and is gone on the next load, which presents as "I muted them and they came back", not as a storage fault. Nothing else on screen looks wrong, so it is warned about at the write. A signed-in user still publishes, and the relay copy is then the only durable record. |
| `bmb:follows:*` | Per-npub last-known-good kind:3 follow set (`hex[]`). Written **only from a real kind:3**; a nuke-guard signal read by `toggleFollow`, never used for rendering. |
| `bmb:wrelays:*` | Per-npub NIP-65 (kind:10002) **write** relays, from the last load that resolved them. A routing hint, **not a cache and not evictable**. It exists because the read and the write of every shared list must target the same relay set: `loadProfile` fetches kind:10002 in parallel with the favorites and mute-list hydrations, so on a cold load those two ran against `DEFAULT_RELAYS` alone while their republish moments later went to `resolvePublishRelays` — the user's write set unioned with the defaults. A read narrower than its write is how a shared replaceable event gets merged against a version that never saw half the relays, and on a device with no local cache it renders as the list simply not being there. `resolvePublishRelays` reads this whenever `identity.writeRelays` is absent; the live NIP-65 answer always wins over it, so narrowing your write set takes effect immediately. **Never written from an empty result** — `fetchRelayList` returns the same `null` for "no kind:10002" and "nothing answered", and adopting the second would drop a good hint on one bad query. Losing it costs one cold load reading the narrow set again, which is why it is small enough to keep and important enough not to evict. |
| `bmb:profile4:<pubkey>` | kind:0 cache. **7-day TTL on hits, 15-min on misses** (so relay additions / temp outages re-resolve). The numeric suffix is a schema version — bumped on each `PROFILE_RELAYS` expansion, and again to flush miss entries poisoned by a relay-stall bug. Bump it whenever the shape changes or a cached miss becomes untrustworthy. |
| `bmb:pmeta:<key>` | `/api/by-guid` cache, 7-day TTL. `<key>` is a guid or `url:<feedUrl>`. |
| `bmb:epmeta:<key>` | `/api/episode-by-guid` cache, 7-day TTL. `<key>` is `<feedGuid>:<itemGuid>`. Same eviction class as `bmb:pmeta`. |
| `bmb:feed:<key>` | `DiscoveredNote[]` per feed. **No TTL** — every mount paints it, then a full relay fetch replaces it. Legacy `{ t, v }` wrapper tolerated on read. Keys: `'global'`, `'podcast:<guid>'`, and **two per npub the boost explorer has opened** (`npub:<hex>:sent`, `npub:<hex>:recv`). Those last are the one key shape here whose COUNT is driven by browsing rather than by the app's own structure — a shared `/npub/<npub>` link passed around adds a pair per visit, each holding up to 100 notes with their raw events and replies. That is bounded by eviction, not by design: `bmb:feed` is second in `EVICTABLE_PREFIXES`, so a full store drops the whole namespace including `'global'`, which costs a refetch and nothing else. Watch it if the page becomes popular; a per-entry cap would be the fix, not a smaller blob. |
| `bmb:social:<uri>` | `DiscoveredNote[]` per `socialInteract` URI. Same no-TTL paint as `bmb:feed` (reuses its normalizer + legacy tolerance). Written on every successful thread fetch and after an optimistic comment; never on fetch error. |
| `bmb:boosts:*` | Local sent-boost log, capped 200 newest-first. Each entry holds intent + per-leg results + the Nostr `noteId` patched in once `publishBoostNote` resolves. `boostsTick` wakes subscribers; `GlobalNostrFeed` mixes these in and dedupes against returned notes by `noteId`. |
| `bmb:pi:dead` (sessionStorage) | Circuit-breaker sentinel; cleared on hard-refresh-into-new-tab. Reached through `storage.piBreaker`. |
| `bmb:nwc_uri_sess:<npub>` (sessionStorage) | NWC URI stashed at sign-out so a same-tab sign-back-in restores instantly without a relay query + decrypt (which hangs when iOS kills the extension's service worker mid-wait). Consumed and removed by the fast path atop `doLoadProfile`; cleared on explicit NWC disconnect so a disconnected wallet can't resurrect. Reached through `storage.nwcSessionUri`. |

**The two `bmb:amber_*` keys are localStorage because the callback lands in a DIFFERENT TAB, and that fact costs them the right to hold a secret.**

They were sessionStorage first, on the reasoning that an in-flight signer request should die with the tab. Measured on a Pixel 6 against a real https origin: Brave opens Amber's `ACTION_VIEW` in a **new tab** — count went 15 to 16 — and sessionStorage is per-tab, so the pending record written by the dispatching tab was simply not there. `/amber-callback` reported "this browser tab was not waiting for anything" and offered a manual paste, which is the right failure and still a failure: the automatic path never ran.

localStorage fixes that and puts the record on disk, so the tab lifetime — the thing that made parking a result acceptable — is gone. The rule replacing it is enforced in `lib/storage.ts` rather than remembered: **neither key may ever hold a secret.** `AMBER_PERSISTABLE_TYPES` is the gate, and it is deliberately NOT the same list as `RESUMABLE_TYPES` in `lib/nostr/amber.ts`. They answer different questions — *is this result safe on disk* and *can this request afford a page reload* — and a type must satisfy both to round-trip. Collapsing them into one list is exactly how the decrypt case would quietly acquire permission to write the user's plaintext into a browser profile. Reasoning for the round trip itself is in [`signers.md`](signers.md).

**The two sessionStorage keys go through `lib/storage.ts` like everything else, but NOT through `safeGet`/`safeSet`.** Those two read and write `localStorage`, and their in-memory mirror would outlive the tab — which is the only reason a spending credential is allowed in `bmb:nwc_uri_sess:<npub>` at all. `storage.nwcSessionUri` and `storage.piBreaker` therefore touch `sessionStorage` directly, with the same try/catch posture. The key template was previously hand-written in four places across two files; `CLAUDE.md`'s "every `bmb:*` through a typed helper" rule was written for `localStorage` and these slipped the gap. The disconnect path is what stops a disconnected wallet resurrecting, and it was one character from no longer matching the writer.

**Not in `localStorage`:** the local-signer nsec, which lives in **IndexedDB** (`bmb-keys` / `keys`) as `{ iv, ct }` plus a non-extractable AES-GCM `CryptoKey`. Don't add a `bmb:*` accessor for it.

**External:** the Spark mnemonic lives encrypted on Nostr as kind:30078. The `SparkWallet` keeps its own state (leaves, transfer history) keyed off the seed + `accountNumber`; we don't manage a storage dir for it.
