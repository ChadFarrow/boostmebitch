# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**How to read this file.** Each entry is a rule plus one clause naming the consequence of breaking it. The consequence is there so you can judge a trade-off, not as history — where a rule says "this shipped broken once," treat that as evidence the obvious version is wrong, not as an invitation to re-litigate. **The reasoning behind each rule lives in `docs/`, indexed below, and the `→` pointer at the end of an entry is where to find it.** Follow the pointer before you edit in that area; the rule alone is the reminder, not the argument. The README at the repo root is the architecture spec; treat overlap with this file as the README's job.

**What lives here vs `docs/`.** This file holds only what must be in mind *before* you know which file you're opening: money-path and security invariants, boundaries, repo-wide conventions, and the stop-ship checks. Everything else — the deep "why the obvious version is wrong" reasoning for each subsystem — lives in `docs/`. **When you learn a new rule, it goes in the relevant `docs/` file unless it (a) can lose funds or leak a credential, (b) governs where code may go, or (c) applies to edits in files you haven't opened yet.** Only those three go here, and even then as a rule plus a pointer, never as a narrative. Without that test this file grows back — it reached 26,000 words once, which is why `npm run check:claudemd` now measures it.

## Report in ASD-STE100 Simplified Technical English

Write every chat reply to the user in **ASD-STE100 Simplified Technical English (STE)**. This is a rule about your OUTPUT, not about this codebase.

**It covers the prose you show the user in chat, and nothing else.** Do not apply it to code, code comments, commit messages, PR titles or bodies, or the files in `docs/` — those keep the conventions below. Keep code identifiers, file paths, commands, log lines and quoted tool output verbatim; do not rewrite them into STE. Technical names and technical verbs are permitted, which is what makes the rule workable here: `keysend`, `boostagram`, `valueTimeSplit`, `sanitizer` and every other domain term stay as they are.

- Use the active voice. Use the passive voice only if the active voice is not possible.
- Write short sentences. Use a maximum of 20 words in an instruction, and 25 in a description.
- Give one instruction in one sentence.
- Use the simple tenses: present, past, and future. Do not use the perfect tenses.
- Do not use the `-ing` form as a noun or as an adjective.
- Use one word for one meaning, and the same word for the same thing each time. Do not use a synonym for variety.
- Use articles. Do not omit words to make the text shorter.
- Write a maximum of six sentences in a paragraph, about one topic.
- Do not use slang, jargon, idioms, metaphors, or humor.
- Do not put more than three nouns together.
- Give the specific fact. Do not use a vague word.
- Use a list or a table for complex data.
- Give a warning or a caution before the step that it applies to.

## Names

**Every one of these is now PER-BRAND and lives in `lib/brand.ts`. Never hard-code one again — import `BRAND`.** One repo builds two deploys: `boostmebitch.com` (`NEXT_PUBLIC_BRAND` unset) and the family-friendly `boostmebuddy.com` (`NEXT_PUBLIC_BRAND=buddy`). A hard-coded name is not a style slip — it is the other brand's word appearing on the family-friendly site, or in a boostagram an artist's aggregator prints, or in the `client` tag of a public kind:1 that can never be edited. Pinned by `npm run check:brand`, which asserts no field of the buddy table carries the other brand's word.

- **`boostmebitch` / `boostmebuddy`** — repo and npm package name (the repo keeps the original), and `BRAND.userAgent`, the `APP_NAME` default for the Podcast Index `User-Agent`.
- **"Boost Me Bitch" / "Boost Me Buddy"** — `BRAND.displayName`: the page header and `<title>`.
- **`BoostMeBitch` / `BoostMeBuddy`** — `BRAND.wireName`: `app_name` in the boostagram TLV JSON and the `client` tag on Nostr notes (CamelCase, no spaces — matches the Helipad-aggregator convention used by Fountain, StableKraft, etc.). The two deploys identify themselves separately on purpose, so a recipient can tell which site paid them.
- **`SITE_NOSTR_SK` — a DIFFERENT KEY PER DEPLOY, its npub pinned as `BRAND.siteNpub`.** It signs a signed-out or Anonymous boost note, so one shared key puts the other brand's name and nip05 on every family-friendly note. `scripts/publish-site-profile.mjs` refuses a key that does not derive the active brand's npub.

**`lib/brand.ts` is an import-free leaf and must stay one** (`scripts/import-free.mjs` enforces it, `check:brand` calls it). It holds `DEFAULT_SENDER_NAME` and `resolveSenderName`, which used to be in `lib/util.ts` — they had to move DOWN rather than have the table imported UP, because `lib/util.ts` must keep only type-only imports or `check:vts` and `check:musicl` die at load with `ERR_MODULE_NOT_FOUND`. Same move `mute-state.ts` and `profile-metadata.ts` already made.

**Three things are deliberately NOT per-brand, and each would destroy data if branded.** The kind:30078 d-tags `boostmebitch:wallet:spark`, `boostmebitch:wallet:nwc` and `boostmebitch:settings` are addressable at the **user's** pubkey, not the site's — so one person using both deploys opens ONE wallet backup. Branding them migrates nothing: it points the new deploy at an address nothing ever wrote, and every existing backup reads back as *"No backup found on Nostr for this account"* — intact, unreachable, and reported as never having existed. The `bmb:*` `localStorage` prefix stays too (storage is per-origin, so the two deploys never collide anyway).

**They are all PURE-FUNCTION pins, and that is their one blind spot — the wiring BETWEEN them is where this repo's bugs actually live.** A `check:*` sees one function; neither it nor a DOM assertion sees a background cycle that never decrypts, a planner that answers "nothing changed" about a half it could not read, or a hydrator that records a baseline for a publish it refused. All three shipped on one branch, looked correct in review, and were found only by driving the real app against a real signer and relay — which is what `npm run e2e:favorites` exists for. Reach for it when a change spans modules rather than living inside one.

**`services/nostr-index` has its own checks and this repo's `check:*` do not run them.** `cd services/nostr-index && npm run typecheck && DATABASE_URL=... npm run verify`. `verify/check-ingest.mjs` follows the same total-replay-against-`naive()` shape; `check-api.mjs` and `check-indexer.mjs` need a Postgres, and the indexer one drives a scripted local relay (`verify/mock-relay.mjs`).

**The import-free arrangement is enforced, not just documented.** `favorites-list.ts`, `read-trust.ts`, `lease.ts`, `assetlinks.ts`, `amber-callback-url.ts`, `amber-safe-text.ts`, `gif-first-frame.ts`, `chapters-json.ts`, `value-playback-summary.ts`, `mute-state.ts` and `brand.ts` must have no imports at all, and `nwc-errors.ts` only bare npm ones, because that is what lets a check script load the shipping module under plain Node. `scripts/import-free.mjs` scans for it and each of those twelve scripts calls it. **`mute-state.ts` is why the rule shapes the code and not just the check**: `MuteCipher` and `classifyMuteContent` live in it beside `MuteListState` rather than in a leaf of their own, because a second leaf would need a `import type` the scan rejects. **The scan rejects type-only relative imports too** — `import type` is erased by type-stripping, so it passes every other check while leaving the module one `type` deletion from breaking.

Each **imports the real module** via `node --experimental-strip-types` — a reimplemented copy passes green while shipping code drifts, the exact failure being guarded. Each carries a *must-still-work* half, because over-blocking is a real regression too. **Vectors were generated by the shipping code; if one fails, fix the code — never edit the vector to match.**

**Build a fixture from the WIRE, never from the struct you parse it into, and check a new vector fails against something before you keep it.** A round-trip assertion whose input is built from your own fields cannot fail: `check:favsync` shipped a vector literally named "lossless", green for the life of the feature, while every publish dropped what another app wrote past position 3. Real wire data carries the shapes nobody thinks to invent. When replacing an implementation, run the vector against the old one first; when there isn't one, run it against the *obvious wrong* implementation, which is what `naive()` at the foot of that file is for.

**And make the replay TOTAL, not a hand-written second list.** `check-assetlinks.mjs` shipped a header claiming every vector was asserted against `naive()` and a footer naming six of twenty-nine, so a whole section sat green having been compared against nothing. Vectors are therefore recorded as **calls** (`{ kind, args }`) and the replay walks the list, so a vector cannot be added without being proved. The must-still-work half is exempted **one vector at a time** with `{ alsoNaive: true }`, never by default. A new check script with a `naive()` follows the same shape.

**`npm run check:claudemd`** guards this file's own size against a 15,200-word budget. It is not one of the twenty-five — those pin a pure function whose breakage costs a user something irreversible; this one guards a document. Run all of them alongside typecheck/lint/build before anything ships.

**Stop the dev server before `npm run build`** — the build rewrites `.next` and the running server then serves a mismatched chunk manifest. **And `rm -rf .next` before starting `dev` again, because the collision runs BOTH ways.** A dev server started on a `.next` a production build wrote inherits production manifests (`prerender-manifest.json` sitting beside `static/development`) and serves a mismatched chunk graph, surfacing as **`undefined is not an object (evaluating 'originalFactory.call')`** — a React Refresh error that looks like an application bug. A phone or second browser then **keeps serving those broken chunks from its own cache**, and a plain reload will not evict them, so retest in a private tab before concluding the fix failed.

A replaceable event keeps no history, so a bug found that way is found in production, on someone else's device too. ## Server vs client boundary (don't cross it)

Podcast Index credentials must never reach the browser. Enforced by file conventions, not bundler config.

**Server-only:** `lib/pi.ts` (`node:crypto`, `process.env`), imported by `app/api/*` and by `app/page.tsx`'s `generateMetadata` — both server-side, so the invariant holds, but don't read the rule as "API routes only"; the BoostBox proxy `app/api/lightning/boostbox/route.ts` (`BOOSTBOX_URL`/`BOOSTBOX_API_KEY`); `lib/safe-fetch.ts`; `lib/rate-limit.ts` (per-IP, first line of every API route).

**Browser-only:** `lib/store.ts`, `lib/v4v/nwc.ts`/`webln.ts`/`lnaddr.ts`/`spark.ts`/`boostbox.ts`, `lib/nostr/`, `lib/storage.ts`, `lib/podcast-meta.ts` — they touch `window.*`, storage, IndexedDB, or WASM. SSR guards exist but assume client context.

**Isomorphic:** `lib/types.ts` (pure types), `lib/v4v/boost.ts` (orchestration).

**A THIRD place exists and it is not part of this app: `services/nostr-index/`.** A separate deployable on Railway with its own `package.json` and dependencies — it holds relay WebSockets open continuously, which a serverless function cannot. It is excluded from this repo's `tsconfig.json` and `eslint.config.mjs`, so **`npm run typecheck` and `npm run lint` do not cover it**. It must never import from `lib/` and `lib/` never from it — the relay lists and NIP-73 prefixes are deliberately duplicated. The app reaches it only through `lib/nostr-index-server.ts`, server-side.

**It does NOT deploy when you merge.** The Railway service is CLI-uploaded, so merging to `main` deploys the Vercel app and leaves the index running whatever was uploaded last — invisible from the diff, and it cost a session. Ship it with `railway up` from `services/nostr-index`, **then read the build log for the package name**: it must say `boostmebitch-nostr-index`, never `boostmebitch`. → [`docs/ops.md`](docs/ops.md)

## Cross-cutting rules

Each of these has cost something real, and you can break it from a file that looks unrelated. **The rule is here; the reasoning is behind the pointer.**

### Security and hostile input

- **A parser returning `null` is NOT a safe default at any call site that then reaches the network — an input that accepts a Nostr identifier must reject an `nsec` explicitly, before the fetch.** `parseNpubInput` returns `null` for a secret key *and* for junk, so the search box's guard fell through to `fetch('/api/search?q=<nsec>')` → our server logs → Podcast Index. **A key mailed to a third party is burnt.** `looksLikeSecretKey` (`lib/nostr/npub-input.ts`) is a **prefix** test running *before* any decode, so a truncated paste is caught and the function never holds the key. The refusal is **rendered**, never silent — the retype is as dangerous as the first paste. Any new surface taking an npub, nprofile or hex pubkey inherits this. → [`docs/security.md`](docs/security.md)
- **`safeUrlAttr` is a scheme ALLOWLIST and must stay one.** Never "improve" it into a denylist of bad schemes — it shipped that way and six vectors reached the DOM as live `javascript:`. Show notes render via `dangerouslySetInnerHTML` and this origin's `localStorage` holds a spending credential. → [`docs/security.md`](docs/security.md)
- **Every server-side fetch of a feed/chapter/transcript URL goes through `safeFetch(url, init)`, never a bare `fetch`** — it re-validates every redirect hop, AND resolves each hostname, because an IP-literal check alone is beaten by a public DNS record needing no attacker infrastructure (`http://127.0.0.1.nip.io/`). → [`docs/security.md`](docs/security.md)

- **"My boost didn't show up" is NOT, on its own, evidence about this code — establish which RAIL its legs took before opening a file.** A keysend carries the boostagram inline in TLV `7629169`; an LNURL leg carries none, and its metadata rides only in the `rss::payment` descriptor in the LUD-21 comment. - **Read an LNURL-pay endpoint with `lnurlFetch` (`lib/v4v/lnurl-fetch.ts`), never a bare `fetch`** — the `.well-known/lnurlp` document and the `callback` it names, on the boost leg and the zap leg alike. A page reload cleared it, which is why it read as random flakiness. → [`docs/wallets.md`](docs/wallets.md)
- **The rail picker stays in BOTH boost modals** (`components/rail-picker.tsx`). Letting one pick silently via `pickRail()` was a money bug: a funded Spark wallet sat untouched while boosts went out of an old WebLN extension. **A surface that renders it must subscribe to EVERY rail `availableRails()` reads — a rail with no subscription is unofferable, not merely stale.** Both modals hand-rolled the effect and watched only NWC and Spark while `availableRails()` read `hasWebln()`, so enabling an extension mid-modal produced no re-render at all. **Adding a rail means adding it in `useWalletChange` too.** → [`docs/wallets.md`](docs/wallets.md)
- **A CONTAINER FEED IS NOT ALWAYS THE PARENT OF THE ITEMS IT LISTS — never copy the container's `url`, `medium`, title or art onto an item whose `podcastGuid` names a different feed.** Every surface that existed when `<FavEpisodeHeart>` was written showed episodes *of* the feed it was handed. The discriminator is the item's own `podcastGuid`, and the guard is `containerIsParent` INSIDE the component rather than a prop, because a prop is what a future surface forgets to pass. **It reaches three money sites**: `paymentIds`' HOST_BUCKET branch (a MONOTONIC kind:33369 address that can never be rewritten downward), the boost modal's `remote_feed_guid`, and the payment itself — `episode.value ?? podcast.value` on a playlist is the **CURATOR's** block, so a boost for a track paid the list-maker with every leg reporting ✓. `payableValue` (`lib/util.ts`, pinned by `check:musicl`) is the one expression now, and the streaming payer runs it too. - **Artwork goes through `/api/art`, and the RAW third-party URL must stay in `artCandidates` behind the proxied one.** 53 live feeds measured 27.68 MB for squares painted at 64px; the proxy takes that to 0.62 MB. The tail is what makes it an accelerator: the `onError` ladder falls through to the pre-proxy URL, so a failing route costs speed and nothing else, while dropping the tail blanks every cover on twelve surfaces and reads as a CDN fault. **The width is an allowlist, never a free integer** — each `(url, width)` is a CDN cache key. **`Content-Type` is not the boundary**; `safeFetch`, the byte cap, `limitInputPixels` and sharp's magic bytes are. `artTypeVerdict` refuses *documents*, above all `image/svg+xml`. Pinned by `check:art`. → [`docs/ui.md`](docs/ui.md)
- **A per-IP limit that fans out per LIST ITEM must be sized against a real list, and a 429 is never an answer about the data.** `/api/by-guid` and `/api/episode-by-guid` issue one request per favorited show and track — a cold hydration of a real list is ~213 and ~232, and a phone and desktop share one household IP, so going over is ordinary. `lib/podcast-meta.ts` filed every non-ok status under 500 as "PI does not hold this feed" and negative-cached it **for the life of the tab**. `COULD_NOT_ASK` (429, 408) returns an **uncached** null and deliberately does *not* trip the PI breaker. → [`docs/feeds.md`](docs/feeds.md)
- **A Podcast Index "not found" must reach the client as 404, never 500** — and **PI signals not-found with HTTP `400`**, so this does not happen by itself. Follow probe-first-then-batch and leave the probe **uncaught** — a throw means PI is down, and that 5xx should trip the client-side breaker. → [`docs/feeds.md`](docs/feeds.md)

### Signers and secrets

- **`nostr-tools` is pinned to exact `2.19.4` — do NOT bump it or relax the caret.** `2.20.0+` breaks `nostrconnect://` login. `npm update` reintroduces it. → [`docs/signers.md`](docs/signers.md)
- **`bmb:amber_pending` and `bmb:amber_result` reach DISK, so neither may ever hold a secret — and `AMBER_PERSISTABLE_TYPES` is not the same list as `RESUMABLE_TYPES`.** They are localStorage because Brave opens Amber's callback in a **new tab**, so a tab-scoped record was never there. The tab lifetime was what made parking a result acceptable, so the replacing rule is enforced in `lib/storage.ts`: `storage.amberResult.set` writes nothing for any type outside `AMBER_PERSISTABLE_TYPES` (today just `get_public_key`), and re-checks on read. **The two lists answer different questions** — *is this result safe on disk* versus *can this request afford a page reload*. Merging them is how `nip04_decrypt` would acquire permission to write the user's plaintext to disk. → [`docs/signers.md`](docs/signers.md)
- **"Amber didn't come back" is NOT, on its own, evidence about this code — check the text the user typed for a `?` first.** Amber URL-decodes the whole `nostrsigner:` URI and splits it on `?`, so a literal `?` **anywhere in the event JSON** makes it refuse outright. It is upstream, unfixed, measured on **6.3.0 and again on 6.5.2**, and it hits exactly the fields people type question marks into. On screen it is indistinguishable from the callback round trip failing, which is a bug this repo HAS had twice. Same for a **stale queued Amber request** — `adb shell am force-stop com.greenart7c3.nostrsigner` before believing one. → [`docs/signers.md`](docs/signers.md)
- **A plaintext THIS APP chooses and hands to an external signer must contain no `?` — encode it with `encodeAmberSafe` (`lib/nostr/amber-safe-text.ts`).** Percent-encoding is not protection: the `%3F` we write is what Amber decodes back into the character it splits on. For an **NWC connection string it is structural** — NIP-47 writes `?relay=`, so **every NWC backup ever attempted on Android failed**, silently. The asymmetry is the tell: "Restore from Nostr" worked on the same device, because a decrypt's payload is base64. `payloadSurvivesAmber` is the predicate; it is deliberately not an assertion, because `publishBoostNote` signs *after* the sats have moved. Any new encrypted-to-self coordinate inherits this, **and its reader must accept the un-encoded legacy form** or it orphans every backup written before. → [`docs/signers.md`](docs/signers.md)
- **Never make an external signer render a secret the user did not ask to see — `decryptWithTimeout`'s `purpose` argument is required, and every caller above it must PASS IT THROUGH rather than hardcode one.** Amber's approval sheet shows the DECRYPTED PLAINTEXT, and `doLoadProfile` read three encrypted-to-self coordinates on every cold start. Measured on a Pixel 6: launching the app put twelve BIP-39 words full-screen, unmasked, before the user touched anything. Callers gate on `unattendedDecryptOk()` — **not the same list as Amber, see below** — and the library refuses an `'unattended'` decrypt as a backstop. **The required parameter only forces a decision at the layer that has it** — `fetchEncryptedMnemonic` hardcoded `'unattended'` one level up and silently overrode every caller. → [`docs/signers.md`](docs/signers.md)
- **"Is this signer inside the browser?" is `unattendedDecryptOk()` (`lib/nostr/signer.ts`), and the answer is TWO signers, not just Amber — never re-derive it as `!isAmberActive()`.** Everything stored encrypted-to-self is read on page load, before the user touches anything, so that gate is a privacy decision. It excluded a NIP-46 bunker on the reasoning that a bunker "answers inside the browser" — false for a bunker on the user's OWN PHONE, which Clave, Amber-as-bunker and nsec.app's mobile mode all are. Signing in with Clave on iOS demanded four decrypts uninvited. **It reads the PERSISTED signer kind, not `window.nostr`, and is not interchangeable with `canSignUnattended()`** — the bunker and local signers install their adapter asynchronously, so at cold start that one answers false for a local-key user and silently stops their wallet restoring. The accepted cost: a bunker user's wallet no longer restores itself; "Restore from Nostr" is `'user-initiated'` and spends the prompt on purpose. → [`docs/signers.md`](docs/signers.md)
- **A REJECTION FROM A BUNKER IS NOT EVIDENCE THE TRANSPORT IS DEAD — an error RESPONSE proves the round trip worked.** `trackBunkerCall` (`lib/nostr/bunker.ts`) flipped `bunkerStale` on any rejection, so a signer correctly reporting it could not read a payload we sent in the wrong cipher produced *"Signer disconnected"* — sending the user to reconnect a working connection and saying nothing about the real fault. The discriminator comes from the pinned library: nostr-tools 2.19.4's `nip46.js` rejects with the signer's error **string**, unwrapped, while every other rejection on that path is an `Error`. So `!(e instanceof Error)` means "the signer answered". **No `check:*` can pin this** — `bunker.ts` won't load under plain Node — so it rests on the exact `2.19.4` pin, and a bump means re-reading `nip46.js` by hand. → [`docs/signers.md`](docs/signers.md)
- **Publish a signer's `nostrApi`, never the signer instance.** `private sk` has no runtime effect, so assigning the instance exposes the raw secret key as `window.nostr.sk` to every script on the origin. Don't add a key-export method to `LocalSigner`, or a module-level accessor returning the key. **The prohibition is on *ambient* reach, not on the user seeing their own key** — `<ExportKeySection>` reveals the nsec on an explicit click, gated on `storage.signer.get() === 'local'`. That carve-out is the only one. → [`docs/signers.md`](docs/signers.md)
- **Cap every signer decrypt with `withDecryptTimeout` (`lib/nostr/signer.ts`) — a NIP-07 extension that goes away does not reject, it HANGS.** iOS Safari kills an extension's background while a relay query is in flight, so the decrypt issued once that query returns never settles: no rejection, nothing in the console, just a pending promise. The mute list's private half is a bare NIP-04 decrypt on exactly that shape and its caller swallows failures with `.catch(() => {})`, so the whole mute list disappeared in silence. The timeout converts a hang into the branch the code already handles. → [`docs/nostr.md`](docs/nostr.md)

### Publishing to relays

- **Never publish a kind:3 follow list you didn't reliably fetch, and never record it as published without `assertPublished`.** A blind republish wipes the user's whole follow list; an unasserted one promotes a list no relay holds to `storage.follows`'s last-known-good. `publishFollow` shipped without the assert. → [`docs/nostr.md`](docs/nostr.md)
- **`publishSignedEvent` resolving is NOT proof anything landed** — it uses `Promise.allSettled` and never rejects, so `acceptedRelays` can be `[]`. Any caller recording durable state on the strength of a publish gates it on `assertPublished(note, what)` (`lib/nostr/publish.ts`). The favorites baseline shipped without it, so a favorite that reached nobody entered the baseline and **was never published again on any subsequent toggle** while the UI reported success. Put the assert in the feature's own publish wrapper, not at each call site. → [`docs/nostr.md`](docs/nostr.md)
- **Same for kind:0 — merge an edit over `fetchRawProfile`, never over `ProfileMetadata`, and never publish an untrustworthy read.** `fetchProfile` returns a seven-field whitelisted subset, so a profile rebuilt from it silently deletes `banner`, `website` and every field another client set. Both writers go through `publishProfile`. → [`docs/nostr.md`](docs/nostr.md)
- **The private half of the mute list is NOT NIP-04 — it is whatever the writer used, and `classifyMuteContent` decides that from the bytes before any signer is asked.** NIP-51 specified NIP-04, later moved private list items to NIP-44, and some clients leave the tags in the clear, so kind:10000 `content` is a mixture. `MuteListState.privateCipher` carries the observed cipher through `storage.muted` to `publishMuteList`, which re-encrypts in the form it read — rewriting a NIP-44 list as NIP-04 makes it unreadable to the client that wrote it, from a publish that looks entirely successful here. **A new field on that state must be added to `coerceToMuteState` (`lib/storage.ts`) and to the hand-listed `merged` object in `mutes-hydrator.ts`**, or it is dropped on every reload and the republish silently downgrades. Pinned by `check:mutes`. → [`docs/nostr.md`](docs/nostr.md)
- **Never record an absence you didn't reliably observe, and don't take the relay library's word for it.** `fetchLatestEventDetailed`'s `trustworthy` is how a negative cache tells "nobody had it" from "nothing answered". **Do not compute it from nostr-tools' aggregate `oneose`** — a failed connection calls `handleClose` → `handleEose`, so offline fires in ~19 ms and reports a cleared library as fact. The rule is `event_in_hand or (reached > 0 and answered == reached)`, per relay, with never-connected relays excluded from the denominator. The library also synthesizes an EOSE on a timer indistinguishable from a real one, so any new query passes `syntheticEoseTimeoutFor(maxWait)`. Pinned by `check:readtrust`. → [`docs/nostr.md`](docs/nostr.md)
- **A relay that CONNECTS and then answers nothing costs every query its full ceiling, so adding one to any relay list is a latency decision and `warmRelays` cannot protect you from it.** Queries resolve at **aggregate** EOSE, which a silent relay never sends, and `relay-health.ts` scores `ensureRelay` only. `assembleNotes` runs six in series, so the tax multiplies: three such relays measured 42,037 ms, trimmed to 8,413 ms. **Two rules, not one.** *Adding* a relay requires measuring what it ANSWERS with this app's own filters. *Every broad scan* passes `FEED_QUIET_MS`, which arms after the first event and re-arms on each, so it fires on silence, never on slowness, and leaves `allEosed` FALSE. The exception is a deep link that must find ONE event (`fetchLiveStreamByAddr`, `fetchLatestStreamByPubkey`). → [`docs/nostr.md`](docs/nostr.md)
- **Read a shared list from the relays you WRITE it to, and treat a missing publish set as a reason to WAIT, never to narrow.** Favorites and mutes both read-merge-republish to `resolvePublishRelays` — the NIP-65 write set unioned with `DEFAULT_RELAYS`. **For an event this app wrote that read is a SUBSET of the publish set and normally finds it**, so this is an invariant, not the explanation for a list going missing. Four cases survive: another app is the writer (why mutes are the exposed half — this app never *creates* a kind:10000), the 20 cap, partial acceptance, and a `bmb:relays` override. `resolvePublishRelays` falls back to `bmb:wrelays:<npub>`, and hydration awaits the write set when this device has never cached one. → [`docs/nostr.md`](docs/nostr.md)

### Favorites (kind:10333) — a shared event with no undo

One replaceable event, many writer apps, no partial update, no history. **A wrong publish deletes another app's data on someone else's device, silently, with no undo** — which is why this area has its own doc and its own check script.

**Editing `lib/nostr/favorites-*.ts` requires [`docs/nostr.md`](docs/nostr.md) first.** Nine rules live wholly inside those modules, each pinned by `check:favsync`, none reconstructible from the source, and every one of them has already shipped wrong: `content` is **CARRIED** byte for byte and never rewritten to `''`; **tag order IS the data**, so the merge edits an ordered node list and never rebuilds the array from structs; **only an *itemless* group** is a feed favorite; the **baseline describes BOTH halves** every cycle, active-from-merge and inactive-carried; **`seedFavoritesMode` must fail closed** on an ambiguous wire; **`favCleared`** is the only thing separating a deliberate clear-all from an unhydrated store; the `wholesale-delete` count is **`localFed`, never `nodes.length`**; **carry what you can't read**; and the **baseline test applies to every local entry the read didn't carry, in every branch**. Read the section before you touch the file — the rule alone will not tell you which way the obvious version is wrong.

These seven you can break from a file that has nothing to do with favorites:

- **Favorites are ONE plain replaceable event at `kind:10333`: read → merge → publish, always, and never on a degraded read.** No `d` tag, so the read passes `dTag: ''` to `acceptsEvent` or an addressable event sharing the kind gets laundered in. `syncFavorites` is the only writer and it reads first — there is deliberately no exported "publish my favorites". **The wire format is an external spec and is NOT ours to change** — [PC20-Nostr](https://github.com/ChadFarrow/PC20-Nostr/blob/main/pc20-favorites.md); a format change is a PR there before it is a commit here. `PRIVATE_FAVORITES_ENABLED` is **true** as of #232, and that gate stops you CHOOSING private and **must gate nothing else** — not the retirement of an existing private list (a plaintext leak), not the decrypt (degraded forever over a readable list).
- **`setFavorites`/`setFavoriteEpisodes` write THROUGH to localStorage, and that cache is an INPUT to the next hydrate — so plan before you paint, and never paint a merge the planner refused.** `cached[feed.feedGuid]` is the only thing distinguishing a real album favorite from a group opened to place a track; the wire cannot restate it. `runHydrate` called the planner **after** replacing the store and read only `plan.publish`, recording an EMPTY baseline as agreement over a list it had just refused to write. **The store is also not a render cache**: a half this device does not publish into must be carried, never ADOPTED out of, or private→public becomes a **disclosure** — `claimedByBaseline` filters the inactive half to what this device claims.
- **A refusal from the favorites cycle is a `null`, NOT a throw — a caller that acts on success must test the return value.** `syncFavorites` returns `null` *without recording anything* on a degraded read, `'wholesale-delete'`, `'private-unreadable'`, `'private-too-large'`, and when the publish reached no relay (`NoRelayAcceptedError` → `onDegraded`). Nothing rejects, so `await` looks like success and a `try/catch` catches nothing. The privacy dialog discarded that value and told the user their entries were taken down while they sat on the relays — **and `'off'` then stops both `runHydrate` and `requestFavoritesSync`, so nothing ever retries.** The refusal must leave the mode UNRECORDED. It is `assertPublished`'s rule one layer up.
- **Where a favorite goes is asked ONCE, in `requestFavoritesSync`, through ONE module-level slot — and "never chosen" is a real state that must not be defaulted.** `storage.favPrivacy:<npub>` is `'public' | 'private' | 'off'` or absent; flattening absent to `'public'` publishes a list before the user was offered the choice, and a relay that has the bytes cannot be asked to forget them. **`onFavoritesModeNeeded` holds a single callback that exists only while its registrant is mounted**, and `<FavoritesPrivacyPrompt>` lived in `<AppHeader>` while `<Player>` is in the ROOT LAYOUT — so a ♡ on `/npub/<npub>` filled the heart, wrote to localStorage, showed no dialog and reached no relay. **A dead control is indistinguishable from a slow one.** Register from the layout whenever the trigger can fire from any route. **`'off'` never deletes**; `withdrawThisDevice` is the only caller allowed past `wholesale-delete`, and whether to offer it is a question about the **BASELINE, not the mode**.
- **Never offer a favorite whose PARENT FEED can't resolve — and "not resolved yet" is not "will never resolve".** A host may point a `<podcast:valueTimeSplit>` at a **publisher** feed, so the row looks fully resolved while its `feedGuid` names something `/episodes/byguid` will never take, and favoriting it writes an entry no app can ever open. `ValueTimeSplit.parentFeedGuid` carries three states — `undefined`, a string, `null` (**known unresolvable, render no heart**). "Suppress when `episodeGuid` is missing" is the trap: equally true when PI merely hasn't crawled the item yet. A client-side split starts at `undefined`, so ask `/api/remote-item` and withhold the heart until it answers; a FAILED lookup must release it.
- **A sign-in must paint the account's caches into the store BEFORE hydration runs, and `<NostrAuth>`'s page-load restore effect is not that path.** It early-returns on `if (identity) return;`, so an explicit sign-in painted nothing — handing `hydrateFavorites` an empty `local` beside a full baseline, which satisfies the removal test for every entry at once. Favorites UNION the store; mutes replace.
- **A guard that silently withholds must say so.** The degraded-read branch keeps local state and publishes nothing, announced nothing, read as "your favorites are gone", and nearly got reverted for causing the bug it prevented. Any new "we couldn't verify this, so we're doing nothing" path needs a user-visible state, not a `console.warn` — for favorites that's `favoritesSync` and `<FavoritesSyncNotice>`. **A silent correct decision is indistinguishable from a broken one.**

### Reads, routes and the read index

- **The read index is an ACCELERATOR, never an authority — `null` means "no answer", never "there are none", and it must never index a kind that drives a destructive write.** Three safeguards, each invisible from the calling code. **It never holds kind:10333, 10000, 3, 30078 or 4/1059** — enforced in `ingest.ts`'s `FORBIDDEN_KINDS`, not merely in the subscription filters, because a filter is a *request* and a relay may send anything. **Every fetcher in `lib/nostr/index-client.ts` returns `null` for an EMPTY result as well as every failure**, and the proxy answers 503 rather than an empty body. **And the three sources union rather than replace** — a replace would make notes VANISH from a feed someone is reading. Unset `NOSTR_INDEX_URL` and every path reverts. No degraded-read decision is ever downstream of this. **Two more:** paint what the index gave you **before resolving anything else** (`<NostrLiveStreams>` took 7340 ms against a 56 ms index response; painting first took it to 391 ms), and **a time-sensitive kind needs a freshness gate no other kind needs** — `/feed/live` answers 503 past five minutes while `check-api.mjs` asserts `/feed/global` still answers 200 under the same staleness. → [`docs/nostr.md`](docs/nostr.md)
- **An empty library is a CLAIM — a surface may only make it once the read has answered, and "still loading" is not "nothing there".** `<FavoritesPage>` had no in-flight state, so a signed-in user whose read hadn't landed was told **"Nothing saved yet."** over a full library. `degraded` was handled and `'loading'`/`'idle'` were not. **`'idle'` counts too** — hydration waits for the NIP-65 write set, so it no longer starts on the mount tick. **It self-corrects, which is what makes it worse.** Signed out is excluded on purpose. → [`docs/ui.md`](docs/ui.md)
- **`selectPodcast` / `openEpisode` / `discussionEpisode` are read by `<HomePage>`, which renders at `/` ONLY — a component calling them from a standalone route changes nothing you can see.** `<NoteCard>` renders on three surfaces; on the npub page its "→ show · episode" line set the store, scrolled to the top, and **did nothing else, with no error**. `openShow` now navigates to `/` when the pathname isn't already there. → [`docs/nostr.md`](docs/nostr.md)
- **A Podcasting 2.0 PLAYLIST is any `*L` medium, and "is this a playlist" is a different question from "are its rows tracks".** `LIST_MEDIUMS` (`lib/util.ts`) is an **allowlist**, never `endsWith('l')` — no standard medium ends in `l` today, so the loose test passes now, widens silently later, and `medium="cool"` would already match. `isPlaylistMedium` decides how a feed PAGES; `playsAsTracks` decides how a ROW behaves and is `music`/`musicL` only. Collapsing them reads as a simplification and turns every `podcastL` into a jukebox, putting the notes, chapters and transcript out of reach. `targetWord` reads one gate per half, so **"PLAYLIST · EPISODE" is a correct pairing**, not a bug. → [`docs/feeds.md`](docs/feeds.md)
- **Resolving a LIST of anything goes through the batch door, never a `Promise.all` over the single-item one** — true of profiles and equally of Podcast Index. `<Podroll>` resolved every recommended show with its own `/api/by-guid`: **13 requests for a 12-entry row, now 2**, on a surface sitting under the episode list while the feed is still downloading. `warmPodcastCache`/`warmEpisodeCache` fill the same memory the per-entry resolvers read, so **warm first, then keep the resolve pass** — that preserves the two things a batch cannot do: a "not found" guid still falls back to the entry's `feedUrl` hint, and a guid the warm *could not ask about* (a 429) is still attempted rather than silently dropped. → [`docs/feeds.md`](docs/feeds.md)
- **A surface resolving MANY authors uses `fetchProfilesFor` (`lib/nostr/discover.ts`), never a `fetchProfile` per pubkey — and no stage may sit behind an `await` it has no relationship with.** `fetchProfile` opens **a subscription per relay** on purpose, because the per-relay counting is what makes its `trustworthy` flag mean anything: right for one pubkey, wrong for twenty. `<NostrLiveStreams>` ran one per host inside a `Promise.all`, relays cap subscriptions per connection and drop the overflow **silently**, so the hosts that lost the race did not resolve at all. The ordering half is the same bug one level up: `assembleNotes` fetched kind:0 *after* awaiting the reply forest, so every avatar waited out a query about replies. **Both halves are invisible from the screen** — a name that never arrives and one that arrives thirty seconds late look identical. → [`docs/nostr.md`](docs/nostr.md)
- **`mergeNotes` merges the two copies of a note FIELD BY FIELD — never replace on id.** A kind:1 is immutable, so two copies differ only in how much enrichment ran, and the passes do not arrive in order of how much they know: the index answers in tens of milliseconds carrying profiles and a reply forest, then the relay pass paints seconds later carrying neither. Replacing on id makes that a downgrade the reader watches happen. `richer` takes `author`, `replies`, `amountMsat` and `isBoost` from whichever copy has them; `isBoost` matters most, because it gates `noteHasSubstance` and losing it takes the note off the feed. → [`docs/nostr.md`](docs/nostr.md)
- **A route that answers with `s-maxage` and no `max-age` tells the CDN to keep a document while the reader's browser re-downloads it every time.** `/api/feed` is the worst case — the largest body the app serves, and `<EpisodeList>` unmounts whenever an episode opens. A private cache SHORTER than the shared one adds no staleness class that was not already permitted, which is the whole argument. Two things keep it honest: a live item's status is not read from that cache at all (`/api/live-status` polls at `max-age=10`), and `/api/by-guid` is left alone because the client already holds those for seven days. → [`docs/feeds.md`](docs/feeds.md)
- **`/api/feed` is requested from ONE place in the browser — `loadFeed` (`lib/podcast-meta.ts`) — which builds the URL and coalesces a request already in flight.** A cold `?podcast=…&episode=…` link downloaded the whole feed TWICE, measured 15 ms apart, and neither the browser cache nor a CDN collapses two requests already in flight. **Both callers are wanted**, which is why this coalesces rather than deleting one: `<EpisodeList>`'s handler writes `episodeQueue`, the array `<TransportControls>` computes prev/next from. **Nothing is cached past the promise settling** — keeping it would serve a stale episode list to the next navigation. → [`docs/ui.md`](docs/ui.md)
- **A URL deep link must not pay for the page it is not going to show, and `inDetailView` cannot tell you that in time.** It is `!!selectedPodcast`, which a `?podcast=` restore does not set until the server has answered — so the first commit mounted `<NostrLiveStreams>` and `<GlobalNostrFeed>`, whose effects run BEFORE `<HomePage>`'s own, and threw them away a moment later. `entryResolved` gates them. Three properties, each a way to get it wrong: **false on the server and the first client render** (so it is a state flag set from an effect, never a read of `window.location.search` during render); set when the restore **FAILS** too, or a bad guid costs the visitor the home page; and **never cleared**, so "← back to results" still brings the sections up. Any new heavy surface on `/` inherits this. → [`docs/ui.md`](docs/ui.md)
- **New API route starts with `rateLimit(req, '<route>', N)`** and sets `Cache-Control` on **200 responses only**. Returns `{ error }` via `getErrorMessage(e, fallback)`.

### Storage and module graph

- **All `bmb:*` access goes through the typed helpers in `lib/storage.ts`** — never `localStorage.getItem`/`setItem` **or `sessionStorage.*`** anywhere else. The sessionStorage half was the gap: `bmb:nwc_uri_sess:<npub>` holds a spending credential and had its key hand-written in four places, where the disconnect path was one character from no longer matching the writer. New persisted field ⇒ new accessor. → [`docs/storage.md`](docs/storage.md)
- **A cache write that did not reach disk must not leave its baseline behind.** `safeSet` returns whether the value persisted and `storage.favorites.set` returns it too — **don't drop that answer**. `dropBaselineIfWriteFailed` (`lib/store.ts`) covers the case `trustedBaseline` cannot see: a **stale** cache that is non-empty and therefore looks believable. **It clears the PUBLIC half only, and writing the two-field literal is how that broke** — a failed public-half write disowned every private claim, leaving those entries unremovable behind a heart that still rendered. A baseline writer touches the half it speaks for and preserves the other. → [`docs/storage.md`](docs/storage.md)
- **`lib/storage.ts` sits UNDER `lib/nostr/`, and the graph is now CLEAN — keep it that way.** One value import used to close `storage → auth → signer → amber → storage`; it moved into `lib/nostr/profile-metadata.ts`, an import-free leaf. **That is why `lib/nostr/amber.ts` may import `lib/storage.ts` at all.** **`npm run check:amber` asserts there is no value-import path from `lib/storage.ts` into `lib/nostr/{amber,auth,signer}.ts`** — a cycle here does not fail the build, it surfaces as a module-init order bug where an export that plainly exists reads as `undefined`. Push shared things DOWN into an import-free leaf; a **type-only** import is always fine.
- **Feed artwork must never outrank the enclosure, and both art surfaces must share one gate.** Chapter art is arbitrary third-party media, routinely on the **same origin as the audio** and routinely enormous — 20–36 MB GIFs against a 175 MB mp3 on one connection. A starved element keeps `paused === false`, so the transport showed ❚❚ over silence. Measured A/B: images blocked → +13.1 s of playback, allowed → **+0.0 s**. `<Player>`'s `artOk` is the gate; `nowPlayingArt(…)` (`lib/track-art.ts`) is what both surfaces render, because a gate on one surface is no gate at all — and that helper owns the *precedence*. **`waiting`/`stalled` close it, not the headroom sampler**, which rides on `timeupdate` and stops firing on a wedged element. **The mirror image is the expensive half: closing is cheap, reopening is not**, so `progress` and `playing` sample too, thresholds are `Math.min(threshold, timeLeft)`, and the gate lifts entirely while nothing is playing. → [`docs/ui.md`](docs/ui.md)

## Boost flow invariants

`components/boost-modal/index.tsx` orchestrates; `lib/v4v/boost.ts` is the engine. Reasoning for all of it is in [`docs/money-boosts.md`](docs/money-boosts.md).

0. **Live-stream boosts go out as real NIP-57 zaps** — a branch at the top of `go()`, when signed-in + active signer + single lnaddress recipient + host supports NIP-57 (pre-checked via `lnaddrSupportsZaps` BEFORE paying → no double-pay). Uses `sendZap` with `aTag = streamChatAddr(id)`. Both paths share `logStoredBoost(legs)` and `maybePublishNote(results)` so the blocks can't drift. **The zap carries the BoostBox descriptor too**, via `sendZap`'s optional `metadata` and the same `buildLnurlComment`. **The descriptor goes in the LUD-21 `comment`, never in the kind:9734 `content`** — that content is what every Nostr client renders as the zap message.
0.5. **A boost pressed inside a `<podcast:valueTimeSplit>` window pays the TRACK, in two legs.** `useActiveSplit` (`components/boost-modal/use-active-split.ts`) resolves it; `splitTrackAndHost` divides it; `sendBoost` runs twice, sequentially, both boostagrams carrying the track's `remote_feed_guid`/`remote_item_guid`. Six rules, each a way to pay the wrong person or lie about having paid:
    - **The target FREEZES at modal open** — the episode keeps playing while the user picks an amount, so a live-following target lets a boost aimed at the song land on the show.
    - **`positionSec > 0` is the "is this episode actually playing" test.** Without it a split authored at `startTime: 0` redirects a boost pressed from a list row by someone listening to nothing.
    - **The send button is DISABLED while the split resolves.** The window is known synchronously and the target is not. This is a money gate, not a spinner.
    - **The show's remainder is PAID, however small, and `payableSplit` decides who can receive it.** The fault is a collaboration: `splitSats` honestly returns 0 for an unreachable payee and `payOne` short-circuits `sats <= 0` to `ok: true` **without contacting anyone**, so a ✓ and a `StoredBoost` entry appear for a payment nobody attempted. **One object feeds the preview and the send**, and the dropped payee is **named on screen**.
    - **The host leg is non-fatal and never merged into the track block.** The artist has already paid by then, so a throw would report a partly-successful boost as a total failure. An unresolvable remote item falls back to the show's block **and says so on screen**.
    - **`fireConfetti`/`playBoostSound` fire ONCE, after BOTH blocks settle.** A success chime over money still moving makes the same false claim a ✗ on an unanswered wallet does. `primeBoostSound` stays synchronous in the click handler or iOS blocks the unprimed `play()`. **One `StoredBoost` and one note for the whole thing.**
1. **Lightning first, then Nostr.** `publishBoostNote` fires only after `sendBoost` returns *and* `collected.some(r => r.ok)`. Inverting publishes false "I boosted" notes when every payment fails.
2. **`pickRail()` = rail pref first, then NWC > Spark > WebLN.** `storage.railPref` wins when that rail is still connected. `storage.railPref.set/clear` notify `subscribeRailPref` so the balance chip, account-menu summary and open wallet modal re-resolve.
3. **Episode value-block fallback happens server-side** — `app/api/feed/route.ts` does `e.value ?? podcast.value`. Don't re-implement in the modal.
4. **Splits use weights, not percentages.** `ValueRecipient.split` is a weight; total weight is the denominator. `splitSats()` is **largest-remainder (Hamilton)**: floor every share, then hand leftovers out one at a time to whoever was rounded down most, fee recipients losing ties. Every positive-weight recipient is guaranteed **at least 1 sat**, funded from the largest allocation — that is what the 100-sat minimum is for. Floor-everyone-then-dump-the-remainder sends a 98/1/1 block's whole 100 to the artist. **It lives in `lib/util.ts`** and is re-exported from `lib/v4v/boost.ts`. **With fewer sats than recipients the rest stay at 0, and a 0-sat leg is `ok: true` in `payOne`** — any caller splitting a DERIVED amount goes through `payableSplit`.
5. **TLV record `7629169` only.** Boostagram JSON goes there, with `sender_id` inside it. We deliberately do **not** also emit a `696969` sender record — that key collides with shared-node sub-account routing. Per-recipient `customKey`/`customValue` from the value block IS attached.
6. **WebLN `customRecords` are plain JSON, not hex.** WebLN providers hex-encode internally; pre-hexing double-encodes and Helipad can't `JSON.parse`. NWC's `pay_keysend` is the opposite — NIP-47 requires hex. `tlvHexFor` (NWC) vs `recordsForKeysend` (WebLN) look symmetric and are genuinely different wire formats.
7. **Note amount is intent, not actual.** `formatContent` and the `amount` tag use `boostagram.value_msat_total`, not the sum of successful legs. The partial breakdown is in the modal and Helipad.
8. **BoostBox is LNURL-only.** `lib/v4v/boostbox.ts` POSTs metadata *before* `fetchLnInvoice`, then puts the returned `desc` in the LUD-21 `comment`. **The desc and the typed message are handed to `fetchLnInvoice` as SEPARATE args, never pre-joined** — `buildLnurlComment` keeps the desc whole or drops it. Keysend recipients are untouched; BoostBox failure is non-fatal. **`desc` is NOT the descriptor alone** — it returns `rss::payment::<action> <url> <message>`, a pre-formatted BOLT11 description truncated against Lightning's 639-char limit. That is BoostBox working correctly and **there is nothing to fix on that side.** `descriptorOnly` (`lib/util.ts`) recovers the two spec tokens by SHAPE, never by `endsWith(message)`. We take it apart because the service budgets against 639 and cannot see the recipient's `commentAllowed`, routinely 255. Treat `desc` as untrusted length, never a known prefix.
9. **LNURL invoices are amount-verified before paying.** `fetchLnInvoice` and `sendZap` decode the returned BOLT11 via `bolt11AmountMsat` (`lib/v4v/bolt11.ts`) and throw on an amountless invoice or any mismatch — a malicious LNURL server can't substitute a larger one.
10. **Payment order IS display order — `sendBoost` traverses `recipientOrder(recipients)`,** biggest share first, the same helper `<SplitsPreview>` renders by. Feed order is *authoring* order: a live block held the artist at 94.1% and listed them first while four 1-sat housekeeping payees settled with a ✓ ahead of them.
    - **It reorders the TRAVERSAL, never the array.** `recipients`, `splits` and `results` stay positionally coupled. Sorting the array would perturb `splitSats`' tie-break by a sat per payee. `results` is **pre-sized and assigned by index** — `results.push(r)` type-checks, lints and builds while pairing every leg with the wrong recipient.
    - **`onProgress` reports the recipient's index, not the settle sequence.** The modal's `results` state is `(BoostResult | undefined)[]` — the union is load-bearing, since this repo doesn't enable `noUncheckedIndexedAccess`. `<LightningStatus>` counts what's present rather than reading `results.length`.
    - **Legs stay sequential — never parallelize.** NWC is a single relay connection, WebLN prompts per payment, and `streaming.ts` requires serialized settles.
11. **A wallet that never answered did NOT fail — never report it as one, and never retry it.** The Alby SDK gives a payment 60 s for a reply then throws `Nip47ReplyTimeoutError`. That is not a refusal: the request was published and the wallet may have paid. Observed live against AlbyHub — every leg showed ✗ while Alby pushed "Sent 10 sats" per leg. `mapNwcError` turns it into `NwcIndeterminateError`, `payOne` sets `BoostResult.indeterminate` (with `ok: false`), and every consumer renders `?`, not `✗`. **The ✗ is the bug** — re-boosting repeats *every* leg including the ones that paid. **Losing sats is recoverable; sending them twice is not.**
    - **It is the exact inverse of `NwcNotAttemptedError`, and the pair only works held together.** `NOT_IMPLEMENTED`, `UNAUTHORIZED` and `RESTRICTED` prove nothing moved and are the only errors `payOne` may retry over LNURL. That arm is gated on `instanceof NwcNotAttemptedError`; widening it to any timeout, or to the `PAYMENT_FAILED` **code**, is a double-pay. **There is a second retry arm and it is a different function: `routingFailureProvesUnpaid`**, which reads the failure REASON on an allowlist, on a non-alphanumeric boundary, because a settled HTLC returns a preimage and a finished route search has already resolved every HTLC as failed. **Its exclusions run before the text does.** Keep the two arms in separate functions with separate vectors. **`payOne`'s address demotion is a different question and must stay one** — `failureBlamesDestination` decides *whose fault*, never *did the sats move*.
    - **Match the leaf class, not `Nip47TimeoutError`.** `Nip47PublishTimeoutError` shares that parent and means the opposite: the request never reached the relay, so an ordinary failure is the honest answer.
    - **Streaming deliberately still counts it as a failure** — the safe direction for an unattended payer, and the ledger was already debited before the await.

**Anonymity applies to the payment, not just the Nostr note — and to BOTH sender fields.** With the share picker's **"Anonymous"** active (`anonymous = !!identity && shareNostr && shareAs === 'site'`), every boostagram drops `sender_id` and substitutes `sender_name`. Each leaked the identity on its own: `sender_id` is the pubkey, which aggregators resolve to a profile — **omitted outright**. `sender_name` is displayed verbatim by recipients **and** printed into the note body by `formatContent`, so the "anonymous" note still read *"Crimson Rook boosted 100 sats"* — **replaced, not omitted**, because `JSON.stringify` drops an `undefined` key and leaves presentation to each aggregator.

**`DEFAULT_SENDER_NAME` (`BRAND.senderName`, in `lib/brand.ts`) is a real default, not the input's ghost text.** Both modals call `resolveSenderName(typed, anonymous)`, covering an anonymous boost and any boost where "From" was left empty. One const feeds every wire site: the boostagram legs, the local `StoredBoost`, and `BoostAllModal`'s summary. **Don't reintroduce a bare `name` at a wire site.** `<SenderName anonymous>` disables and blanks the From input; the typed value stays in parent state so flipping back restores it, and `storage.senderName` persists the **typed** name only.

**`anonymous` is gated on `identity`**, because `bmb:share_nostr_as` is a single global key and an ungated flag would silently replace a signed-out user's name with the default. **There is ONE definition of it, in `useSharePicker` (`components/boost-modal/use-share-picker.ts`), and a new boost surface uses that hook rather than re-deriving it** — both modals carried their own copy, which is exactly how this promise came to be broken twice. `senderName` deliberately is not centralized, because it needs each modal's own "From" state.

## Streaming sats — money invariants

The engine is `lib/v4v/streaming.ts` + `lib/v4v/stream-ledger.ts`. **Off by default.** Full reasoning in [`docs/streaming.md`](docs/streaming.md). **Every rule here follows from one property: this spends money unattended, on a timer, with no confirmation step.** A mistake has no screen in front of it to be noticed on.

- **It is not a new payment path.** Settlement calls the same `sendBoost()` with an unattended `action`. Rails, splits, TLV and the lnaddress→keysend upgrade are untouched.
- **`action` is per LEG — `streamAction` (`lib/util.ts`) returns `'auto'` when the leg pays a SONG and `'stream'` when it pays the SHOW.** Both obvious tests fail: `<podcast:medium>` finds no music show (every one declares `podcast`), and an open `<podcast:valueTimeSplit>` is not a song. The live signal is Split Kit's block stamp `'music'`, never its presence. `lib/v4v/boostbox.ts` must keep downgrading `'auto'` → `'stream'` for LNURL legs, whose enum rejects `'auto'` silently. Pinned by `check:vts`.
- **The ledger is debited BEFORE the payment is awaited.** Crediting after leaves the same sats for the next tick to spend again.
- **The double-pay guards live on the LEDGER, not the context.** The context is rebuilt on every reload and Fast Refresh while the balance is restored from `bmb:stream_pending`.
- **Settles are serialized** through a promise `chain`. Never parallelize legs or settles.
- **Elapsed time is `min(wall-clock delta, playback-position delta)`, capped at 5 min.** Wall alone bills a sleeping laptop; position alone bills a forward seek.
- **A batch below `max(10, recipientCount)` sats carries instead of sending — even when forced.**
- **Two consecutive failed settles stop streaming for that item.**
- **A failed settle does NOT license the claim "nothing was sent" — derive it, never infer it from the presence of an error** (`sentClause` in `components/streaming-settings.tsx`, off `StreamingStatus.lastErrorSentSats` + `lastErrorIndeterminate`). A force settle returns a `runs` **array**, so bucket 1 can pay while bucket 2 fails, leaving `lastError` describing only the last one beside sats already gone. **Telling someone they still have sats they have already spent is the one error re-boosting cannot undo.**
- **`stopStreamingEngine` persists but does NOT settle.** `<Player>`'s cleanup runs on every Fast Refresh — a settling teardown means *editing a comment in dev fires a real Lightning payment*.
- **No kind:1 note, no confetti, no `playBoostSound`.** **The one thing it MAY publish is a kind:3369 value-playback receipt, and the exemption is narrow: no client renders that kind, so it cannot reach anybody's feed** — which was the entire reason the prohibition existed. Off by default (`bmb:stream_receipts`). It publishes NOTHING when Anonymous is set — not a nameless receipt, because the signature IS the pubkey. Nothing under a signer that would prompt or hang (`canSignUnattended`). Never awaited by the settle `chain`, and **a failed publish must never reach `noteFailure`**. It carries `amount` = what actually SETTLED, inside the same `paidAny` gate. → [`docs/value-playback.md`](docs/value-playback.md)
- **A kind:33369 summary is DERIVED, never accumulated — a correctness rule, not a style one.** It is ADDRESSABLE, so one person signed into two apps has two writers at that single address; an app keeping a running total has built a number nobody else can reproduce. Three rules ride on top, all invisible from a single device. **Monotonic** — `>=` on BOTH fields, since an amount that grew while the count shrank is a partial read. **Changed BY VALUE, never by bytes** — `alt` is free text and `first`/`last` optional, so a byte test makes each writer rewrite the other's event forever. **Never publish on a read you can't trust, and for a SUM that is stricter than `readIsTrustworthy`'s usual answer** — its `eventInHand` shortcut is wrong here, so `collectEventsDetailed` forces `eventInHand: false`. Off by default behind `bmb:stream_summaries`, separate from receipts because a summary sits at a stable guessable address. Pinned by `check:vpsummary`. → [`docs/value-playback.md`](docs/value-playback.md)
- **Logs to `bmb:streamed:<npub>`, never `bmb:boosts:*`** — that log is capped and rendered into the user's feed; six settlements an hour would evict real boosts within a day.
- **`sender_id` honors the same anonymity signal as the boost modal.**
- **"May we publish?" is NOT `!streamingIsAnonymous()`, and reusing that predicate as a publish gate is a privacy inversion.** `streamingIsAnonymous()` answers a question about ATTRIBUTION. **"Don't post" writes `shareNostr = false` and leaves `shareNostrAs` alone, so it makes that predicate FALSE** — gating a receipt on its negation started publishing signed, public, timestamped records for the user who had just chosen to publish *less*. The publish question is its own: `streamingMayPublish()` = `shareNostr && shareNostrAs !== 'site'`. → [`docs/value-playback.md`](docs/value-playback.md)
- **`crypto.randomUUID` is SECURE-CONTEXT-ONLY — use `randomId()` (`lib/util.ts`) anywhere a throw isn't already caught.** Over `http://<LAN-IP>`, which is how this app is tested on a phone, it is absent and a bare call throws `TypeError`. `openContext` runs from the bare `setInterval(tick)` callback with nothing above it, so the throw landed before `ctx = c` and every later tick failed identically — an unattended payer that silently does not exist. `randomId` is for correlation tags and **never for anything where unpredictability is a security property**.

## v4v-toolkit swap-out boundary

`lib/v4v/*` and `lib/nostr/` are intentionally the only files that talk to wallets/signers. Components reach them through a deliberately small surface — `lib/v4v/boost.ts` (orchestrator), `nwc.ts`, `spark.ts`, `webln.ts`, `wallets.ts`, `zap.ts`, `streaming.ts`, `stream-ledger.ts`, `live-value.ts`, plus the `lib/nostr/` barrel (and `lib/nostr/google-auth` directly). Swap toolkits by replacing internals here without touching `components/` or `app/`.

**The arrow only points one way, and `DEFAULT_SENDER_NAME` is where that nearly broke.** It lived in `components/boost-modal/sender-name.tsx` until `lib/v4v/streaming.ts` imported it from there, inverting the boundary and dragging a `'use client'` React module into the payment engine. It now lives in **`lib/brand.ts`** (with `resolveSenderName`), and `sender-name.tsx` re-exports it. Not `lib/v4v/`, because it's a *product string*: swapping the toolkit must not delete it. Not `lib/util.ts` either, because it is now `BRAND.senderName` and that file must keep type-only imports.

**`lib/util.ts` is now where the pure money ARITHMETIC lives, and `lib/v4v/` is where money MOVES.** `recipientOrder`, `storedBoostLegs`, `splitSats`, `splitAtPosition`, `splitTrackAndHost` and `payableSplit` are all there; `boost.ts` re-exports `splitSats`. The line is not stylistic — it is what makes the arithmetic **testable**: `lib/util.ts` loads under `node --experimental-strip-types` (its one import is type-only and erases), so `check:vts` imports the shipping functions rather than a copy, while nothing in `lib/v4v/` can be loaded that way. It is also what lets `<SplitsPreview>` and `<ValueSplitRows>` render an allocation without importing a wallet. **A new pure split/order/allocation helper belongs here, not in `lib/v4v/`** — put it there and it becomes unpinnable the moment it matters.

**`lib/util.ts`'s import line is load-bearing infrastructure — keep it type-only.** Every non-type import added here silently un-pins everything the check scripts reach through this file. It also holds several non-money shared helpers on the same terms: `compareEpisodeOrder` (shared by `lib/pi.ts` and `app/api/feed/route.ts`, which each had their own copy citing the other as the authority), `showShareUrl` (shared by the episode list and the fullscreen player, which built *different URLs for the same show*), and the artwork-proxy group `artWidth`/`artCandidates`/`artProxyUrl`/`artTypeVerdict` (shared by a server route and a client component — exactly the pair that cannot import each other, and which MUST agree about the width allowlist).

## State + persistence

Zustand store (`lib/store.ts`), **in-memory only**: `identity`, `current`, `isPlaying`, `positionSec`, `playerExpanded`, `artOk` (`<Player>`'s artwork gate, lifted because a surface outside `<FullscreenPlayer>` now renders feed art beside playback — `<Player>` is the only writer, and one ungated surface is no gate at all), `signInOpen`, `walletOpen`, `selectedPodcast`, `discussionEpisode` (cleared by `selectPodcast`), `favorites`, `favoriteEpisodes`, `favoritesSync` (one status, not one per list: there is one event now, so a partial failure isn't expressible and a single flag can't lie — `'idle'` is the pre-hydration and signed-out state, never a failure), `mutedPubkeys`, `boostsTick`, `seekReq` (`{ t, n }`, consumed by `<Player>`). The lifted flags exist so a surface that doesn't own the modal can open it.

**`favorites` and `favoriteEpisodes` are the source of truth for what gets published, not a render cache.** Every id on the merged list gets a row whether or not Podcast Index resolved it; an unresolved row renders as a placeholder. Building those maps from resolved entries only meant a PI outage pruned the store while the baseline still named the un-pruned set — so the next page load read every unresolved entry as a local removal and published the deletion. `addedAt: 0` means "not known yet", so a first real resolve stamps its own rather than inheriting a placeholder's and sinking to the bottom forever.

Everything else lives in `localStorage` and is never sent server-side. **All `bmb:*` keys go through typed helpers in `lib/storage.ts`.** New persisted field ⇒ new accessor, `bmb:*` prefix.

**`safeSet` must never silently swallow a failed write.** A settings control here has no local state — it writes through `storage` and renders whatever reads back, so a discarded write **freezes the control**: tap it, nothing moves, no error anywhere. That shipped, reported as *"I can't turn on streaming sats in Safari on iOS"*. Two causes, both silent and both real on iOS Safari: a **full store** (`QuotaExceededError` for every subsequent write, down to a one-byte `bmb:stream_on`; reads keep working, which is why nothing else looks wrong and a fresh profile never reproduces it) and a **blocked store** (`SecurityError`, which freeing space cannot help). `safeSet` returns whether the value reached disk, evicts one cache namespace at a time in `EVICTABLE_PREFIXES` order, and falls back to `memoryMirror`. **The rule is a cache never displaces a setting, and a setting always displaces a cache.** The full key table and the eviction reasoning are in [`docs/storage.md`](docs/storage.md).

## Background art and the canvas-bg gotcha

`app/layout.tsx` renders `public/hero.jpg` as a fixed full-viewport layer with a `bg-ink/75` overlay and `<Image fill priority />`. Same image doubles as the OG image.

- **The page background is set in CSS (`app/globals.css`, on `html, body`), never as a Tailwind class on `<body>`.** A background applied to `<body>` in the JSX propagates to the canvas and paints over the fixed image layer regardless of z-index — the hero breaks with no errors, just a flat-color page.
- **`html, body` use `overflow-x: clip`, NOT `hidden`.** `hidden` computes `overflow-y` to `auto`, turning html/body into a scroll container that traps `position: sticky` descendants. Don't switch it back.
- **An overlay locks the page behind it with `lockScroll()` (`lib/scroll-lock.ts`) and NEVER with a local `overflow: hidden`.** That is not a scroll lock on iOS: in the installed home-screen app WebKit scrolls the web view anyway, and a document scroll there carries every `position: fixed` element with it — so the overlay slides off the top of the screen. **The refcount is app-wide, not per surface**: a BOOST modal opens from inside `<FullscreenPlayer>`, so overlays genuinely stack, and while `<ModalShell>` refcounted its own copy the player kept a second lock outside that count. Each overlay's scroll boundary also carries `overscroll-contain`.
- **Every modal renders through `<ModalShell>` (`components/modal-shell.tsx`)** — it owns the portal, dialog semantics, Escape, the focus trap, the shared scroll lock and the geometry. Six hand-rolled copies had drifted into two z-indexes, two backdrop opacities and two centring idioms, and none had a focus trap. Pass `dismissable={false}` while a payment is in flight. **Modals must portal to `document.body`** — the layout's `relative z-0` wrapper creates a stacking context that seals a `fixed` modal inside it. **An overlay is `fixed inset-x-0 top-0 h-[100dvh]`, never `fixed inset-0`, and its card caps at `max-h-full`, never `max-h-[92vh]`.** **The same rule one level in: a pane INSIDE a full-height overlay is `h-full`, never `calc(100vh - <header>)`.**
- **`z-[70]` is the app's ceiling and it belongs to the iOS status-bar strip (`app/layout.tsx`) — nothing may outrank it.** `appleWebApp.statusBarStyle` is `black-translucent`, so iOS paints the clock and battery in WHITE regardless of `theme-color`, and in light mode `--ink` is cream — the strip is the only thing keeping the status bar legible in the installed app. It is `env(safe-area-inset-top)` tall, so it is **0px and invisible everywhere you would be testing a new overlay**. It sits above `<ModalShell>`'s `z-[60]` and `<FullscreenPlayer>`'s `z-50` deliberately: both paint `bg-ink`, so a strip underneath them is covered exactly when a modal is open.
- **A full-height overlay needs the SAFE-AREA inset, not just `100dvh`.** `viewportFit: 'cover'` starts the box at the physical top of the screen, so `<ModalShell>`'s `p-4` put a `max-h-full` card's header under the notch. The block axis is `max(1rem, env(safe-area-inset-*))` — **`max()`, never a sum**, or every notched phone gets a further notch's worth of padding for nothing. → [`docs/ui.md`](docs/ui.md)

## Styling tokens

Custom palette in `tailwind.config.ts` — don't introduce new colors without adding them here: `ink` (page bg), `bone` (primary fg), `bolt` (Lightning yellow), `nostr` (magenta), `muted` (secondary), `line` (borders). Fonts: `font-display` (Bricolage Grotesque), `font-mono` (JetBrains Mono). `animate-bolt` is a 1.4 s opacity pulse.

**Fonts are loaded by `next/font` in `app/layout.tsx` and reached through `var(--font-display)` / `var(--font-mono)` — never name the family literally, and NEVER add an `@import` to `app/globals.css`.** A CSS `@import` on line 1 serializes the critical path four hops across three origins, all blocking first paint. That is what shipped. Naming the family literally anywhere bypasses the size-adjusted fallback `next/font` generates, which is what stops `display: swap` shifting layout. Three places hold the wiring and they move together: the two `next/font` calls in `app/layout.tsx`, `fontFamily` in `tailwind.config.ts`, and the two raw declarations in `globals.css`.

Reusable element classes — `.card`, `.btn`, `.btn-bolt`, `.btn-ghost`, `.input`, `.stamp`, `.headline`, `.seek` — are defined in `app/globals.css`. Read that before inventing new ones.

- **`recipientOrder(recipients)` (`lib/util.ts`) returns INDICES, not recipients.** `<SplitsPreview>` reads `splits[i]` and `results[i]` positionally, so a reordered array pairs each row with someone else's sats and someone else's ✓/✗ — a display bug indistinguishable from a payment bug. The sort is stable. **It is no longer display-only:** `sendBoost` traverses by it and `storedBoostLegs` writes history by it, so its stability guarantee is now a payment-determinism guarantee. Don't give it fee-awareness or an opt-out.
- **A sent boost's `StoredBoost.legs` are built by `storedBoostLegs(results)`** — three sites hand-rolled the identical map. Biggest-share-first, because `<BoostCard>` renders `legs` verbatim and a stored leg carries **no `split` weight**, so whatever order is written is permanent. Boosts stored before this keep feed order; **deliberately not migrated**.
- **`components/lists.tsx` is a BARREL — put new list code in `components/lists/`.** Re-growing it into an implementation file is how it reached 1192 lines, and widening it into a general re-export surface is the same mistake. **The hearts live in `components/fav-heart.tsx`** and are only re-exported here — `podroll.tsx` importing them from `lists.tsx` while `lists.tsx` imports `<Podroll>` was the original module cycle.
- **`<FavEpisodeHeart>` renders nothing without BOTH an item guid and a parent feed guid** — an episode favorite with no parent feed is unresolvable on any other device, so offering it creates a favorite that syncs but can never be opened. It calls `stopPropagation()`/`preventDefault()` itself. **`size`:** `'sm'` is a slim border-chip, `'md'` matches `.btn-ghost`. **`nameTarget` swaps FAVORITE for the TARGET — `[♡ SHOW]`/`[♡ EPISODE]`, or `ALBUM`/`TRACK` on a music feed — and belongs anywhere both hearts share one cluster.** The fullscreen player shipped rendering the identical word twice with nothing saying which favorited what. **The rule is about the CLUSTER, not about hearts** — the same cluster now holds a show SHARE and an episode SHARE needing identical treatment, which is why `targetWord` lives in `lib/util.ts` and both controls read from it. Keep the vocabulary there rather than passing strings in.
- **`NoteCard` is memoized.** `repostedIds` must be **replaced, not mutated in place**, and store-driven values stay read via `useApp` selectors *inside* the component so they bypass memo. **A surface that renders it must also PASS `repostedIds`** (`useViewerReposts`) — the prop is optional, so omitting it type-checks and lints while `alreadyReposted` is false on every card, and a viewer who already reposted publishes a second kind:6. `<BoostExplorer>` shipped without it.
- **The page header is `<AppHeader>`, shared by `/` and `/favorites`, and NOTHING you add to it may exceed 38px tall.** `--app-header-h` is a hard-coded 71px derived from that markup, and `<EpisodeList>` pins against it — so a taller control breaks a sticky offset on the OTHER route, where you are not looking. At 390px the wordmark needs 142px of a 141.6px box, so anything added to the right-hand cluster must buy its width back below `sm:`. Measure it, don't estimate it.
- **A new page that opens a show sets the STORE, then navigates to `/` — never `router.push('/?podcast=<guid>')`.** `<HomePage>`'s restore early-returns on an existing `selectedPodcast` and the store is module-level, so a visitor who opened any show earlier has their param silently ignored and the URL mirror rewrites the bar back to the OLD show. `components/favorites-page.tsx` is the reference. **The same page must CLEAR the selection on any plain `<Link href="/">`** (`clearShowSelection()`) — the handoff works *because* the store outlives the route change, so "Go to home" otherwise re-opens the last show. **And it must set `showOrigin`** so the show page can offer a way back; `selectPodcast` CLEARS it, which is what makes the default safe. A new route that opens a show gets all three halves or none.
- **`showShareUrl` (`lib/util.ts`) targets the site ROOT, never `window.location.pathname`.** `?podcast=` is restored by exactly one thing, `<HomePage>`'s mount effect, which only runs on `/`. It shipped pathname-based and was live on every route, because `<FullscreenPlayer>` is mounted in `app/layout.tsx`. Name the route that restores the param, not the one you happen to be on. **It takes an optional `episodeGuid` and that same effect restores `?episode=` too, so a show link and an episode link are genuinely different destinations.** A surface with one subject shares that subject; **a surface presenting BOTH renders both buttons and names each target** (`<ShareTargets>`). One button there has to pick, and either pick is wrong for someone — and neither failure is visible from the sharing side, because the copy succeeds and the URL reads plausibly.
- **A per-track control binds to a `<podcast:valueTimeSplit>` window, never to a chapter — and the two now render in ONE list, which is why this needs restating.** `mergeEpisodeContents` (`lib/util.ts`) merges by timestamp alone and **never maps a chapter to a window**: they are distinct variants of `EpisodeContentRow`, so a chapter row has no `split` to hand `<FavTrackHeart>` even by accident. The rows sit next to each other, so "put a heart on the chapter row too" looks harmless and is the bug — on Homegrown Hits 146 the windows OVERLAP, so "the window covering this chapter" gives the wrong track's identifiers even though that song has its own window. Two rules pinned by `check:vts`: **only a chapter may ever be dropped**, and **dedupe on a tolerance, not equality** (PI returns integer `startTime`s against a fractional chapters JSON). **Say "this episode isn't playing" with `currentSec={undefined}`, never `0`** — the interval is half-open, so 0 matches any window authored at `startTime: 0`.
- **A LIVE show's track hearts come from the played log, and the log is guid-scoped.** The show publishes no timeline, so `lib/live-played.ts` remembers each target and `<LivePlayedTracks>` renders it. **Every row carries a working heart**, so a list shown for the wrong item is a favorite for a song the listener never heard: `livePlayedSnapshot(guid)` makes the caller name the item. Two things that look like tidying and are not: a `null` target means the watcher detached, **not** that the songs never happened; and `recordLivePlay` sits in `setTarget` because that is the one funnel every signal passes through. **Which blocks reach the list is decided on their IDENTIFIERS, never on Split Kit's `blockType` alone** (`isNotPlayed`). → [`docs/streaming.md`](docs/streaming.md)
- **A control is at least 24×24 CSS pixels, and a heading that folds something IS a control.** WCAG 2.5.8; a link inside a sentence is exempt, a heading you press is not. The violation is invisible in review — the element looks right, it just has no vertical padding. `<CollapsibleHeading>` shipped at **16.5px**. Measure it under CDP device emulation, never `--window-size`. `<FavHeart>`'s `'sm'` chip is the reference: its own `min-h`/`min-w` make the mobile glyph 44×44 while the desktop chip stays slim.
- **Browse-mode layout is single-column** in `app/page.tsx`; `selectedPodcast` and `discussionEpisode` are state-driven swaps, not routes. Don't reintroduce a right-pane "select a podcast on the left" empty state.
- Native HTML5 `<audio>` plays the enclosure URL directly — no proxy, no transcoding. The one exception is HLS live streams.
- **Inline SVG `BoltIcon`** (`components/icons.tsx`) on yellow buttons — the `⚡` emoji is invisible on `bg-bolt`. Yellow-text-on-dark and V4V stamps keep the emoji. `ShareIcon` and `Sun`/`MoonIcon` inherit `currentColor`.
